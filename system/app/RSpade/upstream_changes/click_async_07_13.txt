$.fn.click_async() + Button_Utils BUSY-STATE (CORE ADDITIONS)
Date: 2026-07-13

SUMMARY
    The framework core gained a new jQuery method, $.fn.click_async(handler),
    and the core static class it is built on, Button_Utils, which manages a
    button "busy-state" (locks the rendered size, swaps the content for a
    CSS-animated loader, blocks interaction) with themeable CSS custom
    properties. Both live in /system/ and arrive automatically via the submodule
    merge. This is a NEW capability - nothing in the template used it before, so
    most apps need to do nothing. The ONE thing that can break silently is a
    downstream app that already ships its OWN class named Button_Utils (in its
    theme). Read ACTION REQUIRED item 1 if that is you.

THE CHANGE
    Additions to /system/ core:

    1. $.fn.click_async(handler) in
       app/RSpade/Core/Js/Rsx_Jq_Helpers.js (beside .click / .click_allow_default).
       Binds a click handler that:
         - throws immediately if handler is not a function;
         - auto-preventDefaults and returns this (chainable);
         - on click, puts the element into the busy-state, runs the handler,
           and clears the busy-state when the returned promise settles;
         - ignores re-entrant clicks while a run is in flight (covers
           programmatic .trigger('click') and double-taps past pointer-events);
         - clears on settle ONLY if the element is still in the DOM (a handler
           that navigates the SPA away leaves the detached button untouched);
         - does NOT catch the handler's rejection - it escapes as an unhandled
           rejection and reaches the global handler (console + flash), like any
           other uncaught async error.

    2. Button_Utils - a new core static class, co-located JS + SCSS under
       app/RSpade/Lib/Buttons/ (Button_Utils.js, Button_Utils.scss), bundled
       via Core_Bundle's existing 'app/RSpade/Lib' include:
         Button_Utils.set_submitting($el)   // enter busy-state (idempotent)
         Button_Utils.clear_submitting($el) // leave busy-state (no-op if not busy)
         Button_Utils.is_submitting($el)    // boolean
       set_submitting locks the element's rendered size inline, stashes its
       inner HTML (jQuery .data), swaps in a loader span, and adds the
       btn--submitting class (pointer-events: none). It deliberately does NOT
       set the disabled attribute (that changes form semantics and styling).

    3. The loader is styled entirely in core SCSS and is themeable via CSS
       custom properties (defaults shown) set on .btn--submitting or any
       ancestor:
         --btn-submitting-loader-color      currentColor
         --btn-submitting-loader-size       1em
         --btn-submitting-loader-thickness  2px
         --btn-submitting-loader-speed      0.6s

THE FIX
    Informational only - all of the above lives in /system/ and reaches you via
    the submodule merge on the next `php artisan rsx:framework:pull`. There is
    nothing here to copy into your own code.

ACTION REQUIRED
    For MOST apps: NONE. This is a brand-new capability; adopt it when you want
    a button to show a loader while an async handler runs:

        $('.save-btn').click_async(async function(e) {
            await My_Controller.save(form.vals());
        });

    You only act if the following applies to your app.

    1. You already ship your OWN class named Button_Utils (name collision).
       If your app/theme defined a Button_Utils class of its own (for example an
       app that grew a theme-side button busy-state helper before this landed in
       core), the manifest requires simple class names to be unique across the
       app. Two classes named Button_Utils - yours and core's - collide.

       Remediation: DELETE your theme-side Button_Utils class file on pull. The
       core class provides the same set_submitting / clear_submitting /
       is_submitting surface, so your existing call sites keep working
       unchanged. If your copy used the same btn--submitting class name, your
       existing markup/styles keep working too; if you want to restyle the core
       loader, set the CSS custom properties above rather than reintroducing a
       competing class.

       Find any collision with:

           grep -rn "class Button_Utils" rsx --include="*.js"

       If it returns a file under your app/theme, remove that file. If it
       returns nothing, you have no collision and nothing to do.

    2. Restyle the loader (optional). If your old helper drew a differently
       colored or sized loader, reproduce it by overriding the CSS custom
       properties on .btn--submitting (or a wrapping scope) - no need to touch
       core SCSS or fork the class.

OUT OF SCOPE (DEFERRED)
    A declarative data-attribute variant (e.g. a data-click-spinner attribute
    that wires the busy-state automatically without a JS handler) was proposed
    as an optional follow-on and is NOT implemented. Only the imperative
    .click_async(handler) method and the Button_Utils API ship here. Do not
    write code that depends on a data-attribute trigger - it does not exist.

VERIFICATION
    - grep (ACTION REQUIRED item 1) returns no app/theme class named
      Button_Utils.
    - Bind .click_async() on a button whose handler awaits ~1s: the button shows
      a loader and locks its width while in flight, then restores its original
      content and size on settle. A second click during the run is ignored.
    - A handler that throws restores the button AND surfaces the error globally
      (console + flash), not swallowed.
