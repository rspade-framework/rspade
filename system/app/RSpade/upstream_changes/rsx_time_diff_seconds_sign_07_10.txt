RSX_TIME::DIFF_SECONDS() SIGN FIX - AUDIT YOUR OWN CODE
Date: 2026-07-10

SUMMARY
    Rsx_Time::diff_seconds($start, $end) - and therefore seconds_since($time)
    and seconds_until($time), which delegate to it - was returning the
    NEGATION of the correct value. Any elapsed-time guard your app built on
    these (freshness windows, debounce checks, "expired N seconds ago?" logic,
    TTL comparisons) has been silently comparing against the wrong sign. This
    is now fixed in core. The fix ships to you automatically via the
    `system/` submodule merge - this document is about what YOU need to check
    in your OWN code now that the contract is correct.

THE BUG
    diff_seconds($start, $end) is documented to return the signed seconds
    FROM $start TO $end (positive when $end is after $start). The old code:

        return $end_carbon->diffInSeconds($start_carbon, false);

    had the operands backwards for the installed Carbon version's sign
    convention, so it actually returned $start - $end instead of $end -
    $start. Concretely, for any $time in the past:

        seconds_since($time)   returned a NEGATIVE number (should be positive)
        seconds_until($time)   returned a NEGATIVE number for a future $time
                                (should be positive)

    This was silent - no error, no exception, just a wrong-signed integer -
    which is exactly the kind of bug that hides inside a comparison. A guard
    written as:

        if (Rsx_Time::seconds_since($last_run_at) < $window_seconds) {
            return; // "too soon, skip"
        }

    was ALWAYS true (a negative number is always less than a positive
    window), so the guard ALWAYS fired - the "skip if too soon" branch ran
    on every single call, forever, regardless of how much real time had
    passed. This is precisely how the bug was discovered: a freshness-window
    guard on an external sync integration never let a real pull through
    after the very first one, because the elapsed-time check was
    unconditionally true.

    Rsx_Date::diff_days() (the calendar-date equivalent) does NOT have this
    bug - it was independently verified correct and is untouched.
    Rsx_Time::relative()/is_past()/is_future() also do NOT go through
    diff_seconds() (they use Carbon's own diffForHumans()/isPast()/isFuture())
    and are untouched.

THE FIX
    Core file: app/RSpade/Core/Time/Rsx_Time.php, diff_seconds(). One-line
    operand swap:

        return $start_carbon->diffInSeconds($end_carbon, false);

    seconds_since()/seconds_until() needed no changes - they delegate to
    diff_seconds() and are correct automatically once it is. This ships to
    you automatically the next time you run `php artisan rsx:framework:pull`
    - there is nothing to copy from this section into your own code.

ACTION REQUIRED
    Your own application code may have grown a compensating workaround
    around the old (wrong-signed) behavior, or may have logic that assumed
    the old sign and will now behave differently once the fix lands. Audit
    for both:

    1. Search your app for direct callers of the affected functions:

           grep -rn "seconds_since\|seconds_until\|diff_seconds" rsx/ --include="*.php" --include="*.js"

    2. For each call site, ask:
       - Does the comparison direction assume a NEGATIVE result for "time
         has passed" or "time remains"? (e.g. `> -30` instead of `< 30`,
         or an `abs()` wrapped around the result to paper over the sign).
         If so, that workaround must be removed now that the sign is
         correct - leaving it in place will silently re-invert the logic
         a second time.
       - Is this a freshness/debounce/TTL window guard (e.g. "skip if the
         last run was less than N seconds ago")? These are the highest-risk
         pattern - re-verify the guard actually gates correctly now (test
         both the "too soon, skip" and "stale, proceed" branches).
       - Is this a countdown/expiry display (e.g. "expires in N seconds")?
         Confirm the displayed number is still sensible (it will likely
         FLIP from a small always-negative number to the correct positive
         one - this is expected and correct, but re-check any UI that
         formatted the old negative value defensively, e.g. wrapping it in
         abs() or checking `< 0` to mean "expired").
       - Any raw Carbon `->diffInSeconds(`, `->diffInHours(`, `->diffInMinutes(`,
         etc. calls in your own code (not through Rsx_Time) may have the
         same sign convention footgun on the installed Carbon version. Grep:

           grep -rn "diffIn" rsx/ --include="*.php"

         and manually verify the operand order/sign convention for each hit
         against what you actually intend.

    3. If you found and removed a workaround, or confirmed a guard now
       behaves correctly, mark this change fulfilled:

           php artisan rsx:framework:upstream_changes:mark rsx_time_diff_seconds_sign_07_10 --fulfilled

VERIFICATION
    Framework-side regression coverage (Rsx_Time_Test.php) now locks down:
        diff_seconds('2026-01-01T00:00:00Z', '2026-01-01T02:00:00Z') === 7200
        diff_seconds('2026-01-01T02:00:00Z', '2026-01-01T00:00:00Z') === -7200
        diff_seconds($a, $b) === -diff_seconds($b, $a)   (antisymmetry)
        seconds_since(now() - 3600) is approximately +3600 (was negative)
        seconds_until(now() + 3600) is approximately +3600 (was negative)
        seconds_since(now()) is approximately 0

    For your own code: after auditing per ACTION REQUIRED above, exercise
    each affected guard/display in both directions (elapsed-time-exceeded
    and elapsed-time-not-yet-exceeded) and confirm the branch taken is the
    one you actually intend, not the one that happened to "work" by
    accident under the old inverted sign.
