CATEGORY: 1 - ACTION REQUIRED (one check, and only if a build is currently failing)
TITLE: Orphaned RPC daemons are reaped; RPC startup failures now report what was
       observed instead of prescribing a harmful npm install
DATE: 2026-08-11

--------------------------------------------------------------------------------
WHY YOU ARE READING THIS
--------------------------------------------------------------------------------

A downstream app's `rsx:framework:pull` synced and committed correctly, then failed
its rebuild with all 6 bundles broken:

    Results: 0 compiled, 0 skipped, 6 failed
      - Backend_Bundle
        JS Transformer RPC server failed to start within 10000ms.
        Check that Node.js and Babel dependencies are installed.
        Fix: cd system/app/RSpade/Core/JavaScript/resource && npm install
      - Dev_Bundle
        JS Transformer RPC server socket not found at ...
      ... 4 more, all "socket not found"

Not one clause of that message was true, and the "fix" was actively dangerous.

  * The dependencies were present and resolving correctly.
  * The named directory DOES NOT EXIST (the transformer lives under
    Core/JsParsers/resource), so following the instruction gives
    "cd: no such file or directory" and reads as deeper breakage.
  * `npm install` inside system/ writes into a framework-OWNED zone. That is
    exactly the condition that makes the tamper gate refuse every future framework
    update - a dead-end that cost a full night to escape.

The real cause was two things this release fixes.

--------------------------------------------------------------------------------
1. DAEMONS ORPHANED BY THE STORAGE RELOCATION - DO THIS ONCE
--------------------------------------------------------------------------------

The six node RPC helpers (js-parser, js-transformer, minify, jqhtml-compile,
js-sanitizer, js-code-quality) take their unix socket path as an argv argument AT
SPAWN TIME and never reconsider it. When the one-time storage relocation moved
system/storage -> storage/, every daemon then running was stranded on a path that no
longer existed: still running, still serving nothing. Eight of them were found alive
hours later, and every build failed until they were killed.

The relocation script now reaps them. If your box relocated storage BEFORE taking
this release, check for survivors:

    pgrep -af -- '--socket=.*/system/storage/rsx-tmp/'

Anything listed is stranded on the dead path. Kill it - these daemons hold no state
and are respawned on demand:

    pkill -f -- '--socket=.*/system/storage/rsx-tmp/'

Then re-run whatever was failing. Nothing else is required; boxes that relocate from
this release forward are reaped automatically.

--------------------------------------------------------------------------------
2. STARTUP FAILURES NOW REPORT EVIDENCE
--------------------------------------------------------------------------------

One diagnostic serves all six helpers and states what was OBSERVED, never a guess:
whether the spawned process exited (quoting its own stderr), whether the socket
appeared, whether a stale socket is being held by something, whether the server
script is even on disk. Three conditions that used to collapse into one misleading
message are now distinguished.

The remedy follows from the observation. For a genuinely missing node module the
answer is `php artisan rsx:framework:pull` - an absence in an owned zone is a SYNC
DEFECT, and the message says explicitly not to npm install into system/.

The readiness budget is now a config key rather than a hardcoded 10s:

    rsx.javascript.rpc_server_ready_wait_ms      (default 10000)

Raise it if your box is consistently slow to boot node - the original failure
happened mid-backup on a loaded machine. This bounds a wait on a process that may
never start and degrades to a loud error; it is not a cap on the helper's work.

--------------------------------------------------------------------------------
3. ONE SLOW START NO LONGER FAILS EVERY BUNDLE
--------------------------------------------------------------------------------

The cascade in the report above - one timeout, then five instant "socket not found"
failures - was a state bug. The process handle was published BEFORE the readiness
wait, so a failed start left it non-null and every later caller decided the server
was "already started", skipped the spawn, and died. Nothing ever retried.

The handle is now published only once the daemon is SERVING, and a failed start kills
what it spawned and leaves no trace. The next use is a clean retry, which for a
transient slow boot simply succeeds.

--------------------------------------------------------------------------------
4. SERVICES NO LONGER START BEFORE THE LOCK DAEMON SERVES
--------------------------------------------------------------------------------

`rsx:maintenance:disable` used to start php-fpm on the strength of
`supervisorctl start rsx-lockd` having returned. That confirms a process was spawned,
never that it is serving - and a request that takes a cluster lock against a daemon
which is not yet listening waits with no deadline and no error.

Disable now proves rsx-lockd answers a `ping` before starting php-fpm, printing
"Waiting for rsx-lockd to answer on host:port (Ns)..." while it does. If you see that,
it is working as intended. It waits as long as the daemon takes rather than imposing a
deadline; Ctrl-C is safe (the maintenance flag stays raised).

Nothing to configure. A box with no rsx-lockd unit skips the probe.

--------------------------------------------------------------------------------
5. TWO MORE DAEMON SPAWNS HARDENED (no action)
--------------------------------------------------------------------------------

The js-sanitizer and js-code-quality helpers were spawned without the lock-descriptor
guard the other four already had, so they could inherit and hold a build lock forever.
Same class as the leak fixed last release; both are wrapped now.
