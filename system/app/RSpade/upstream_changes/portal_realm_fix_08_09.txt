FLASH ALERTS AND @csrf ON PORTAL REQUESTS
Date: 2026-08-09 (corrected 2026-08-10)
Category: 2 (framework-core behavior change - audit your own code)

SUMMARY
    Two framework surfaces used to call the STAFF session facade unconditionally,
    on portal requests as well as staff ones:

        Flash_Alert  - every write called Session::get_session_id(), which CREATES
                       a session. On the old two-cookie design that minted a
                       SECOND session and set a second cookie on a portal
                       response. Confirmed live: POST /_portal/login used to
                       answer with both Set-Cookie: rsx and Set-Cookie:
                       rsx_portal.

        @csrf        - the Blade directive emitted the staff token while
                       Portal_Dispatcher verified the portal one, so a portal form
                       rendered while a portal session existed was rejected.

    BOTH ARE GONE, and the second one is gone for good: there is now ONE session
    per browser (one `rsx` cookie, one `_sessions` row, one `csrf_token`), so
    @csrf has nothing to fork on and Rsx_Csrf::enforce() takes no realm argument.
    Flash_Alert queues against the browser's session, whichever experience raised
    it. Nothing about the API changed - Flash_Alert::success() and @csrf are
    written exactly as before, in both experiences.

    Flash alerts also acquired a CLI contract: in console context they no longer
    create a session or touch the database at all. They print to STDERR, and
    warning/error additionally reach the Laravel log.

    ACTION IS REQUIRED IF your app (a) worked around the second-cookie bug - a
    realm column on _flash_alerts, a portal-only flash mechanism of your own,
    suppressed portal flashes; (b) hand-rolled a portal CSRF token input instead
    of @csrf; or (c) calls Flash_Alert from a command, task or seeder.

    If your portal code just calls Flash_Alert and @csrf like your staff code
    does, you have nothing to do - it started behaving correctly on its own.

    KNOWN LIMITATION, STATED PLAINLY. With one session per browser, a flash alert
    queued by a portal page is delivered to whichever page of THAT BROWSER renders
    next - staff or portal. Alerts still cannot cross browsers. Experience scoping
    (an is_portal flag on _flash_alerts, stamped on write and filtered on read) is
    a separate, still-pending change and will ship its own note. If your app shows
    portal-worded alerts on staff screens in the interim, that is this gap; do not
    build a private mechanism around it.

THE BUG
    Both defects had the same shape: a framework surface serving BOTH experiences
    reached for one specific facade.

    The flash one was the more damaging, because Session::get_session_id() is not
    a read - it is "the id of the session, making one if I have to". On the old
    design, calling it during a portal request created a staff session row and set
    a staff cookie for a person who had never visited the staff application. After
    that, a staff CSRF token was demanded and the page could only present its
    portal one, so every portal Ajax call was rejected - permanently.

    The CSRF one was latent in most template layouts (a portal page with no portal
    session emits no token at all, and the pages that DO have one usually redirect
    away), which is exactly why it survived so long.

THE FIX
    Informational - this arrives with the framework update, there is nothing to
    copy.

    Flash_Alert (system/app/RSpade/Lib/Flash/Flash_Alert.php)
        - Writes resolve the session through the REQUEST's own facade; with one
          session per browser both facades return the same id, and the portal
          branch is what carries the portal's site contract.
        - Reads ask has_session() first (which creates nothing), then read that
          session's rows.
        - The per-session cap is keyed on the resolved id, so it is
          session-correct automatically.
        - NO realm/discriminator column was added to _flash_alerts.
        - Console context: no session, no DB read, no DB write. STDERR, plus
          Log::error / Log::warning for those two levels.

    Flash_Alert_Cleanup_Service (new, hourly, #[Exclusive])
        - Deletes _flash_alerts rows older than 30 minutes. The read-path
          1-minute expiry only reaches sessions that come back; an alert queued
          for a visitor who never returns used to sit there until the session
          itself was deleted months later. Nothing to configure or schedule.

    @csrf (system/app/RSpade/Core/Providers/Rsx_Bundle_Provider.php)
        - Emits Session::get_csrf_token() - the browser's one token - and nothing
          else. Same directive, same hidden input name (_csrf_token). Rsx_Csrf
          verifies against the same row on both channels.

    Also in this release, and part of the same arc: a deliberately-built CSRF
    rejection response is no longer replaced by a generic 500 error surface
    (Rsx_Exception_Handler now honors HttpResponseException before the handler
    chain runs). A rejected portal POST returns the documented contract - the Ajax
    error shape on /_ajax and /_portal/_ajax, 419 on a native form POST.

ACTION REQUIRED

    1. Remove flash-alert workarounds.

           grep -rn "Flash_Alert" rsx/portal/
           grep -rn "flash" rsx/resource/migrations/

       If you added a realm/experience column to _flash_alerts (a `session_realm`
       VARCHAR, a `realm_id`, a `portal_session_id`), it is dead weight. Drop it
       with a forward migration:

           php artisan make:migration:safe drop_flash_alert_realm_column

           // up()
           Schema::table('_flash_alerts', function (Blueprint $table) {
               $table->dropColumn('session_realm');   // your column name
           });

       Any app-side code that read or wrote that column comes out with it.

       If you built a portal-only flash mechanism (your own table, a session
       variable, a query-string message parameter) to avoid the second cookie, you
       can delete it and call Flash_Alert directly from portal controllers. The
       template does exactly that:

           // rsx/portal/auth/Portal_Login_Controller.php
           Portal_Session::set_portal_user_id($portal_user->id);
           $portal_user->touch_last_login();

           Flash_Alert::success('Welcome to the Client Portal!');

           return redirect(static::_post_auth_destination($portal_user, $client_id));

       If you SUPPRESSED portal flashes (commented-out calls, an `if (!is_portal)`
       guard around them, a TODO), restore them.

    2. Revert hand-rolled portal CSRF inputs back to @csrf.

           grep -rn "_csrf_token" rsx/
           grep -rn "Portal_Session::get_csrf_token" rsx/

       A portal blade form that builds its own hidden input:

           <!-- BEFORE - the workaround -->
           <input type="hidden" name="_csrf_token"
                  value="{{ \App\RSpade\Core\Portal\Portal_Session::get_csrf_token() }}">

           <!-- AFTER -->
           @csrf

       @csrf emits NOTHING when no session exists yet (a first-visit login page
       has no token to send, and none is required). A hand-rolled input that
       renders `value=""` is worse than absent.

       If you call Rsx_Csrf::enforce($request, $is_portal) anywhere of your own,
       drop the second argument - the signature no longer accepts it.

    3. Audit your CLI callers of Flash_Alert.

           grep -rn "Flash_Alert::" rsx/commands/ rsx/services/

       These calls used to be silent no-ops. They now print to STDERR, and
       error/warning levels also write to the Laravel log. That is the intended
       behavior, but if a scheduled task raises a warning-level flash on every
       tick you will now get a log line on every tick. Either it is worth logging
       - or the call belongs behind a condition, or it was never a flash alert to
       begin with.

    4. Re-test any portal page you previously believed was "just how the portal
       behaves". Sign out, clear cookies, and walk your portal flows once.

VERIFICATION

    - Log in to your portal and inspect the response headers of the POST. There
      must be exactly ONE Set-Cookie, and it must be `rsx`:

          curl -s -D - -o /dev/null -X POST http://localhost/_portal/login \
               --data-urlencode "email=you@example.com" \
               --data-urlencode "password=..." | grep -i set-cookie

      An `rsx_portal=` line means something in YOUR code is still setting it.

    - The flash actually arrives. After the redirect, the portal page's payload
      carries it:

          window.rsxapp.flash_alerts   ->   [{"type":"success","message":"..."}]

    - Exactly one session row exists for that browser:

          SELECT COUNT(*) FROM _sessions WHERE session_token = '<the rsx cookie>';

    - A portal form POST with a stale/absent token returns the documented
      rejection (419 for a native form post, the Ajax error contract for
      /_portal/_ajax) - not a 500 error screen.

    - php artisan rsx:check reports no new findings.

    Full contract: system/app/RSpade/Lib/Flash/CLAUDE.md (SESSION / EXPERIENCE
                   AWARENESS, CLI CONTRACT, RETENTION)
                   php artisan rsx:man csrf
                   php artisan rsx:man portal
