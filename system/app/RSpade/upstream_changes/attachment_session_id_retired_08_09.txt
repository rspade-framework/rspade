_file_attachments.session_id RETIRED - CLAIM WINDOW REPLACES IT
Date: 2026-08-09

SUMMARY
    The _file_attachments.session_id column is DROPPED. It was written at upload
    time and compared against the current session by
    can_user_assign_this_file(); the guard now keeps only the two checks that
    actually mean something - not already attached, and same site.

    A new nullable created_by_ip_address VARCHAR(45) column records the client IP
    at creation, as AUDIT METADATA ONLY. It authorizes nothing.

    Because the session stamp is gone, the bound it implied is now explicit: an
    unattached upload is claimable for
    config('rsx.attachments.unattached_claim_window_hours') (default 24), after
    which a new 6-hourly task SOFT-deletes it into the ordinary retention window.

    The migration runs automatically. ACTION IS REQUIRED IF your app queries or
    writes _file_attachments.session_id, or if it relied on "same session" as an
    upload authorization check, or if any upload workflow can take longer than 24
    hours between upload and attach.

WHY
    The comparison asked the wrong question and answered it unreliably:

    - It read the STAFF session facade (Session::get_session_id())
      unconditionally. A portal upload was therefore compared against a staff
      session id and matched only by accident.
    - It made "may this key be claimed" a property of a browser session rather
      than of the attachment, so an ordinary session rotation between upload and
      save broke a legitimate claim.
    - It was never a per-user permission check in any case, and the framework
      cannot know your app's answer to that question.

    What the framework can guarantee, and now states plainly: the access key is
    64 characters of random hex, an attachment can be claimed exactly ONCE, a
    claim never crosses a tenant boundary, and an unclaimed upload does not
    linger indefinitely. WHO may upload is the mandatory file.upload.authorize
    gate's decision; WHO may claim is your endpoint's.

WHAT CHANGED (informational - arrives with the framework update)

    Schema (migration 2026_08_09_053054):
        _file_attachments  DROP INDEX  idx_session_id
        _file_attachments  DROP COLUMN session_id
        _file_attachments  ADD  COLUMN created_by_ip_address VARCHAR(45) NULL

    File_Attachment_Model:
        - create_from_upload() no longer stamps session_id. It stamps
          created_by_ip_address instead. (Side benefit: uploads no longer MINT a
          session as a side effect of recording one.)
        - create_from_disk() / create_from_string() / create_from_url() route
          through create_from_upload() and inherit the stamp;
          create_external() stamps it too. NULL outside a request context.
        - can_user_assign_this_file() now returns true when: the attachment has
          no fileable_type/fileable_id, AND its site_id equals the current site.
          Nothing else.
        - attach_to() / add_to() are otherwise unchanged, including the
          handler-backed (create_external) exemption.

    New: App\RSpade\Core\Session\Session::get_client_ip(): ?string - the client
    IP as the framework sees it (proxy header chain), null outside a request.
    Creates no session and reads no session state.

    New task: File_Disposal_Service::sweep_unclaimed_uploads, #[Exclusive],
    #[Schedule('every 6 hours')]. Soft-deletes plain-local attachments still
    UNATTACHED past the claim window. Never touches attached rows,
    handler-backed (external) rows, or rows already soft-deleted. A soft-deleted
    row is recoverable (undelete()) for the normal retention period and its blob
    stays pinned - nothing is destroyed by this sweep.

    New config: rsx.attachments.unattached_claim_window_hours (default 24).
    Set it to 0 to disable the sweep entirely.

ACTION REQUIRED

    1. Find any reference to the dropped column:

           grep -rn "session_id" rsx/ | grep -i "attachment\|_file_attachments\|upload"

       Any query, migration, seeder, report, admin screen, or model property
       touching _file_attachments.session_id must be removed or repointed. A
       query naming a dropped column fails loud at runtime, so anything you miss
       will announce itself - but a report that quietly filtered on it will
       simply have been wrong for portal uploads all along.

    2. Re-check anything that treated "same session" as authorization:

           grep -rn "can_user_assign_this_file" rsx/

       Keep calling it - it is still the correct pre-attach check. But if your
       code reasoned "the guard proves this user uploaded the file, so I need no
       further check", that reasoning was never sound and is now plainly not.
       The per-user decision belongs in two places:

         - WHO MAY UPLOAD: your file.upload.authorize #[OnEvent] handler
           (mandatory since the previous release - see
           upstream_changes mandatory_upload_gate_08_09.txt).
         - WHO MAY CLAIM / attach to WHICH record: the #[Auth] gate and the
           record-level checks in the endpoint that receives the key. An endpoint
           that accepts a file key and a record id must verify the caller may
           write THAT record - exactly as it must for any other id it accepts.

    3. Audit upload workflows for the 24-hour claim window:

       A file uploaded and attached in the same request or the same sitting is
       unaffected. Look for anything that can leave a file unattached for longer:

         - multi-step wizards or long-lived draft forms that upload on an early
           step and save at the end;
         - "upload now, an admin approves later" flows;
         - queued/deferred jobs that attach a previously uploaded key.

       If such a flow can legitimately exceed 24 hours, raise the window in
       rsx/resource/config/rsx.php:

           'attachments' => [
               'unattached_claim_window_hours' => 168,   // 7 days
           ],

       Do NOT work around it by pre-attaching at upload time (passing fileable_*
       to a factory bypasses the claim guard and is only appropriate for trusted
       server-side code).

    4. OPTIONAL: if you show upload provenance anywhere, created_by_ip_address is
       now available. Treat it as audit data only - never as a permission input.

VERIFICATION

    - php artisan migrate:status shows 2026_08_09_053054 applied.
    - An ordinary upload-then-attach flow in your app still works end to end.
    - php artisan rsx:task:list shows
      File_Disposal_Service::sweep_unclaimed_uploads.
    - An unattached upload older than the window disappears from live queries
      after the sweep runs, and is still visible via
      File_Attachment_Model::withTrashed() (retention, not destruction).

    Full contract: php artisan rsx:man file_upload (THE CLAIM WINDOW)
                   php artisan rsx:man file_disposal (SCHEDULED TASKS)
