ORM FETCH SERVES NON-DELETED RECORDS ONLY
Date: 2026-08-13

SUMMARY
    The JavaScript ORM fetch (Model.fetch / Model.fetch_or_null, and the lazy
    relationship loads built on them) is now contractually a LIVE-RECORD lookup.
    A soft-deleted row reads as not-found, and a model's fetch() / portal_fetch()
    body must not widen its default scope to serve one.

    A new rsx:check rule, MODEL-FETCH-TRASHED-01, flags withTrashed() inside a
    fetch() / portal_fetch() body (severity high; ordinary rsx:check, NOT a build
    failure).

    ACTION IS REQUIRED ONLY IF ONE OF YOUR MODELS FETCHES TRASHED RECORDS.
    Run rsx:check; if it reports no MODEL-FETCH-TRASHED-01 violations there is
    nothing to do.

THE CHANGE
    Two reasons the ORM lookup stops serving trashed rows:

    1. Client contract. Every consumer of an ORM-fetched record - a view screen,
       a datagrid label, a relationship traversal - is entitled to assume the
       record is live. A model that quietly returned deleted rows made that
       assumption false for every caller of that model, including callers
       written by someone who never read that fetch() body.

    2. A scope-stripped body cannot use the framework's batched preload, so a
       model that strips scopes loads its records one query at a time.

    Deleted-record lookups are not forbidden - they are moved to where the
    server can choose the authorization for that specific situation: an explicit
    #[Ajax_Endpoint]. Being allowed to READ a record is a different question from
    being allowed to read a record that someone deleted.

THE FIX
    Informational - this arrives automatically with the framework update:

    - Core model User_Model::fetch() no longer calls withTrashed().
    - New rsx:check rule MODEL-FETCH-TRASHED-01
      (CodeQuality/Rules/Models/ModelFetchTrashed_CodeQualityRule.php). AST-based:
      it walks every method named fetch / portal_fetch on a model class and
      reports a withTrashed() call at any depth of the body. Suppress with a
      standard @MODEL-FETCH-TRASHED-01-EXCEPTION comment on (or above) the call
      line, with a rationale.
    - The template app (/rsx/) was converted: Client_Model, Contact_Model,
      Project_Model, Party_Model and User_Group_Model dropped withTrashed() from
      fetch(), and the one screen that depended on it - the deleted-client view -
      was rewired onto a dedicated endpoint (see ACTION REQUIRED step 3).

    NOT part of this change for you: the ORM wire contract between the framework
    client and Orm_Controller was also replaced in this release. That is entirely
    internal - the framework JavaScript and the server ship together in this
    update - and requires no downstream action.

ACTION REQUIRED

    1. Find the violations:

           php artisan rsx:check

       and/or grep directly:

           grep -rn "withTrashed" rsx/models/

       Only fetch() / portal_fetch() bodies matter. withTrashed() anywhere else
       in your models (admin endpoints, restore flows, reports, server-side
       display of a deleted author) is untouched and stays legal.

    2. For each flagged body, delete the scope strip:

           // BEFORE
           public static function fetch($id)
           {
               $model = static::withTrashed()->find($id);
               return $model ?: false;
           }

           // AFTER
           public static function fetch($id)
           {
               $model = static::find($id);
               return $model ?: false;
           }

    3. If a screen actually needed the trashed record, give it its own endpoint
       instead. The template's worked example is the deleted-client view:

           Server - /rsx/app/frontend/clients/clients_controller.php

               #[Ajax_Endpoint]
               public static function fetch_deleted(Request $request, array $params = [])
               {
                   $client_id = $params['id'] ?? null;

                   if (!$client_id) {
                       return response_error(Ajax::ERROR_VALIDATION, ['message' => 'Client ID is required']);
                   }

                   $client = Client_Model::withTrashed()->find($client_id);

                   if (!$client || !$client->trashed()) {
                       return ['client' => null];
                   }

                   return ['client' => $client->to_fetch_array()];
               }

           Choose the endpoint's gate for THIS situation. In the template it
           carries the class gate the restore endpoint runs under: whoever may
           restore a deleted client may see the deleted client they are
           restoring. A live record is not the endpoint's business (the ORM path
           serves it) and a missing one is indistinguishable from it - both
           answer with no record.

           Client - /rsx/app/frontend/clients/view/Clients_View_Action.js

               let not_found_error = null;

               try {
                   this.data.client = await Client_Model.fetch(this.args.id);
               } catch (e) {
                   if (e.code !== Ajax.ERROR_NOT_FOUND) throw e;
                   not_found_error = e;
               }

               if (not_found_error) {
                   const deleted_result = await Frontend_Clients_Controller.fetch_deleted({id: this.args.id});
                   if (!deleted_result.client) throw not_found_error;

                   this.data.client = deleted_result.client;
               }

           The ORM fetch runs first; the deleted-record endpoint is asked only
           when it answers not-found; anything that is neither live nor
           deleted-and-visible keeps the original not-found error.

    4. If you genuinely cannot convert a body right now, the rule accepts an
       exception comment with a rationale - but note the record is then served to
       client code that assumes it is live:

           // @MODEL-FETCH-TRASHED-01-EXCEPTION - <why>

       A not-yet-converted model keeps working; it simply fetches unbatched.

VERIFICATION
    php artisan rsx:check                     # no MODEL-FETCH-TRASHED-01 findings

    Then exercise any screen that displayed a deleted record and confirm it
    still resolves it through its own endpoint. A screen that silently lost its
    deleted record will show its not-found state, not an error.

    Reference: php artisan rsx:man model_fetch
               (SECURITY MODEL -> "Non-Deleted Records Only";
                COMMON PATTERNS -> "Soft Delete Handling")
