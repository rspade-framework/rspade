LOGIN_REDIRECT IS NOW PORTAL-CONTEXT AWARE - AUDIT YOUR PORTAL REDIRECT HANDLING
Date: 2026-07-23

SUMMARY
    App\RSpade\Core\Login\Login_Redirect (and its JS mirror) - the single
    intended-URL ?redirect= sanitizer - is now context-aware. It adapts its
    page-path and loop-prevention rules to whether the current request is a
    staff request or a client-portal request (Rsx_Portal::is_portal_request()),
    so the identical four-call idiom (capture / params / hidden_input / consume)
    now works in the portal login flow, including prefix mode (portal served
    under /_portal with no dedicated domain). Two behaviors changed in core that
    downstream code may need to audit; a new config key was added. The template
    portal (/rsx/portal/) was wired to use it - fork owners should replicate that
    wiring and retire any hand-rolled portal redirect mechanism.

THE CHANGE
    Three things changed in core:

    1. The validator now rejects non-page paths.
       Previously capture() rejected framework-internal / asset / Ajax-endpoint
       (/_...) and external API (/api/...) paths, but the validator behind
       params()/consume() did NOT. A hand-threaded ?redirect=/_ajax/foo would
       therefore survive params()/consume() even though capture() would never
       produce it. That capture/validate asymmetry is now closed: the validator
       rejects non-page paths too. A ?redirect= pointing at a /_... or /api/...
       path now degrades to the default in params()/consume(), where before it
       was returned as a valid target.

    2. Portal context rules.
       In a portal request the class consults Rsx_Portal. In prefix mode the
       portal prefix (config('rsx.portal.prefix'), default /_portal) is treated
       as a page namespace: a target must be exactly the prefix or start with
       prefix + '/', the prefix is stripped, and the base rules apply to the
       remainder. So /_portal/workspace/5 is a valid portal target while
       /_portal/_ajax/... and /_portal/api/... still reject, and a non-prefix
       path (/login, /contacts) is rejected in portal context. In domain mode
       portal paths are unprefixed and the base rules apply directly. Staff and
       portal targets are isolated in BOTH directions: a staff redirect can never
       point under the portal prefix, and a portal redirect can never point
       outside it.

    3. New config key: rsx.login_redirect.portal_excluded_prefixes.
       Portal loop-prevention list, expressed in portal-NAMESPACE (unprefixed)
       terms. Framework default:
           ['/login','/logout','/register','/password/reset','/request-access',
            '/impersonate']
       Staff requests continue to use rsx.login_redirect.excluded_prefixes
       unchanged.

THE FIX
    Core files (arrive automatically via the system/ submodule merge - nothing to
    copy from this section):
        app/RSpade/Core/Login/Login_Redirect.php   - context-aware predicate,
            validator now rejects non-page paths, context-aware exclusion list
        app/RSpade/Core/Js/Login_Redirect.js       - identical JS mirror
        config/rsx.php                             - portal_excluded_prefixes key

ACTION REQUIRED
    1. If your portal grew its own redirect mechanism (an ad-hoc ?next= param, a
       hand-rolled "safe next" validator, or a hand-concatenated
       ?next=/?redirect= URL string), CONVERT it to the standard four-call idiom
       now that Login_Redirect works in portal context, and DELETE the duplicate
       validator. There must be exactly ONE redirect sanitizer in the codebase.
       Grep your portal for the anti-patterns:

           grep -rn "next\|redirect" rsx/portal/ --include="*.php" --include="*.blade.php"

       Replace with:
         - Portal_Main::pre_dispatch (the auth rejection point):
               return redirect(Rsx_Portal::Route('Portal_Login_Controller',
                   Login_Redirect::capture($request)));
         - portal login / register forms (Blade):
               {!! Login_Redirect::hidden_input() !!}
         - the portal login / register terminal destination decision:
               Login_Redirect::consume(Rsx_Portal::Route('Portal_Dashboard_Action'))
           (your flow-owned destination - e.g. an invited-client workspace -
           still WINS; consume() supplies only the default).

       The template shows the finished wiring; use it as the reference:
           rsx/portal_main.php
           rsx/portal/auth/Portal_Login_Controller.php
           rsx/portal/auth/Portal_Register_Controller.php
           rsx/portal/auth/portal_login_index.blade.php
           rsx/portal/auth/portal_register_index.blade.php

    2. Audit any code that passed a /_... or /api/... value through
       params()/consume() and relied on it being returned. That path now degrades
       to the default. (This is the closed asymmetry - it was never a sanctioned
       target, but re-verify nothing depended on the old lax behavior.)

    3. If your portal auth routes differ from the framework defaults, override
       rsx.login_redirect.portal_excluded_prefixes in rsx/resource/config/rsx.php
       (portal-namespace / unprefixed terms). Add your own portal login-flow
       routes so a redirect can never loop back into them.

    4. Mark this change fulfilled once your portal is converted and audited:

           php artisan rsx:framework:upstream_changes:mark login_redirect_portal_07_23 --fulfilled

VERIFICATION
    Framework-side regression coverage lives in
    app/RSpade/tests/login_redirect/php/Login_Redirect_Portal_Test.php (portal
    prefix + domain context, cross-context isolation, the closed asymmetry, and
    the config override) plus the staff-side asymmetry additions in
    Login_Redirect_Test.php.

    For your own portal: while logged OUT, visit a protected deep portal URL in
    prefix mode (e.g. /_portal/workspace/5). Assert the 302 goes to
    /_portal/login?redirect=%2F_portal%2F... and, after portal login, you land on
    the deep URL - not the portal dashboard. Repeat with hostile / cross-context
    values (/login, //evil.example, /_portal/login) and assert each degrades
    silently to the portal dashboard. See the portal manual walk in
    rsx:man prelaunch_checklist (entry #1).
