CATEGORY: 2 - ACTION REQUIRED (audit your login flow and your session-terminate endpoints)
TITLE: attempt() now records login history, failures stopped being database rows, and
       cross-user session termination is guarded and THROWS on refusal
DATE: 2026-08-12

--------------------------------------------------------------------------------
WHY YOU ARE READING THIS
--------------------------------------------------------------------------------

Five behaviors changed in the login/session area. Four of them can leave EXISTING
downstream code doing something subtly wrong - double-recording an audit trail,
displaying a statistic that can no longer be true, or silently swallowing an
authorization refusal it now receives as an exception. Read the whole document
once; the greps take a couple of minutes.

    1. RsxAuth::attempt() records login history itself
    2. Failed attempts are no longer stored in the database
    3. Cross-user session termination is guarded, and refusal THROWS
    4. terminate_all_sessions_for_user() is now guarded too
    5. Dev-auth (rsx:debug) no longer stamps last_login
    6. A new session.terminated event you can listen to

--------------------------------------------------------------------------------
1. attempt() RECORDS - REMOVE YOUR OWN record_success() BESIDE IT
--------------------------------------------------------------------------------

    RsxAuth::attempt(array $credentials,
                     bool $record = true,
                     bool $touch_last_login = true): bool

attempt() now writes the outcome to Login_History itself:

    SUCCESS              authenticated
    FAILED_NOT_FOUND     unknown address (a soft-deleted identity included)
    FAILED_PASSWORD      hash mismatch, carrying the login_user_id

It does this because it is the ONLY place that can tell those three apart before
collapsing them into a bool - a caller wanting an accurate status previously had
to repeat the Login_User_Model lookup. Malformed input (missing email or
password) records nothing: nobody offered a credential pair.

ACTION: find app code that records beside attempt() and delete the app-side call.

    grep -rn "record_success\|record_failure" rsx/

The shape to fix:

    // BEFORE - now records TWICE
    if (RsxAuth::attempt($credentials)) {
        Login_History::record_success($login_user->id, $email);
        ...
    }

    // AFTER - attempt() already wrote the row
    if (RsxAuth::attempt($credentials)) {
        ...
    }

If your flow genuinely must record the SUCCESS itself - a two-factor completion,
an invitation acceptance - suppress the framework's recording instead of removing
yours, so a recorded SUCCESS always means FULL authentication:

    // password stage: authenticate, record nothing, stamp nothing
    if (!RsxAuth::attempt($credentials, record: false, touch_last_login: false)) {
        Login_History::record_failure($email, Login_History::STATUS_FAILED_PASSWORD);
        return response_form_error('Invalid credentials');
    }

    $login_user = Session::get_login_user();
    // ... issue the challenge ...

    // challenge passed:
    RsxAuth::login($login_user);                          // stamps last_login
    Login_History::record_success($login_user->id, $email);

    // challenge failed:
    Login_History::record_failure($email, Login_History::STATUS_FAILED_2FA,
                                  null, $login_user->id);

record_success() / record_failure() remain public and are still the right call for
outcomes the framework cannot see (2FA, locked, disabled).

Account state is still YOURS. attempt() checks a live identity plus the password
and nothing else - it does NOT read login_users.status_id, is_activated or
is_verified, and it will not. Those are application vocabulary (owner ruling
2026-08-12). Enforce them in your own login function AND in Main::pre_dispatch()
(which can halt a request; init() is a bootstrap hook that cannot) - the worked
recipe is in `php artisan rsx:man session`, ACCOUNT STATE.

--------------------------------------------------------------------------------
2. FAILURES ARE EPHEMERAL - THE 30-DAY FAILED COUNT IS GONE
--------------------------------------------------------------------------------

Login_History::record_failure() writes NO database row any more. It increments a
per-email and a per-IP counter (expiring on
rsx.sessions.login_failure_window_minutes, default 15) and logs one warning line.

Why: /login is anonymous-reachable, so a persisted failure row was an
UNAUTHENTICATED INSERT - any bot could grow `_login_history` without limit - and
the only consumers of those rows were the two short-window counts. `_login_history`
now holds SUCCESSES only, and is pruned hourly past
rsx.sessions.login_history_retention_days (default 365).

The function signatures did NOT change:

    Login_History::get_failed_attempts_count(string $email, int $minutes = 15): int
    Login_History::get_failed_attempts_count_by_ip(string $ip, int $minutes = 15): int

BUT THE ANSWER IS NOW BOUNDED BY THE CONFIGURED WINDOW. $minutes is accepted and
ignored beyond that: asking for 30 days returns the window's count. A "Failed
logins (30d)" stat therefore cannot mean what it says.

ACTION: find every call and shrink the stat to the window.

    grep -rn "get_failed_attempts_count" rsx/

    // BEFORE - a number that can no longer exist
    'failed_logins_30d' => Login_History::get_failed_attempts_count($email, 30 * 24 * 60),

    // AFTER - label it as what it is
    'failed_logins_recent' => Login_History::get_failed_attempts_count($email),
    // and in the view: "Failed logins (last 15 min)"

Also audit any UI that reads get_history_for_user() expecting failure rows: it
returns successes only now. The status / failure_reason keys remain in the shape
(an app may record its own outcomes), but framework-written rows are all SUCCESS -
a "Status" column on that table is now a constant.

Two consequences stated plainly rather than discovered later:
- A long-horizon failure history ("who attacked this account, from where, over the
  last month") is not answerable from this API. The log line is the forensic
  record.
- Throttling built on the counters FAILS OPEN: under maintenance mode Redis is
  stopped, the increments drop and the counts read 0. Deliberate - a cache outage
  must never lock users out.

Both windows are configurable in rsx/resource/config/rsx.php:

    'sessions' => [
        'login_failure_window_minutes' => 15,
        'login_history_retention_days' => 365,   // 0/null disables the prune
    ],

--------------------------------------------------------------------------------
3. CROSS-USER TERMINATION: A NEW PRIMITIVE, AND REFUSAL NOW THROWS
--------------------------------------------------------------------------------

There was no safe way for an admin to end ONE session of ANOTHER user, and the
function that looked like it did that never worked:

    // BEFORE - terminate_session() is SELF-ONLY. It resolves login_user_id from
    // the ADMIN's own session and puts it in the WHERE clause, so another user's
    // session id matches zero rows and returns false. Every admin "terminate
    // session" button built this way has been reporting a generic failure.
    $success = Session::terminate_session($session_id);

    // AFTER - the primitive that actually exists for this
    $success = Session::terminate_session_for_user($login_user_id, $session_id);

THE GUARD (applied inside the framework, to both cross-user functions): allowed
when the target IS the actor, or when Permission::can_admin_role() passes against
the target's per-site users.role_id. That list is strictly "roles below mine", so
a PEER is refused and a SUPERIOR is refused, by construction. A target with no
users row on the acting site is refused. No acting identity is refused.

Your endpoint still declares its own #[Auth] gate - the SURFACE gate is yours, the
TARGET rule is now the framework's. Core deliberately does not name an
#[Auth_Check] like can_manage_users; that vocabulary is application-owned.

REFUSAL THROWS AjaxUnauthorizedException (403 on the Ajax channel). A false return
now means ONE thing: no matching active row (wrong id, wrong owner, already
terminated, or the actor's own current session).

ACTION: any caller that tested `=== false` to mean "not allowed" must change.

    grep -rn "terminate_session\|terminate_all_sessions_for_user" rsx/

    // BEFORE - the two outcomes were the same value
    if (!Session::terminate_session($session_id)) {
        return response_error(Ajax::ERROR_GENERIC, 'Failed to terminate session.');
    }

    // AFTER - let the exception surface as the 403 it is; false is absence
    if (!Session::terminate_session_for_user($login_user_id, $session_id)) {
        return response_not_found('That session is no longer active.');
    }

Letting AjaxUnauthorizedException propagate is the recommended handling - the Ajax
layer renders it as a 403 with your message. Catch it only if you want a specific
UI.

SINGLE-TENANT ASSUMPTION: the rule resolves the target's role on the ACTOR'S site
while terminating sessions that are scoped to no site at all. On a one-site
deployment those are the same population. On a genuinely multi-tenant install they
are not, and the multi-tenant model is backlogged rather than approximated - do not
build a multi-tenant user-management page on these functions yet. See
`rsx:man session` (SINGLE-TENANT ASSUMPTION, and USER MANAGEMENT PAGES for what
each tenancy model's admin page is permitted to do).

PORTAL: one _sessions row is one BROWSER and may carry a portal identity alongside
the staff one. Terminating it deactivates the WHOLE row, portal identity included.
That is intended; there is no realm parameter.

terminate_all_other_sessions() ("sign out my other devices") is UNCHANGED.

--------------------------------------------------------------------------------
4. terminate_all_sessions_for_user() IS NOW GUARDED
--------------------------------------------------------------------------------

It used to be a bare UPDATE with no authorization at all. It now applies the same
guard and throws the same exception on refusal.

If you call it from an operator-driven endpoint, that is the correct behavior and
there is nothing to do beyond item 3's return-value audit.

If you call it from somewhere with NO acting user - a CLI command, a queued task,
a background consequence of an action you already authorized - it will now THROW
("Session termination requires a logged-in actor"). Move those call sites to the
unchecked internal path:

    // unattended / already-authorized callers
    Session::_deactivate_sessions_for_user($login_user_id, $except_session_id);

It fires the same refresh push and audit event, with scope 'internal' and a null
actor.

--------------------------------------------------------------------------------
5. DEV-AUTH NO LONGER STAMPS last_login
--------------------------------------------------------------------------------

`rsx:debug /path --user=N` logs in through the dev-auth harness, which now passes
touch_last_login: false. A harness login is not a real login, for the same reason
an impersonation identity swap is not.

ACTION: none in code - but if you have been eyeballing last_login to confirm a
harness run worked, stop: it will not move. (It never moved in CLI at all -
Session::set_login_user_id()'s CLI branch returns before the stamp.)

--------------------------------------------------------------------------------
6. NEW: THE session.terminated EVENT
--------------------------------------------------------------------------------

Every deactivated session now fires an audit event and pushes a realtime refresh
to the browser holding it (so the terminated tab reloads into anonymity instead of
sitting on a dead page). Nothing to do - but if you want the audit trail:

    #[OnEvent('session.terminated')]
    public static function on_session_terminated(array $payload): void
    {
        // $payload = [
        //     'actor_login_user_id'  => ?int,   // null on the internal path
        //     'target_login_user_id' => int,
        //     'session_id'           => int,
        //     'scope'                => 'self' | 'admin' | 'internal',
        // ]
    }

CAVEAT: this is not a complete record of every deactivation. The concurrent-session
cap (rsx.sessions.max_web_sessions_per_user) evicts a user's oldest sessions on
sign-in and fires NO event and NO push - it is capacity management, not
termination. Account for that separately if you report on it.

--------------------------------------------------------------------------------
VERIFICATION
--------------------------------------------------------------------------------

- A real interactive login leaves EXACTLY ONE `_login_history` row (not two), and
  `rsx:debug --user=N` leaves none and does not move last_login.
- A wrong-password POST to /login creates NO `_login_history` row, and
  get_failed_attempts_count() for that address goes up by one.
- An admin with authority over the target ends one of the target's sessions and
  the row goes active = 0; the target's next request is unauthenticated.
- The same admin attempting it against a PEER receives a 403, not a generic
  failure - and the row is untouched.
- A user can still terminate their own sessions, and only their own.
