CATEGORY: 1 - ACTION REQUIRED (read the pull output; act only on what it names)
TITLE: Owned zones now converge unconditionally; --force means only "override the
       tamper gate"; system/.gitignore is framework-owned
DATE: 2026-08-11

--------------------------------------------------------------------------------
WHY YOU ARE READING THIS
--------------------------------------------------------------------------------

A downstream app lost 15 framework files from a CURRENT install - 13 migrations,
an error view, and a supervisor config - and every command reported the tree
healthy the whole time. The app ran a release of framework code against a schema a
release behind; `migrate` said "Nothing to migrate"; a missing error view surfaced
later as "View [errors.rsx_error] not found" during an unrelated outage.

Two things were wrong, and they compounded:

  1. The sync only ever handled DELTAS. Three mechanisms - the owned-zone rsync,
     the three-way pass, and the completeness check - each assumed the tree was
     already correct, so any one of them dropping a file made the loss permanent
     while the other two faithfully preserved it.

  2. --force had quietly acquired a SECOND meaning. It was both "override the
     tamper gate" and "actually restore what the release says should be there".
     So the only offered cure for a missing file was the one flag that DESTROYS
     locally modified files - the tool routed people through the destructive
     option to solve the problem that endangers nothing. And on that box --force
     could not satisfy the check anyway, leaving it one command away from being
     unable to take any framework update at all.

--------------------------------------------------------------------------------
DO THIS ONCE
--------------------------------------------------------------------------------

    php artisan rsx:framework:pull

Then READ THE OUTPUT. There are exactly three things it may now tell you.

1.  "N file(s) shipped in this release were MISSING from system/ - RESTORED"

    Framework files were not on disk and have been put back. Nothing is required
    of you - EXCEPT that if the list contains anything under database/migrations:

        php artisan migrate

    A box that lost migrations has been running current framework code against an
    older schema, silently, and `migrate` reported nothing to do because the
    migration FILES were gone. Check the list; this is the case that matters.

    It is also worth asking how they went missing. The known causes are a
    `git clean -fd system`, a bad restore, and a merge with an environment that is
    a release behind (see "A merge can delete framework files" below).

2.  "N file(s) ... are OUTSIDE what this updater can restore"

    Advisory. Never fatal, and it is NOT telling you to use --force. Either the
    release no longer carries those paths - a stale marker from a release whose
    inventory over-promised, which clears itself on the next update - or they sit
    outside both the owned-zone sync and the three-way pass.

    If you deleted them deliberately, nothing needs doing. Otherwise:

        php artisan rsx:git checkout -- system/<path>

3.  "Unauthorized changes detected under framework-owned zones", naming
    system/.gitignore

    See the next section. This is the one case that needs a decision from you.

--------------------------------------------------------------------------------
system/.gitignore IS NOW A FRAMEWORK-OWNED FILE
--------------------------------------------------------------------------------

If you have ever hand-edited system/.gitignore, this pull will stop and name it.
That is deliberate, and the alternative was worse: while it was three-way
reconciled, ONE local tweak preserved the file forever, and that box silently
stopped receiving every future upstream ignore rule. We have already been burned
by exactly this shape on system/config/rsx.php, where a single local edit froze the
file and cost an app-wide outage two releases later.

Decide, once:

    php artisan rsx:framework:pull --diff-system-changes    # see what differs

  * The edit was incidental -> discard it and re-run the pull.
  * You genuinely need the rule -> put it in your PROJECT-ROOT .gitignore instead,
    which the framework never touches, then re-run the pull.
  * You want the release version outright -> php artisan rsx:framework:pull --force
    (this DESTROYS the local edit; that is what --force is for).

Individual owned FILES are now a first-class concept alongside owned directories.
The full owned list is in `rsx:man rsx_upstream`.

--------------------------------------------------------------------------------
A MERGE CAN DELETE FRAMEWORK FILES - AND NOW SAYS SO
--------------------------------------------------------------------------------

This is how the files were lost in the first place, and it is worth understanding
because no tool can undo it automatically.

An environment a release BEHIND has committed the ABSENCE of files it never
received. On a current box those files are untouched since the merge base, so git
has NO conflict to report: it simply applies the incoming deletion, the merge lands
clean, and the loss propagates fleet-wide through shared history.

`php artisan rsx:git` now names every system/ file a tree-rewriting operation
deleted, and points at the repair. It also never resolves a system/ CONFLICT to
absence - if the incoming side carries no content for the path, yours is kept.

The repair is the pull, which is now able to perform it:

    php artisan rsx:framework:pull

Best practice for a fleet: pull the framework on every environment before merging
between them, so no branch is carrying an older framework's absences.

--------------------------------------------------------------------------------
WHAT CHANGED, IN ONE PARAGRAPH
--------------------------------------------------------------------------------

Owned zones are CONVERGENT state, not diffed state: every pull leaves them equal to
the release. A missing file is never read as an instruction - restoring it destroys
nothing, so it happens on an ordinary run and is reported by name. --force governs
ONLY the tamper gate, which protects the case where content is genuinely at stake:
a file you MODIFIED, or an EXTRA file the sync would delete. The completeness check
runs even on an up-to-date install (because "up to date" is a claim about the
marker, not about the tree) and separates what it CAN repair from what it cannot,
so it can never dead-end on a path nothing has the power to fix.

Full contract: `php artisan rsx:man rsx_upstream` (RESTORE IS NOT AN OVERRIDE).
