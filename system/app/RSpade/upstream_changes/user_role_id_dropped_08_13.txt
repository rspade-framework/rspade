users.user_role_id DROPPED - role_id IS THE ONLY ROLE COLUMN
Date: 2026-08-13

SUMMARY
    The users.user_role_id column is DROPPED by a framework migration that runs
    automatically. It was the PRE-ACL role enum (1=read_only, 2=standard,
    3=admin, 4=billing_admin, 5=root_admin), orphaned by the November 2025 ACL
    rewrite that replaced it with role_id (the 100-800 enum) plus the
    user_permissions GRANT/DENY layer. Its $enums block was deleted from
    User_Model at that time; since then nothing has read or written the value and
    every row has held the never-written DEFAULT 2.

    ACTION IS REQUIRED IF your app names user_role_id anywhere - in particular a
    datagrid $sortable_columns entry, which is a live SQL coupling, or a
    user_role_id__label read, which has been displaying a hardcoded default
    string rather than a real role since November 2025.

THE CHANGE
    Migration 2026_08_13_161806_drop_user_role_id_from_users_table:

        ALTER TABLE users DROP COLUMN user_role_id

    MySQL drops idx_users_user_role_id with its only column.

    Nothing in /system/ read the column, so no core behavior changes. The
    template app (/rsx/) is the worked diff - see AFFECTED TEMPLATE FILES below.

ACTION REQUIRED

    1. Find every reference:

           grep -rn "user_role_id" rsx/

       NOTE: _api_keys.user_role_id is a DIFFERENT, unrelated column (the
       reserved per-key role override on Api_Key_Model). Leave it alone.

    2. Repoint any $sortable_columns entry. This is the one that bites - a
       leftover entry produces an unknown-column SQL error the moment a user
       clicks that header, and nothing else will surface it first:

           // rsx/.../users_datagrid.php
           protected static array $sortable_columns = [
               'id',
               'first_name',
               'last_name',
               'email',
           -   'user_role_id',
           +   'role_id',
               'created_at',
               'updated_at',
           ];

       And the matching header in the .jqhtml:

           -   <th $sortby="user_role_id">Role</th>
           +   <th $sortby="role_id">Role</th>

    3. Repoint every user_role_id__label read at role_id__label. These reads
       never resolved: the BEM magic getter only answers for a column with an
       $enums definition, and user_role_id lost its definition in November 2025.
       Every one of them has been rendering its hardcoded default - so the Role
       column in your UI has been showing the same string for every user
       regardless of their actual role. Fixing this CHANGES what the screen
       displays; that is the point.

           // controller payload
           -   'user_role_id__label' => $user->user_role_id__label ?? 'Standard',
           +   'role_id__label' => $user->role_id__label ?? 'Member',

           // template
           -   <%= row.user_role_id__label %>
           +   <%= row.role_id__label %>

       A datagrid whose build_query() returns a User_Model query needs no backend
       change for the label: DataGrid_Abstract serializes rows with toArray(), and
       role_id__label rides along with the enum. A hand-built row array must add
       the key explicitly.

    4. users.role_id is NULLABLE, so role_id__label can legitimately be null for a
       membership created without a role. Where the old code fell through to a
       hardcoded "User"/"Standard", decide what an absent role should actually say
       - the template now says "No role", which is true, instead of naming a real
       role the user does not have.

    5. Check anything that CREATES a users row. Assign an explicit
       User_Model::ROLE_* constant; a bare integer left over from the old 1-5
       vocabulary is not a value in the 100-800 enum.
