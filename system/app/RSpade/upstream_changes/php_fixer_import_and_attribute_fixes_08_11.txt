Php_Fixer NO LONGER CORRUPTS SOURCE (DUPLICATE ATTRIBUTES, STRIPPED IMPORTS)
============================================================================

Category 1 - INFORMATIONAL, mostly self-healing. One thing to check.
Applies to: every downstream app (Php_Fixer rewrites your source on every manifest build).
Date: 2026-08-11


TWO DEFECTS, BOTH FIXED
-----------------------

1. DUPLICATE #[Relationship] ATTRIBUTES - grew on every build.

   Php_Fixer decides whether a relationship method already carries #[Relationship] by
   walking backwards from the `function` keyword. That walk aborted on any token outside a
   small allow-list, and a STRING INSIDE AN ATTRIBUTE'S ARGUMENTS was outside it. So:

       #[Relationship]
       #[Ajax_Endpoint_Model_Fetch]
       #[Auth('is_logged_in')]        <-- this string ended the walk
       public function retainers() { ... }

   ...hid the attribute, and the fixer inserted another one. Every build. Reported by an
   app that watched one method go 1 -> 3 -> 7 attributes across three consecutive builds.

   This hit apps doing the auth-gates migration especially hard, because that release makes
   #[Auth(...)] mandatory on gated relationship surfaces - so the first gated relationship
   you wrote was the trigger.

   Detection now walks whole attribute GROUPS by bracket count, which makes argument
   contents (strings, numbers, arrays, nested calls) structurally irrelevant.

2. STRIPPED FRAMEWORK IMPORTS - on a degraded manifest, or from unscanned zones.

   The fixer deleted any `Rsx\` / `App\RSpade\` import it could not resolve through the
   manifest, treating "the manifest cannot see it" as "the class is gone". Two ways that
   went wrong:

   - A manifest-FATAL rule violation (a code error you would want to be told about) aborts
     a build part-way, so the next rebuild runs against a PARTIAL index and imports that
     were perfectly valid became unresolvable.
   - Some framework directories are deliberately never scanned, so imports of classes
     living there were unresolvable even on a healthy index.

   And the deletion did not heal itself: the re-add pass could not see a trait `use` inside
   a class body, so a stripped trait import never came back - after which every build
   fataled on the missing trait, which is the same state that caused the deletion.

   Deletion now requires positive evidence: the index must look complete, AND the class must
   not exist on disk in an unscanned zone. The re-add scanner also learned two reference
   shapes it was blind to (trait uses, typed properties).


WHAT HAPPENS AUTOMATICALLY
--------------------------

- Duplicate #[Relationship] attributes COLLAPSE TO ONE on your next manifest build. No
  action, no cleanup, no migration script.
- If you added a workaround for defect 1 - typically ordering #[Auth(...)] ABOVE
  #[Relationship] so the walk only crossed argument-free attributes - you can remove it.
  Attribute order no longer matters. Leaving it in place is harmless.


THE ONE THING TO CHECK
----------------------

Import deletions that ALREADY happened are not undone by this release - the fixer has no
record of what it removed. If you ever saw a build fail with something like:

    Trait "Rsx\Models\Portal_Authorizable" not found

...then that import was stripped from your source and needs restoring by hand:

    git log --diff-filter=M -p -- rsx/models/            # find the removal
    git restore <the affected files>                     # or re-add the use statement

If your app builds cleanly today, you have nothing to restore. This cannot recur.


VERIFY
------

    php artisan rsx:manifest:build     # build twice
    git status                         # nothing under rsx/ should be modified by the build

A build that modifies your source is now only ever doing something it was asked to do
(namespace correction, adding a genuinely missing attribute). If a repeated build keeps
changing the same file, that is a bug worth reporting upstream.
