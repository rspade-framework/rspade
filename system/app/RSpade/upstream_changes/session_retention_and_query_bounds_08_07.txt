SESSION RETENTION POLICY + PLURAL RELATIONSHIP CAP + UNBOUNDED QUERY AUDIT
Date: 2026-08-07

SUMMARY
    Three framework-core changes that downstream applications must check their own
    code against:

      1. Session rows now EXPIRE on a per-type inactivity window (previously
         logged-in sessions were kept 365 days). If your app depended on the old
         window, override the new config.
      2. Concurrent WEB sessions per user are now CAPPED (default 25) and the
         oldest are signed out at every sign-in. Raise, lower or disable it.
      3. A lazy plural relationship (`await record.things()`) is now CAPPED and
         THROWS past the cap instead of returning every related record. If any of
         your relationships can exceed 500 records, that call now fails loud.
      4. Four framework record-set APIs now return an Rsx_Result_Set instead of an
         Eloquent Collection. foreach/count keep working; array functions do not.
      5. YOUR OWN models should now declare `public static $unbounded = true` where
         the table grows with customer activity. New convention, applies to app code.
      6. A new prelaunch checklist entry requires an unbounded-query audit of your
         own application code before launch.

    Everything else in this release self-applies: the migrations run, the cleanup
    task registers itself, and rsx:debug cleans up after itself with no wiring.

THE CHANGE

    Sessions
        Every session row (staff `_sessions` and `portal_sessions`) now carries a
        `type_id`, stamped by the writer at creation: Session::TYPE_WEB (a browser),
        Session::TYPE_PLAYWRIGHT (the rsx:debug harness), Session::TYPE_API
        (reserved; Bearer API requests are cookie-less and create no row). The type
        is NEVER inferred from the user-agent - the previous design did that, and it
        is both attacker-influenced and wrong about anything that does not announce
        itself.

        One hourly task (Session_Cleanup_Service::cleanup_sessions, #[Exclusive],
        chunked deletes) expires rows by INACTIVITY against their own type's window.
        The two tasks that existed before - a daily 365-day/14-day sweep and an
        hourly user-agent-matching sweep - are GONE, replaced by this one.

        This was motivated by a production incident. A `_sessions` table reached
        68,712 rows, 62,617 of them for a single login user, because every automated
        browser run minted a session and nothing expired machine sessions. A
        settings page that listed a user's sessions then loaded all 62,617 rows,
        exhausted a 128MB PHP process, and returned a blank 500 - while saturating
        the php-fpm pool and making unrelated endpoints flaky.

    Concurrent session cap
        rsx.sessions.max_web_sessions_per_user (default 25) bounds how many WEB
        sessions one user may hold. On every sign-in the user's web sessions beyond
        that count, ordered by last_active, are signed out - deactivated for staff,
        deleted for the portal (portal_sessions has no active flag). PLAYWRIGHT and
        API sessions are never counted or evicted. The hook is
        Session::set_login_user_id() / Portal_Session::set_portal_user_id(), so every
        sign-in path is covered with no per-caller wiring.

    Record-set APIs return Rsx_Result_Set
        These four now return an Rsx_Result_Set rather than an Eloquent Collection:

            $model->get_attachments($category)
            $model->get_deleted_attachments($category)
            File_Attachment_Model::get_deleted_files($fileable, $category)
            Api_Key_Model::get_for_user($user_id)

        An Rsx_Result_Set is a handle over the WHOLE set that you foreach like a list,
        but which fetches the rows one keyset page at a time. None of these had a
        ceiling - a bulk import can hang thousands of attachments off one record, and
        get_deleted_files() with no arguments is "every retained attachment on the
        install".

    Bounded result sets: Rsx_Result_Set, $unbounded, and a dev tripwire
        Three related pieces landed together, all in service of one rule: a function
        must return EVERY record it promised, AND must not fall over when that turns
        out to be 500,000 rows. Iterating satisfies both; truncating satisfies neither.

        - ->result_set() returns an Rsx_Result_Set: a handle you foreach like a list,
          which fetches the rows one keyset page at a time. count() is a SQL COUNT.
        - public static $unbounded = true declares a model whose row count grows with
          CUSTOMER ACTIVITY rather than with the codebase. A declaration, not a gate.
        - rsx.database.result_set_warn_threshold (default 1000) logs one warning in
          DEVELOPMENT when a get() actually returns more rows than that, naming the
          model and your call site. Never throws, never truncates, no production cost.

    Plural relationships
        Orm_Controller resolves a lazy plural relationship by calling the related
        model's gated fetch() once PER RECORD. That is correct for authorization
        and catastrophic for fan-out: an unbounded relation turns one
        `await record.things()` into one query per related row. It is now capped by
        `rsx.model_fetch.max_relationship_records` (default 500), and exceeding the
        cap THROWS - it does not return a truncated set, because a caller handed a
        silent partial set has no way to detect it.

THE FIX
    Informational only; downstream receives all of this automatically.

    - Migrations `add_type_to_sessions` / `add_type_to_portal_sessions` add the
      column, add the indexes the bounded reads need, and perform a ONE-TIME purge
      of session rows not used in 14 days (the historical bloat). The purge runs in
      bounded chunks; a table with months of accumulation will not lock.
    - `Session::purge_cli_sessions()` is called by rsx:debug as it exits.
    - New config sections `rsx.sessions` and `rsx.model_fetch`.
    - Six framework-internal unbounded queries were bounded (search text lookup,
      the reindex command's selectors, the thumbnail generator, two storage
      commands). No API changed.

ACTION REQUIRED

    1. Decide whether the default retention windows suit your application.

       Defaults (all are minutes of INACTIVITY, measured from last_active - an
       in-use session never expires):

           rsx.sessions.web_timeout_minutes        131400   3 months
           rsx.sessions.api_timeout_minutes         10080   7 days
           rsx.sessions.playwright_timeout_minutes    1440   1 day
           rsx.sessions.anonymous_timeout_minutes   20160   14 days
           rsx.sessions.portal_timeout_minutes      43200   30 days

       The change that may matter to you: an authenticated browser session used to
       survive 365 days of inactivity and now survives 3 months. If your users
       genuinely go a quarter without signing in and you do not want them logged
       out, override it in rsx/resource/config/rsx.php:

           'sessions' => [
               'web_timeout_minutes' => 525600,   // 1 year
           ],

       The `anonymous` rule is applied FIRST and wins where it overlaps: a session
       that never authenticated is deleted after 14 days whatever its type.

       Also confirm the `rsx:task:process` cron tick is installed. It always
       mattered; it now governs session-table growth outright.

    2. Decide whether 25 concurrent web sessions per user suits your application.

       On every sign-in, a user's web sessions past the cap are signed out oldest
       first. For most applications this is invisible - nobody legitimately holds 25
       live browser sessions. Two cases deserve a look:

         - A kiosk / shared-terminal deployment where many people sign in as the
           same account from many devices. Raise the cap, or disable it.
         - An application that treats a session as a durable per-device grant
           (background sync, a long-lived mobile webview). Those sessions now get
           signed out once a user's newer sessions push them past the cap.

       Override in rsx/resource/config/rsx.php:

           'sessions' => [
               'max_web_sessions_per_user' => 100,   // or 0 / null to disable
           ],

       Nothing needs changing if the default suits you - it applies automatically.

    3. Check how your code consumes those four record-set APIs.

       STILL WORKS, no change needed - this covers most call sites:

           foreach ($client->get_attachments('documents') as $doc) { ... }
           $count = $client->get_attachments('documents')->count();   // SQL COUNT now
           $set->first();  $set->map(...);  $set->filter(...);  $set->isEmpty();

       BREAKS - an Rsx_Result_Set is Traversable and Countable, but it is NOT an
       array and NOT an Eloquent Collection:

           $docs[0]                     // no [] indexing
           array_map(..., $docs)        // not an array
           $docs->toArray()             // no such method
           $docs->sortBy('created_at')  // Collection-only methods are not forwarded

       The fix is usually ->all() (materializes to a plain array - only when you are
       sure the set fits) or restructuring to a foreach.

       Find your call sites:

           grep -rn "get_attachments(\|get_deleted_attachments(\|get_deleted_files(\|get_for_user(" rsx/

       Note also: iteration walks by PRIMARY KEY, so any orderBy those methods used to
       apply no longer survives. get_deleted_attachments() and get_for_user() used to
       return newest-first; sort in the view if that ordering mattered to you.

    4. Declare $unbounded on your own models.

       This is a NEW CONVENTION for application code, and the only part of it a
       downstream developer has to do by hand. Framework models are already marked;
       yours are not.

       Add it next to $table on every model whose row count grows with CUSTOMER
       ACTIVITY rather than with your codebase:

           class Invoice_Model extends Rsx_Site_Model_Abstract
           {
               protected $table = 'invoices';
               public static $unbounded = true;   // one row per invoice, forever
           }

       MARK: logs, audit trails, event and message streams, notifications, queues,
       uploads, and anything written per-request / per-login / per-import / per-cron
       tick. Also the core business tables that scale with your customers - clients,
       contacts, projects, tasks.

       DO NOT MARK: human-authored low-volume tables (announcements, groups, roles),
       fixtures, join tables you always narrow to one parent, and 1:1 detail tables.
       The test is "could a reasonable query here return thousands?" Over-marking
       dilutes the signal until nobody reads it.

       The RSpade template app ships marked examples to copy the shape from -
       action_logs, notifications, contacts, tasks, shared_items and the portal
       request streams all carry it, each with a one-line reason.

       What it buys you: a deliberate decision recorded at the model, and a paper
       trail for the prelaunch audit in step 6. It is a DECLARATION, not a runtime
       gate - it changes no behavior, and a small well-narrowed query on a marked
       model is still perfectly fine. (DB-UNBOUNDED-01 lints framework code only;
       your code is covered by the tripwire and the audit.)

    5. Audit your plural relationships against the 500-record cap.

       Find every `#[Relationship]` method that is ALSO `#[Ajax_Endpoint_Model_Fetch]`
       and returns a hasMany / morphMany / belongsToMany:

           grep -rn "Ajax_Endpoint_Model_Fetch" -B4 rsx/models/ | grep "public function"

       For each, ask what the largest realistic related-record count is for ONE
       parent record. Anything that can plausibly pass 500 (a client's contacts, a
       project's tasks, an account's audit entries) must stop being a lazy accessor:

           BAD  - the JS calls await client.contacts() and gets 5,000 records
           GOOD - a #[Ajax_Endpoint] on the controller that paginates, filters,
                  or aggregates, called explicitly by the page that needs it

       Raising `rsx.model_fetch.max_relationship_records` is available and is the
       wrong answer in almost every case: the cost is one authorization round trip
       per record, so the ceiling exists to stop a fan-out, not to size a page.

       If a call does exceed the cap, you will see it immediately and loudly - the
       error names the relationship, the model, and the setting.

    6. Perform the unbounded-query audit on your own application code.

       `php artisan rsx:man prelaunch_checklist` has a new ENTRY 4: UNBOUNDED QUERY
       AUDIT. It defines the rule (every result set bounded BY DESIGN, not by how
       big the table happens to be), the acceptable shapes, and a manual walk. The
       incident above is the reason it exists, and application code has the
       identical failure mode. Run it before you launch.

       The short form:

           grep -rn -e '->get()' -e '::all()' -e '->pluck(' rsx/ | grep -v resource/

       For each hit, state the maximum row count and what enforces it. If the
       answer is "however many the table holds", it is a defect - however small
       the table is today. Then list the tables your app writes to per-request,
       per-login, per-import or per-cron-tick, and name the retention policy that
       deletes their old rows.

       The framework ships the tool for the fix: ->result_set() returns an
       Rsx_Result_Set (foreach it - whole set, one page resident). And in
       development, rsx.database.result_set_warn_threshold (default 1000) logs one
       [DB-UNBOUNDED] warning whenever a get() actually returns more rows than that,
       naming the call site. Skim your dev log for those lines - each one is a real
       query that really did return too much. It never throws and never truncates.

VERIFICATION

    Sessions:
        php artisan migrate                       # applies both migrations
        php artisan rsx:task:run Session_Cleanup_Service cleanup_sessions

        The task reports per-rule deletion counts. Then confirm your session table
        is no longer growing without bound:

            SELECT type_id, COUNT(*) FROM _sessions GROUP BY type_id;

        Run `php artisan rsx:debug /` a few times and re-run that query - the
        playwright count should return to zero.

    Record-set APIs:
        Load every screen that lists attachments or API keys and confirm it still
        renders. A PHP error mentioning "Call to undefined method" or array access on
        an object is a call site from step 3 that needs converting.

    Concurrent session cap:
        Sign in as the same user from more browsers than the cap and confirm the
        oldest are signed out:

            SELECT id, active, last_active FROM _sessions
             WHERE login_user_id = <id> AND type_id = 1 ORDER BY last_active DESC;

    Relationship cap:
        Load the heaviest page in your app that uses a lazy plural relationship and
        confirm it still renders. A page that now errors is telling you about a
        fan-out that was previously silent.

    Unbounded query audit:
        php artisan rsx:man prelaunch_checklist    # read ENTRY 4, perform the walk
