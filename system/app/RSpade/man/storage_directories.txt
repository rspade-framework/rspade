NAME
    storage_directories - RSX framework storage directory organization

SYNOPSIS
    What lives under storage/ (the PROJECT-ROOT storage tree), which entries ship
    in a deployment, and what the maintenance commands (rsx:clean,
    rsx:prod:export) touch.

DESCRIPTION
    Volatile storage lives at <project>/storage - one level ABOVE the Laravel base
    path (system/). It was relocated out of system/ because that tree is the
    framework-owned zone: hard-synced by rsx:framework:pull and committed wholesale
    by it, which runtime data has no business being part of. The move is performed
    once per environment by bin/environment_updates/030_relocate_storage.sh, which
    drops the marker storage/.rspade_storage_relocated; the bootstrap bridge
    (system/bootstrap/app.php) reads that marker and calls useStoragePath(), so
    every storage_path() consumer follows automatically. Pre-boot code (artisan,
    public/index.php, the updater, the node helpers) reads the same marker
    directly, falling back to the historic system/storage until it exists.

    NEVER join a storage path onto base_path(): base_path() is system/. Use
    storage_path(), or rsx_project_file_path() for a project-logical
    'storage/...' path (manifest keys keep that historic spelling).

    The directory groups into three roles:

        PERSISTENT BUILD  artifacts a prod boot needs (rsx-build).
        RUNTIME STATE     data the running app owns - uploads, logs, update
                          markers, caches, locks.
        REGENERABLE CACHE content-addressed caches rebuilt on demand.

    Nothing here is web-accessible: the web-server docroot points at
    system/public ONLY, and everything below is reached through framework code
    (file paths for the file subsystem resolve exclusively through
    App\RSpade\Core\Files\Rsx_File_Paths - never a hardcoded storage_path()).

LIVE TREE (<project>/storage/)
    rsx-build/        persistent build artifacts (see below).                [SHIP]
    rsx-tmp/          temporary caches, cleared by rsx:clean.               [omit]
    rsx-locks/        vestigial scaffold dir; nothing writes to it.        [omit]
    rsx-framework/    framework self-update markers + the maintenance flag
                      (its content is the operator reason).                 [omit]
    flock/            advisory lock FILES: every system lock, plus cluster
                      locks while maintenance mode is up. Inert when idle.  [omit]
    rsx-thumbnails/   generated WebP thumbnails (content-addressed).        [omit]
    rsx-renditions/   cached soffice->PDF renditions (content-addressed).   [omit]
    rsx-ide-bridge/   IDE bridge local-file grant token + passive guards.   [omit]
    storage/          Laravel local disk; storage/storage/files/ is the
                      content-addressed file-attachment BLOB STORE.         [omit]
    framework/        Laravel cache/, sessions/, testing/, views/.          [omit]
    app/              Laravel "public"/"temp" local disk roots.             [omit]
    logs/             laravel.log*, ide-formatter.log, ssr-fpc-errors.log.  [omit]
    db_backups/       mysqldump cache for rsx:test --fresh, keyed by a hash
                      of all migrations (survives rsx:clean).               [omit]

    [SHIP]/[omit] is the deployment posture (see DEPLOYMENT). "omit" entries are
    either runtime state that must not be copied from a dev box (blob store,
    logs, ide-bridge, db_backups) or regenerable caches recreated on demand.

RSX-BUILD DIRECTORY
    Purpose: persistent build artifacts that survive cache clears and ship to
    production.

    Location: storage/rsx-build/

    Contents:
        build_key            content-derived manifest hash (the cache key)
        manifest_data.php    compiled manifest cache
        bundles/             compiled CSS/JS bundles
        js-stubs/            generated JS stubs for the Internal (Ajax) API
        js-model-stubs/      generated JS model classes (fetch/enum/relationships)
        prod_seal.json       sealed-build record (prod/debug modes only)
        cdn-cache/           only present when a build cached CDN assets here;
                             the live dev cache lives at rsx/resource/.cdn-cache/

    There is NO routes.php / route_metadata.php here. Laravel's route cache (prod
    only, via optimize:cache) is bootstrap/cache/routes-v7.php, outside storage.

    Immutability under a sealed build (prod modes):
        When the system is in a prod mode (debug or production) AND a
        prod_seal.json is present, this directory is a SEALED, IMMUTABLE build
        artifact. The framework refuses to mutate it from any unauthorized
        context:

        - rsx:clean REFUSES while sealed (it will not wipe the deployment's only
          copy of the assets); it tells you to run rsx:prod:refresh or
          rsx:prod:disable first.
        - The low-level write choke points (file_put_contents_safe,
          rmdir_recursive, browser-storage clear) throw if a write targets this
          directory from an unauthorized context.
        - The ONLY way to rewrite the assets is an authorized rebuild -
          rsx:prod:refresh (in place) or a fresh rsx:prod:enable.

        prod_seal.json pins the build: build_key, mode, git commit, and a sha256
        of every asset. rsx:prod:verify recomputes those hashes to detect drift.
        See app_mode(3) for the full lifecycle.

RSX-TMP DIRECTORY
    Purpose: temporary files and caches, cleared by rsx:clean.

    Location: storage/rsx-tmp/

    Contents:
        cache/
            code-quality/    code-quality analysis cache
            js-sanitized/    sanitized JS file cache
            js-lint-passed/  JS lint-pass memo
            php-lint-passed/ PHP lint-pass memo
        persistent/          caches that survive between builds
                             js_parser/       parsed-AST cache, keyed by file hash
                             php_reflection/  reflection cache
        jqhtml-cache/        compiled jqhtml template cache
        babel_cache/         babel transform cache
        npm-cache/           npm module resolution cache
        npm-compile/         npm compile scratch
        (babel_*.js, jqhtml_*.js, bundle_*.js scratch files written by the
         transform and compile helpers)
        test-storage/        test-run file subsystem (blob store + thumbnail and
                             rendition caches) redirected here by rsx:test so a
                             test-DB attachment delete never unlinks a blob shared
                             with the developer database (rsx.files.storage_root,
                             read by Rsx_File_Paths; backlog B-38)

        THE HELPER DAEMON SOCKETS. Seven node RPC helpers live directly in this
        directory, each on a unix socket plus a .meta provenance sidecar:

            js-parser-server.sock          + .meta
            js-transformer-server.sock     + .meta
            minify-server.sock             + .meta
            jqhtml-compile-server.sock     + .meta
            js-sanitizer-server.sock       + .meta
            js-code-quality-server.sock    + .meta
            ssr-server.sock                + ssr-server.pid, ssr-server.build_key

        <socket>.meta holds the sha1 of the server script the daemon was spawned
        from. A client reuses a daemon only when the socket exists, that hash
        still matches the script on disk, and a ping is answered - so an edited
        or freshly-pulled server script invalidates its daemon at source. See
        Core/JsParsers/CLAUDE.md (Rpc_Client_Abstract).

        (transient .tmp_<digits> staging dirs from atomic writes)

    Cleared by rsx:clean; recreated automatically. Safe to exclude from deploys.

    THE DAEMONS ARE QUIESCED FIRST. rsx:clean calls
    Rpc_Client_Abstract::quiesce_all() immediately BEFORE wiping this directory,
    and reports the count. Wiping it under a running daemon would strand that
    daemon permanently: it keeps a listener on an unlinked inode that no socket
    message can ever reach again, and its argv still names the deleted path. So a
    clean does NOT leave live daemons behind - it kills them, and the next process
    that needs one spawns it on demand. bin/maintenance-mode.sh enable runs the
    same sweep in bash for the same reason (a framework update rewrites the server
    scripts underneath them). See bin/CLAUDE.md for the normative rule.

RSX-LOCKS DIRECTORY
    Purpose: a vestigial scaffold directory, kept for historical layout only.

    Location: storage/rsx-locks/

    NOTHING WRITES HERE. Web-cluster locks are held by a live socket to the
    rsx-lockd daemon and touch no disk at all; system locks (and cluster locks
    degraded by maintenance mode) are flock() files under storage/flock/. See
    rsx:man locks. This directory contains only a .placeholder and is never
    cleared by rsx:clean.

RSX-FRAMEWORK DIRECTORY
    Purpose: DURABLE framework self-update state (mutation markers + the
    maintenance flag). Not storage/framework/ - that is Laravel's own
    cache/session/view tree, which is routinely wiped wholesale.

    Location: storage/rsx-framework/

    Contents:
        mutations.json    index of framework-authored file mutations (Php_Fixer
                          use-rewrites, .php.upstream renames, composer classmap
                          regen, model_codegen regen)
        shadow/           byte-exact copies of each mutated file's framework-
                          authored content (the "expected state" the tamper check
                          diffs against)
        .maintenance.mode.framework.update
                          present only while rsx:framework:pull holds the update
                          window (web + CLI return 503)

    Never cleared by rsx:clean (the markers must survive rebuild cycles; losing
    them would make legitimate framework churn look like user tampering to
    rsx:framework:verify). Gitignored; recreated as mutations occur; reset by a
    successful rsx:framework:pull. See rsx:man rsx_upstream.

    NOT here: the cached bare clone of the rspade_system distribution repo. It is
    pure re-derivable data and lives at /tmp/rspade_upstream.git (single source of
    truth: Framework_Maintenance::upstream_cache_dir()), so a ~100MB git clone
    never enters a storage backup or export. Losing it costs one re-clone.

FILE-SUBSYSTEM & FEATURE CACHES
    The file attachment subsystem and its caches are content-addressed (keyed on
    the deduplicated blob hash) and resolved through Rsx_File_Paths:

    storage/storage/files/  the BLOB STORE - every uploaded file's deduplicated
                            bytes (Rsx_File_Paths::blob_root()). Real user data;
                            never ships in a deployment.
    rsx-thumbnails/         generated WebP thumbnails (rsx:man thumbnails), LRU-
                            swept.
    rsx-renditions/         cached soffice->PDF renditions served by
                            /_preview/pdf/:key for <Document_Preview>
                            (rsx:man document_search); {blob-hash}.pdf, LRU-swept
                            to config('rsx.preview.quota_max_bytes').

    Thumbnails and renditions are regenerable on demand (safe to omit from a
    deploy; rebuilt on first request). The blob store is NOT regenerable and is
    dev-local data - it must never be copied into a deployment package.

DEPLOYMENT
    The one deployment tool is rsx:prod:export. It is a strict WHITELIST: it ships
    source code + the sealed build artifacts + an env template, and NOTHING else.

    Ships:
        - system/ (code, vendor, node_modules) minus storage, tests, docs.dev,
          docs.goals, ace_reference, bin/publish, DebugProxy, *.expect
        - storage/ - ONLY the sealed build artifacts (rsx-build build_key,
          manifest_data.php, prod_seal.json, bundles/, js-stubs/, js-model-stubs/,
          cdn-cache/) plus an empty, writable storage skeleton
        - rsx/ (application) minus tests and resource/research|archive|incomplete
        - artisan + root composer/package manifests; root vendor/node_modules only
          if a real app-layer install exists
        - a scrubbed .env.dist and a system/.env -> ../.env symlink

    NEVER shipped (excluded by the whitelist, automatically): the blob store
    (storage/storage/), thumbnails, renditions, rsx-ide-bridge (dev grant token),
    rsx-framework, db_backups, logs, rsx-tmp, and the real .env. A whitelist means a
    newly-added runtime directory is left out by default instead of leaking.

    The operator points the web-server docroot at system/public ONLY and populates
    .env from .env.dist on the target.

MAINTENANCE
    rsx:clean [--silent]  clears storage/rsx-tmp/ and storage/rsx-build/, and ALSO:
        - FLUSHES the entire Redis database (Redis backs the cache, realtime
          pub/sub, and task worker slots - expect all of it to be dropped;
          locks are NOT in Redis and are unaffected)
        - removes orphaned .tmp_<digits> atomic-write staging dirs under the tree
        - heals the system/.env -> ../.env symlink first
        - PRESERVES rsx-locks/ and rsx-framework/
        - in a DOWNSTREAM app (not this monorepo) also resets the vendored
          framework tree: git reset + checkout of system/ back to its last
          commit (untracked files untouched). Skipped while a framework update
          is in flight, which would otherwise revert the update itself.
        - REFUSES when a sealed prod build is active (prod_seal.json + prod mode):
          run rsx:prod:refresh or rsx:prod:disable first. This is what makes
          rsx-build safe to include in a deployment - a stray rsx:clean cannot
          wipe a sealed deployment.

    rsx:manifest:build    rebuild storage/rsx-build/manifest_data.php.
    rsx:bundle:compile <name>  rebuild one bundle under rsx-build/bundles/.

    NOTE: never restart the web server to "clear locks". A web-cluster lock is
    held by a live connection to rsx-lockd and is released the instant its holder
    exits - `node system/bin/rsx-lockd/lockd.js dump` shows exactly who holds
    what, and force_clear is the deliberate override. This environment also runs
    with OPcache disabled, so restarts are unnecessary in general.
