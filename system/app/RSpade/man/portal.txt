PORTAL(3)                      RSX Framework Manual                      PORTAL(3)

NAME
    portal - client portal, a second authenticated experience for external users

SYNOPSIS
    // Application portal middleware (/rsx/portal_main.php)
    use App\RSpade\Core\Portal\Portal_Main_Abstract;
    use App\RSpade\Core\Portal\Portal_Session;

    class Portal_Main extends Portal_Main_Abstract {
        public static function init(): void {
            // declare which site this portal serves (the framework never guesses)
            Portal_Session::set_site_id((int) config('rsx.portal.site_id'));
            Portal_Session::init();
        }
        public static function pre_dispatch(Request $request, array $params) {
            // gate everything except public routes
            return null;
        }
        public static function unhandled_route(Request $request, array $params) {
            return null; // default 404
        }
    }

    // A portal PHP route (login, register, password reset, ...)
    #[Portal_Route('/login', methods: ['GET', 'POST'])]
    public static function index(Request $request, array $params = []) { ... }

    // A portal SPA action (authenticated single-page screens)
    @route('/dashboard')
    @layout('Portal_Layout')
    @portal_spa('Portal_Spa_Controller::index')
    class Portal_Dashboard_Action extends Spa_Action { }

DESCRIPTION
    The portal is a complete, separate authenticated experience that runs
    PARALLEL to the main application. It has its own session, its own dispatch,
    its own routing table, and its own user identity - none of which touch the
    staff-facing Session/Dispatcher. Use it for customers, clients, vendors, or
    any external audience that must log in but must never see the internal app.

    The portal is served either from a dedicated domain (production) or from a
    URL prefix (development); see URL DETECTION. A request is routed to the
    portal stack when Portal_Dispatcher::is_portal_request() matches.

    Framework vs application:
      Framework (App\RSpade\Core\Portal\, App\RSpade\Core\Models\)
        - Portal_Session       session, CSRF, login/logout, device sessions
        - Portal_Dispatcher    request -> portal route resolution and dispatch
        - Rsx_Portal (PHP+JS)  context detection and type-safe URL generation
        - Portal_Main_Abstract portal-wide middleware hook contract
        - Portal_User_Model    the portal identity (overridable core model)
        - #[Portal_Route] / @portal_spa manifest support
      Application (/rsx/portal/, /rsx/models/)
        - Portal_Main          the concrete middleware (auth gating)
        - Portal_Spa_Controller, layout, auth controllers, screens
        - app-specific models (memberships, invitations, projects, ...)

URL DETECTION
    Controlled by config('rsx.portal.domain') and config('rsx.portal.prefix'):
      - domain set    -> portal is every request whose host is that domain.
      - domain null   -> portal is every request whose path starts with prefix
                         (default '/_portal'); the prefix is stripped before
                         routes are matched.
    Rsx_Portal::is_portal_request() / Rsx_Portal.is_portal() report context;
    Rsx_Portal::get_normalized_path() returns the path with the prefix removed.

INTERNAL ENDPOINTS (AJAX, BATCH, UPLOAD)
    The framework internal endpoints are served on BOTH channels by the SAME
    handlers - each carries a #[Route] and a #[Portal_Route]:

        /_ajax/:controller/:action    Ajax_Endpoint_Controller::dispatch
        /_ajax/_batch                 Ajax_Batch_Controller::batch
        /_upload                      File_Attachment_Controller::upload

    A portal page calls them under the portal's own base - /_portal/_ajax/...
    in prefix mode, /_ajax/... on the portal domain (the host already selects
    Portal_Dispatcher). The client derives that automatically:

        Rsx_Portal.internal_url('/_ajax/Foo/bar')
          staff page               -> /_ajax/Foo/bar
          portal page, prefix mode -> /_portal/_ajax/Foo/bar
          portal page, domain mode -> /_ajax/Foo/bar

    Ajax.call() (and therefore every generated controller stub) and
    Ajax.upload() already go through it; application code that builds an
    internal URL by hand must too. Uploads use Ajax.upload(form_data), which
    owns both the channel and the CSRF header (multipart cannot ride the $.ajax
    chokepoint that normally attaches it).

    WHY IT MATTERS: on the portal channel the request IS a portal request, so
    CSRF verifies against the portal session, the #[Auth] gates evaluate in the
    portal realm, and Orm_Controller resolves portal_fetch(). Calling the bare
    staff path from a portal page gets the staff realm for all three. The Ajax
    and ORM seams additionally REFUSE a cross-realm call outright - see
    rsx:man auth_gates (PORTAL).

ROUTES
    PHP routes - #[Portal_Route]
        #[Portal_Route('/path', methods: ['GET','POST'], name: 'optional')]
        public static function handler(Request $request, array $params = [])
      Public static methods only. Pattern may contain :params. methods default
      to ['GET']. Registered into the manifest's portal route table, kept
      entirely separate from the main #[Route] table. Use these for
      server-rendered portal pages (login, register, password reset, logout).
      As with main routes, $params carries the GET query string AND the URL
      :params (URL params win on a name clash); read query values from $params
      (e.g. $params['code']), not $request->query() (which a code-quality rule
      forbids in controllers). POST data is not in $params - use $request.

    SPA actions - @portal_spa
        @route('/path')                  // one or more
        @layout('Portal_Layout')         // nested layouts allowed
        @portal_spa('Portal_Spa_Controller::index')
        class Name_Action extends Spa_Action { }
      The portal counterpart of @spa. Routes are GET, served through the single
      Portal_Spa_Controller bootstrap, and navigate client-side. Use these for
      the authenticated portal screens.

PORTAL MAIN HOOKS
    An application MUST provide one Portal_Main extending Portal_Main_Abstract
    (in /rsx/portal_main.php). Called by Portal_Dispatcher:
      init()                       once per process, at the top of the first
                                   portal request - the FIRST application code to
                                   run in the portal stack. Declare the portal's
                                   site here (Portal_Session::set_site_id, see
                                   PORTAL SESSIONS) and init the session.
      pre_dispatch($req, $params)  before every route, AFTER the #[Auth] gates
                                   have already run; return null to continue, or
                                   a Response to halt. NOT for authorization -
                                   gates own that (see AUTHORIZATION).
      unhandled_route($req,$params) when no portal route matches; return null
                                   for the default 404, or a Response
    Order: Portal_Main::init -> dev auth -> CSRF -> route match -> #[Auth] gates ->
    Portal_Main::pre_dispatch -> controller pre_dispatch (if any) -> handler.
    init() runs before every one of those, which is why it is where the site is
    declared: each of them may ask for it.

SESSION & AUTH
    use App\RSpade\Core\Portal\Portal_Session;

    Portal_Session is the portal's Session. It is site-scoped and is a FACADE
    over the PORTAL PROPERTIES of the one session the browser has - not a second
    session. Never read or write the staff properties from portal code, and never
    the portal properties from main-app code.

    That rule is for APPLICATION code. The framework surfaces that serve BOTH
    experiences resolve the experience themselves from
    Rsx_Portal::is_portal_request() and reach the right properties without being
    told - and @csrf and Flash_Alert simply use the browser's one session. So
    portal code writes them exactly like staff code:

      Flash_Alert::success('Welcome to the Client Portal!');   // this session
      @csrf                                                    // this session's token

    Do not hand-roll a portal variant of either: a portal-specific CSRF input or
    flash mechanism reintroduces the coupling these surfaces exist to hide.

    Storage: the portal identity lives in portal-shaped COLUMNS on the browser's
    _sessions row - portal_user_id, portal_site_id, impersonator_user_id,
    handoff_* (see rsx:man session). Portal_Session is a static FACADE over those
    properties, not a model - there is no Portal_Session::where(), no instances,
    and no portal table. The facade's public surface below is the whole API; use
    it rather than querying sessions yourself. A portal session ENDS by CLEARING
    the portal properties - logout(), terminate_session(), terminate_all_*(),
    the sign-in cap and stop_impersonation() all clear; NONE of them deletes or
    deactivates the row, because that row is the browser's session and may carry
    a staff login.

      init(): void                       load session from cookie (no create)
      is_logged_in(): bool               authenticated portal user present
      has_session(): bool                a session exists (does not create)
      get_user() / get_portal_user()     -> Portal_User_Model|null
      get_portal_user_id(): ?int         current portal user id
      set_site_id(int $site_id): void    declare which site this portal request
                                         serves (see PORTAL SESSIONS)
      get_site_id(): int / get_site()    the declared/session site; THROWS when
                                         nothing declared one
      set_portal_user_id(?int $id): void log in / log out (a login uses the
                                         declared site; no site argument exists)
      logout(): void                     clear the identity on the session
      get_session_id(): int              the browser's session id (SHARED with
                                         Session; creates one if needed)
      get_csrf_token(): ?string          the browser's ONE csrf token (SHARED)
      verify_csrf_token(string): bool    constant-time compare
      find_by_token(string): ?Session    resolves only rows that CARRY a portal
                                         identity

    Device session management (for a "your sessions" screen):
      get_sessions_for_user(?int $id = null): array
                                         ALL live sessions carrying this portal
                                         identity, most recent first. Excludes
                                         the "View as Client" handoff rows, which
                                         are transport, not devices. Capped per
                                         user at sign-in by
                                         rsx.sessions.max_web_sessions_per_user
                                         (default 25); see rsx:man session
      terminate_session(int $id): bool   OWN sessions only (fail-closed; false
                                         otherwise). CLEARS the portal properties
                                         on that row; the row survives
      terminate_all_other_sessions(): int
      terminate_all_sessions_for_user(int $id, ?int $except = null): int

    Auth pattern: DECLARATIVE. Every portal surface carries an #[Auth(...)] /
    @auth(...) gate naming portal-realm checks, and Portal_Dispatcher evaluates
    it before any application code:

      #[Portal_Route('/dashboard')]
      #[Auth('is_logged_in')]           // #[Auth('public')] for a public page
      public static function index(...) { ... }

    A surface with no gate does not deploy - the manifest build fails by name.
    Portal_Main::pre_dispatch performs NO authorization; it remains for non-auth
    middleware work (tenant setup, redirects, the login-redirect capture).
    See AUTHORIZATION below and rsx:man auth_gates.

PORTAL SESSIONS
    Cookie and storage
      There is ONE session per browser: one 'rsx' cookie, one _sessions row, one
      csrf_token, shared by the staff app and the portal. The portal identity is a
      set of PROPERTIES on that row - portal_user_id, portal_site_id,
      impersonator_user_id, handoff_* - alongside the staff properties
      (login_user_id, site_id, impersonator_login_user_id). A browser signed into
      both carries both, on one row, and that is normal.

      site_id is STAFF-only; the portal's tenant is portal_site_id, because one
      browser can legitimately be on a different tenant in each experience.

      A dedicated portal domain needs no machinery: per-origin cookie jars mean
      that browser holds its own row on that origin, with the staff properties
      null. There is no portal session table and no portal session model:
      Portal_Session is a static facade over the portal properties. See rsx:man
      session for the table itself.

    Lifecycle
      init()          reads the cookie and resumes the row; creates nothing. The
                      session token string is minted once, at creation, and never
                      rotates - a login is a record UPDATE, not a new session (see
                      rsx:man session SECURITY).
      activation      THE ONE activation path. The first call that NEEDS a row
                      (get_session_id(), get_session(), a login) mints the
                      browser's session exactly as a staff page view would - same
                      cookie, same token machinery, a type_id (TYPE_WEB, or
                      TYPE_PLAYWRIGHT under the rsx:debug harness). No site is
                      needed to CREATE a row; the declared site (below) is
                      stamped onto portal_site_id when it is known.
      logout()        CLEARS the portal properties. The row survives - it is the
                      browser's session and may carry a staff login - and the
                      cookie is untouched.
      end             every portal "end" is a property clear: logout(), reset(),
                      terminate_session(), terminate_all_*(), the sign-in cap,
                      stop_impersonation(). None deletes or deactivates a row.
      retention       idle rows are swept by the session cleanup: a row carrying
                      ANY identity (portal_user_id counts) gets the 3-month web
                      window, one carrying none gets the 30-day anonymous window.
                      Each sign-in also clears the portal properties off the
                      user's oldest sessions beyond
                      rsx.sessions.max_web_sessions_per_user.

    THE SITE CONTRACT
      A portal session is site-scoped: every row carries a site_id, and every
      portal query is narrowed by it. RSPADE DOES NOT RESOLVE THAT SITE. There is
      no detection, no config default, and deliberately no resolve hook or event -
      which tenant a portal request serves is an application fact (one site; a
      host -> site table; a subdomain; an invite code; a chosen workspace), and
      every scheme the framework could guess would be wrong for some app.

      So the application DECLARES it:

        Portal_Session::set_site_id(int $site_id): void

      Rules:
        - Declare it EARLY - before anything asks. Portal_Main::init() is the
          place: it is the first application code in a portal request, ahead of
          dev auth, CSRF, the #[Auth] gates, Flash_Alert, the rsxapp payload and
          every controller. A flow that can only know the site at login (an invite
          code, a workspace picker) declares it there instead.
        - It DECLARES, it does not create: no row, no cookie, no write to an
          existing session.
        - Idempotent for the same id; a DIFFERENT id THROWS. A portal has no site
          switcher, so two answers in one request means two subsystems disagree
          about the tenant.
        - A live session's site wins and cannot be contradicted: declaring a site
          other than the one the browser's session carries THROWS.
        - A non-positive id THROWS. If the site cannot be resolved, do not call
          this - let the failure below happen.

      get_site_id() then resolves: the live session's site, else the declaration.
      Nothing else. WITH NEITHER IT THROWS, naming this page. That failure is the
      contract working: a portal that does not know its tenant must not quietly
      pick one (silently defaulting to site 1 is how a multi-tenant app leaks).
      get_site(), a login, and every framework surface that needs a portal site
      (Flash_Alert's queueing, the realtime connection token, upload site
      stamping, the audit-stamp actor) resolve through it.

      Mono-site (the template app, rsx/portal_main.php):

        public static function init()
        {
            Portal_Session::set_site_id((int) config('rsx.portal.site_id'));
            Portal_Session::init();
        }

      The key is the APPLICATION's own (rsx/resource/config/rsx.php) - the
      framework config has no portal site key to inherit.

      Multi-tenant (host lookup), same call, different source:

        $site = Site_Model::where('portal_domain', Rsx::get_hostname())->first();
        if (!$site) { /* pre_dispatch returns a 404/landing response */ }
        Portal_Session::set_site_id((int) $site->id);

    CLI
      Rsx_Portal::is_portal_request() is false in CLI, so nothing is ever in
      portal context there. The portal facade holds no CLI state of its own beyond
      the declaration and cli_set_portal_user_id(); get_session_id() delegates to
      Session, which mints the process's own TYPE_CLI row on demand (rsx:man
      session, CLI MODE). set_site_id() still works - it
      is the same declaration minus a request, and it is how tests and
      portal-aware commands seed a site (there is no cli_set_site_id()). Having no
      request boundary to protect, the CLI declaration may be re-declared;
      Portal_Session::reset() clears it (plus cli_set_portal_user_id()) and is the
      clean-slate call between tests.

EXPERIENCE FORKS (which properties answer)
    Framework surfaces that serve BOTH experiences resolve the experience
    themselves - /_upload derives its site and its gate 'user' from it, and the
    realtime connection token picks its identity and site the same way. @csrf has
    nothing left to fork on: one browser has one session and one csrf_token, so it
    simply uses it. Flash_Alert has one session too, but STAMPS the experience on
    each alert (_flash_alerts.is_portal) so a portal page's message is not
    delivered to a staff tab on the same session. Portal code calls all of them
    exactly like staff code and must never hand-roll a portal variant.

    WHICH SITE IS THIS? (the tenant seams)
      Every framework seam that resolves a site forks the same way. The one that
      matters most is Rsx_Site_Model_Abstract::get_current_site_id() - the tenant
      boundary for EVERY site-scoped model, portal models included: it feeds the
      site global scope, the forced site_id on create, the cross-site save/retrieve
      fatals, and the site write lock. On a portal request it answers with the site
      the application DECLARED (Portal_Session::set_site_id), and THROWS when the
      application declared none - scoping to 0, or to whatever tenant a co-resident
      staff cookie happens to be on, is a cross-tenant primitive that reports
      success.

      The same fork, for the same reason, in: Rsx_Mail (queue row + unsubscribe
      lookup), Rsx_Sms (ditto), Rsx_Time (the site-timezone tier - a portal account
      has no personal zone, so the site IS the answer there), Rsx_Settings
      (site-scoped values), Rsx_Throttle (the rate-limit bucket).

      Consequence for an app: portal code does NOT hand-scope its queries, and must
      not "help" by setting the staff site on a portal request. Declare the portal
      site in Portal_Main::init() and let the seams read it. A staff site
      declaration in Main::init() is the STAFF app's own tenancy (and the CLI
      default) - nothing portal rides on it.

    When your own code DOES have to fork, fork on the EXPERIENCE OF THE REQUEST:

        if (Rsx_Portal::is_portal_request()) { ... Portal_Session:: ... }
        else                                 { ... Session::        ... }

    NEVER on identity:

        if (Portal_Session::is_logged_in())   <-- WRONG as an experience test
        if (Session::is_logged_in())          <-- WRONG as an experience test

    Identity is not experience, and one browser routinely carries BOTH identities
    on its single session - so an identity test gets both directions wrong:

      - An ANONYMOUS portal caller falls into the staff branch. That covers a
        public portal page, an invite/register flow, and a portal tab that logged
        out but still holds its session. The branch then reports the STAFF user,
        the STAFF tenant and staff-shaped authorization on a portal page - which is
        a data-exposure shape, not a cosmetic one.

      - A STAFF caller whose browser is also signed into the portal falls into the
        portal branch, and gets the portal tenant and portal authorization on a
        staff page.

    A staff-OR-portal disjunction is a different thing and is fine where it is
    genuinely meant - "is anybody signed in" is a real question, and the template's
    file-upload gate handler asks exactly that. What is never acceptable is using
    an identity test to decide WHICH PROPERTIES to read next.

    Prefix mode masks these bugs from developers, because a developer's own browser
    is usually signed into the staff app on the same host - so a portal path that
    silently borrows the staff identity appears to work. Test the portal with NO
    staff login present (a private window, or clear the `rsx` cookie), and perform
    at least one REAL form login: rsx:debug --portal installs the session directly
    and never runs your login controller, so it cannot reproduce anything that
    happens during login. Pre-launch audit: rsx:man prelaunch_checklist ENTRY 5.


PORTAL LOGIN FLOW
    The framework provides the SESSION, not the login SCREEN. There is no portal
    login controller, no portal login form, and no portal registration flow in
    /system/ - those are application surfaces, because their copy, branding,
    fields and onboarding rules are the app's. The template app ships a complete
    worked set in /rsx/portal/auth/ - read it as the reference implementation:

      Portal_Login_Controller           /login    email + password
      Portal_Logout_Controller          /logout
      Portal_Register_Controller        /register invitation-code signup
      Portal_Password_Reset_Controller  /password/reset  request + token
      Portal_Request_Access_Controller  /request-access  invite lookup
      Portal_Impersonate_Controller     staff "view as client" claim/stop

    What the framework gives you:
      #[Portal_Route(..., methods:['GET','POST'])]  the route (GET renders, POST
                                                    handles - one method, like
                                                    the staff login)
      #[Auth('public')]                             the gate every login-flow
                                                    surface carries
      Portal_User_Model::find_by_email($site,$mail) / check_password() /
      can_login() / touch_last_login()              the identity primitives
      Portal_Session::set_portal_user_id($id)       THE login: activates the
                                                    browser's session and stamps
                                                    the portal identity + the
                                                    declared tenant onto it
      Portal_Session::logout()                      clears the portal properties
                                                    (the row survives, along with
                                                    any staff login on it)
      Login_Redirect::capture/params/hidden_input/consume
                                                    intended-URL threading
                                                    (rsx:man login_redirect)
      Flash_Alert / @csrf                           use the browser's one
                                                    session; write them exactly
                                                    like staff code

    The shape of a login handler:

      1. Already logged in?  -> redirect away.
      2. Resolve the site.   -> normally already declared (Portal_Main::init);
                                get_site_id() just reads it. A flow that resolves
                                the site ITSELF (see below) calls set_site_id()
                                here, before touching the session.
      3. Look the account up WITHIN that site: a portal account is a
         (site_id, email) pair - find_by_email($site_id, $email), never a global
         email lookup.
      4. Verify: check_password() AND can_login() (active + verified).
      5. Portal_Session::set_portal_user_id($portal_user->id) - no site argument;
         the session is created for the declared site.
      6. Flash + redirect to the post-auth destination.

    WHERE THE SITE DECLARATION GOES - three patterns:
      Mono-site            Portal_Main::init() reads the app's own config key.
                           The login flow never thinks about the site.
      Domain / subdomain   Portal_Main::init() looks the site up from the request
                           host and declares it; an unknown host is the app's own
                           404/landing response from pre_dispatch.
      Invite / workspace   the site is only knowable from the credential being
                           presented (an invitation code, a tenant-qualified
                           account). Declare it in the login/register handler, on
                           the branch that resolved it, BEFORE the first session
                           call. Everything after that behaves identically.

    Invariants to keep whatever the scheme:
      - A credential is scoped to a site. Never authenticate on a global email
        lookup and then adopt the found row's site - that is a cross-tenant login.
      - An invitation/reset token is scoped to a site too. The template register
        controller rejects a code whose site_id is not the served site.
      - Never call Session:: (the staff facade) in portal code. Portal login is
        Portal_Session, end to end.

PORTAL USER MODEL
    App\RSpade\Core\Models\Portal_User_Model is the portal identity - the portal
    analogue of Login_User_Model. It is a framework-core model so the portal
    subsystem never depends on a class defined in the application. Table:
    portal_users (site-scoped). Surface:
      const STATUS_ACTIVE / STATUS_INACTIVE / STATUS_SUSPENDED
      can_login(): bool                  active and verified
      check_password(string): bool
      set_password(string): void         hashes; does not save
      touch_last_login(): void
      get_metadata(key,$default) / set_metadata(key,$value)
      static find_by_email(int $site_id, string $email): ?self
      portal_can_read(): bool            record-level rule; own record only
      static portal_fetch($id)           Ajax model fetch (via Portal_Authorizable)

    Portal_User_Model exposes portal_fetch() (not fetch()) - it is read by portal
    JavaScript, not staff JavaScript. See AUTHORIZATION below.

    Overriding: to add columns or app-specific lookups, use the standard class
    override (see class_override(3)) - a same-named class in /rsx/models/
    replaces the core one wholesale. Keep app concepts (CRM links, client
    memberships) OUT of the core model; model them as separate app models that
    reference portal_users.id, exactly as site data sits beside User_Model.

    Admin lifecycle (staff side): the model provides the primitives, not an admin
    screen. STATUS_SUSPENDED + can_login() block login; reactivation is just
    status_id back to STATUS_ACTIVE; force-password-reset reuses the existing
    portal reset flow (a Portal_Password_Reset token + the portal reset email).
    The template ships staff admin surfaces over these primitives: a global
    "Portal Users" screen under Settings and per-client portal member rows, both
    calling one set of shared staff Ajax endpoints. To make a suspension effective
    immediately, also terminate the user's sessions:
    Portal_Session::terminate_all_sessions_for_user(int $portal_user_id).

AUTHORIZATION
    Portal authorization mirrors staff authorization exactly: DECLARATIVE #[Auth]
    gates on every surface (evaluated by Portal_Dispatcher, resolved against the
    portal realm's Portal_Permission), plus record-level rules in function bodies.
    There is one way to do each thing.

  Portal_Permission (the facade)
    The portal analogue of the staff Permission class. The marker base
    Portal_Permission_Abstract lives in framework core (Core/Portal/); the concrete
    Portal_Permission lives in the application (rsx/portal_permission.php) because
    its membership/role methods reference app models (Portal_Membership_Model) -
    exactly like staff Permission extends Permission_Abstract. All methods static:

      is_logged_in(): bool
      current_user(): ?Portal_User_Model      current_user_id(): ?int
      site_id(): int
      has_client_access(int $client_id): bool
      client_role(int $client_id): ?int        ROLE_VIEWER=1 / ROLE_COLLABORATOR=2
      can_collaborate(int $client_id): bool     role >= COLLABORATOR
      accessible_client_ids(): array            for whereIn() query scoping
      can_access(string $target): bool          every gate on the target passes

    is_logged_in() additionally carries #[Auth_Check], so it is nameable from
    #[Auth(...)] / @auth(...). The parameterized helpers are NOT gates (a gate
    takes no arguments); they stay inline in function bodies.

    JS mirror: Core/Js/Portal_Permission.js reads window.rsxapp.portal
    (is_auth, user, client_roles map). It is for HIDING UI AFFORDANCES ONLY - the
    server is the enforcement boundary.

  Record-level access: portal_fetch() + portal_can_read()
    A model becomes fetchable from portal JavaScript by using the core trait:

      use App\RSpade\Core\Portal\Portal_Authorizable;

    The trait supplies a gated portal_fetch($id) that (1) requires a portal session
    and (2) defers to the model's portal_can_read(). The ORM endpoint dispatches to
    portal_fetch() in a portal request context and to fetch() otherwise - one ORM,
    the method is chosen by context.

    Each portal-exposed model implements portal_can_read(): bool, FAIL-CLOSED,
    picking exactly ONE visibility rule:
      own-record       $this->id === Portal_Session::get_portal_user_id()
      shared-recipient  row recipient matches the portal user's linked contact
      membership-scoped Portal_Permission::has_client_access($this->client_id)

    Core models' portal_can_read() use Portal_Session; app models' use
    Portal_Permission (no core->app dependency).

  Route gating
    Declared, not detected. Public portal controllers (login, register, password
    reset, logout) carry #[Auth('public')]; everything else names portal-realm
    checks. Portal_Dispatcher evaluates the gate before any application code, and
    the manifest build FAILS on a portal surface that declares none. There is no
    exempt-handler scan and no pre_dispatch authorization.

  Enforcement
    Manifest build      every portal surface (#[Portal_Route], #[Ajax_Endpoint] in
                        the portal realm, portal_fetch(), @portal_spa actions)
                        carries a gate naming a defined portal check; the build
                        fails by file and member otherwise (rsx:man auth_gates).
    PORTAL-MODEL-FETCH-01 (rsx:check) a model exposing portal_fetch() must declare
                        portal_can_read(); a hand-rolled portal_fetch() must call
                        it. This is the RECORD-level layer, which gates do not
                        cover.

ACTIVITY & NOTIFICATIONS
    use App\RSpade\Core\Models\Portal_Notification_Model;

    Portal_Notification_Model is the framework-core portal activity / notification
    primitive - the bus that portal features emit into (the dashboard "what's new"
    feed, announcements, portal requests, and anything else). It resolves the
    activity/audit and notifications essentials in one per-recipient log.

    Shape: ONE ROW PER RECIPIENT. A notification is addressed to a specific portal
    user; emitting to N users writes N rows. This is the natural shape for a
    per-user feed and read-state. The model is site-scoped (Rsx_Site_Model_Abstract)
    and per-recipient authorized (portal_can_read() = own-recipient, fail-closed).

    App-agnostic: there is NO hard FK to application tables. The portal user is core
    (portal_users), so site_id + portal_user_id are first-class. An app-specific
    subject (a client, a project, an announcement) is referenced POLYMORPHICALLY via
    the type-ref system - subject_type stores a BIGINT type-ref id and reads back as
    the class basename, subject_id is the row id. Never FK the primitive to an app
    table.

    Table: portal_notifications
      id, site_id, portal_user_id (recipient), type (string key), subject_type +
      subject_id (polymorphic type-ref, nullable), payload (JSON title/body/url
      snapshot), read_at (nullable), created_at.

  Emit (the write side - features publish here)
    Portal_Notification_Model::emit($portal_user_ids, string $type, array $opts = [])
      $portal_user_ids   one recipient id, or a list (one row written per recipient)
      $type              free-form key owned by the emitting feature
                         ('announcement', 'request_opened', 'request_revision', ...)
      $opts              subject_type (class basename), subject_id (int),
                         payload (array), site_id (int - defaults to current site)
      Returns the created rows. Publishes a realtime event per recipient (below).
      Correct from either a staff request (e.g. an announcement broadcast) or a
      portal request, because the row's own site_id scopes both the write and the
      realtime message.

  Query (the read side - always scoped to one recipient)
    Portal_Notification_Model::feed($portal_user_id, $opts = [])    rows, newest first
        $opts: limit (default 50), unread_only (bool), since (ISO - created_at >
        since, i.e. "what's new since last login")
    Portal_Notification_Model::unread_count($portal_user_id)        int
    Portal_Notification_Model::mark_read($portal_user_id, $id)      bool (ownership-
                                                                   guarded, idempotent)
    Portal_Notification_Model::mark_all_read($portal_user_id)       int (rows updated)
    All read/mutate calls take the recipient id and scope to it; a user can only
    ever see or change their own notifications.

  Portal fetch endpoint (consumed by the feed UI)
    Rsx\Portal\Notifications\Portal_Notifications_Controller - a portal-authed
    #[Ajax_Endpoint] controller (class-level #[Auth('is_logged_in')], portal realm).
    Every
    method derives the recipient from the session - it never accepts a
    portal_user_id from the client. Endpoints: feed, unread_count, mark_read,
    mark_all_read. The feed UI is pure presentation over this.

  Realtime topic
    Portal_Notification_Topic (rsx/lib/topics/) - emit() publishes one message per
    recipient with filter {portal_user_id}. can_subscribe() authorizes ONLY the
    owning portal user (logged-in portal session whose id matches the filter), so a
    browser can live-refresh its own feed and no other. Notification-only: the
    message carries no confidential data; the browser re-fetches the feed via the
    endpoint. (Realtime::publish() takes an optional explicit $site_id, used here so
    portal emits scope by the row's site rather than the staff session.)

  Client portal activity stamping
    clients.portal_last_activity_at is stamped on every authenticated portal request
    by Portal_Main::pre_dispatch: for each client the current portal user is a member
    of (Portal_Permission::accessible_client_ids()), a single bulk UPDATE writes
    now(). A base-account user with no memberships incurs no write. clients is an app
    table, so this stamping lives app-side (portal_main.php); the core primitive
    stays clean.

REQUESTS (firm <-> client conversation thread)
    An application feature (reference template), not framework core. A Request is a
    stateful CONVERSATION THREAD between the firm and a client for collecting documents,
    questionnaires, checklists, etc. The firm opens a thread with an ask; either side
    posts replies (with optional file attachments) on an append-only timeline; the firm
    reviews submitted documents and drives the thread's status to completion. This
    replaces the old flat one-ask-per-request model entirely - there is no backwards
    compatibility.

    Two independent status axes:
      - THREAD status (one per thread): the conversation lifecycle.
      - DOCUMENT review state (per attached client document): Pending -> Accepted /
        Rejected(+reason). Vocabulary rule: a THREAD is "Approved"; a DOCUMENT is
        "Accepted/Rejected" (never "approved" for a doc).

    Audience: CLIENT-LEVEL. Every member of the thread's client sees and participates
    (consistent with the client Documents model). Reply permission: collaborators post,
    viewers are read-only (Portal_Permission::can_collaborate()).

    Data model (4 tables, all Rsx_Site_Model_Abstract, site-scoped):
      Portal_Request_Thread_Model    (portal_request_threads)
        Columns: site_id, client_id, title, status_id, last_activity_at (authorship
        comes from the framework audit pair - see model_normalization(7)).
        + Portal_Authorizable; portal_can_read() = has_client_access(client_id)
        (membership-scoped, fail-closed). resolve_recipient_ids() = active members of the
        client. status_id BIGINT enum (ONE canonical value; status_label($is_portal)
        resolves the audience-specific text):
          1 STATUS_NEW_REQUEST        New Request
          2 STATUS_NEEDS_MORE_INFO    Needs More Info
          3 STATUS_RESPONSE_SUBMITTED Response Submitted  (staff see "Needs Review")
          4 STATUS_APPROVED           Approved
          5 STATUS_CLOSED             Closed   (terminal; no reopen - start a new thread)
        Only RESPONSE_SUBMITTED differs by audience. CLOSED is the only "closed" group;
        everything else (incl. APPROVED) is "active".
        post_message($author,$body): append a message; a PORTAL author on a non-closed
        thread auto-transitions the thread to RESPONSE_SUBMITTED. set_status($new,$actor):
        change status + write an event row (no-op if unchanged).
      Portal_Request_Message_Model   (portal_request_messages)
        Append-only timeline post. author_type is a type-ref BIGINT (Login_User_Model
        staff | Portal_User_Model). is_from_staff(), author_name(), author_email().
      Portal_Request_Document_Model  (portal_request_documents)
        Per-attachment review metadata; the file itself is a File_Attachment (fileable =
        the thread, category 'attachment'). review_status BIGINT enum:
          1 REVIEW_PENDING (Needs Review) | 2 REVIEW_ACCEPTED | 3 REVIEW_REJECTED(+reason).
        requires_review=1 = a reviewable CLIENT submission (sidebar buckets); =0 = an
        informational STAFF attachment. accept($staff) / reject($staff,$reason).
      Portal_Request_Event_Model     (portal_request_events)
        A status-change card in the timeline. from_status/to_status reference the thread
        enum; actor_type is a type-ref. Per-document Accept/Reject does NOT create an event.

    Transitions: staff create -> NEW_REQUEST. A portal member posting a message OR a file
    on a non-closed thread -> RESPONSE_SUBMITTED (auto). Staff set NEEDS_MORE_INFO /
    APPROVED / CLOSED (a staff reply may carry a status change, applied AFTER the message).
    Every status change writes a portal_request_events row (a timeline card).

    Timeline = messages UNION events, ordered by created_at. Sidebar buckets: "Needs
    Review" (requires_review=1 + PENDING, staff-actionable) and "Accepted". Accepted
    documents stay in-thread (NOT auto-promoted to the client Documents library).

    Staff endpoints (Frontend_Clients_Controller, staff-gated):
      request_threads_list({id})            - the client's threads (active/closed) + a
                                              Needs Review count.
      request_thread_create({client_id,title,body})
                                            - open a thread (NEW_REQUEST) with the opening
                                              staff message; redirects to the staff view.
      request_thread_get({id})              - vitals + merged timeline + participants +
                                              the Needs Review / Accepted buckets (staff
                                              labels).
      request_thread_reply({thread_id,body?,status?,attachment_keys?[]})
                                            - post a staff reply; optional review-exempt
                                              staff attachments; optional status change
                                              (NEEDS_MORE_INFO / APPROVED / CLOSED) applied
                                              after the message. Emits notifications (below).
      request_document_review({document_id,decision:'accept'|'reject',reason?})
                                            - accept -> ACCEPTED; reject -> REJECTED+reason.
                                              Emits a DECISION notification.

    Portal endpoints (Rsx\Portal\Workspaces\Requests\Portal_Request_Threads_Controller,
    pre_dispatch on Portal_Permission; every method fails closed on has_client_access):
      list({client_id})        - the client's threads split active/closed (portal labels).
      get({id})                - vitals + timeline + participants + buckets (portal labels);
                                 can_collaborate flag for the composer.
      reply({thread_id,body?,attachment_keys?[]})
                               - collaborators only (viewers -> unauthorized). Posts the
                                 message (auto RESPONSE_SUBMITTED on a non-closed thread);
                                 each attached file becomes a reviewable
                                 Portal_Request_Document (requires_review=1, PENDING).
                                 Emails the thread creator (below).
      needs_response_for_user()
                               - threads across all the caller's clients in NEW_REQUEST /
                                 NEEDS_MORE_INFO (the firm is waiting) - for the dashboard
                                 "Action needed" panel.

    Notifications/email (best-effort, non-fatal to the originating request):
      - Staff reply (request_thread_reply): emits Portal_Notification
        NOTIFICATION_TYPE_REPLY to resolve_recipient_ids() (title + snippet + the portal
        thread URL); if the reply also changed status, ALSO emits NOTIFICATION_TYPE_STATUS.
      - Document decision (request_document_review): emits NOTIFICATION_TYPE_DECISION to
        the thread's client members (accepted/rejected + reason).
      - Client reply (portal reply): no staff in-app notification system exists, so the
        thread's creator (the audit-pair actor, $thread->created_by) is EMAILED
        (Rsx_Mail::send, TRANSACTIONAL, template Portal_Request_Reply_Email); guarded for
        a missing creator. The in-app notification bus is Portal_Notification_Model.

    File access: thread documents are gated by Portal_File_Access_Handlers (the
    file.thumbnail.authorize / file.download.authorize gates). Beyond STAFF (any logged-in
    internal user) and SHARED client-document recipients, a logged-in portal user may read
    an 'attachment' File_Attachment of a Portal_Request_Thread_Model whose client they are
    a member of (has_client_access) - read access is membership-based; review state is
    enforced separately. Fail-closed; anonymous and non-members get 403.

IMPERSONATION (VIEW AS CLIENT)
    Staff can open the portal AS a contact, to see exactly what that client sees,
    in a READ-ONLY session. The framework provides the session-auth machinery; the
    APPLICATION owns the policy (who may impersonate), the entry UI, and -
    critically - the read-only enforcement and experience.

    For the staff-side equivalent - a staff user impersonating another STAFF user
    through the MAIN session - see rsx:man session (IMPERSONATION). That case is a
    same-cookie in-place swap and is full read/write, not read-only.

    Session model. Impersonation is tracked as PROPERTIES on the browser's session
    row, never in the cookie (the cookie still holds only the opaque token, so the
    staff identity never reaches the client). Columns:
      impersonator_user_id      staff User_Model id; NULL = a normal portal login.
                                This both flags the session and records provenance.
      impersonation_started_at  audit / optional auto-expiry.
      handoff_token             single-use, short-TTL token for the claim handoff.
      handoff_expires_at        claim window for the handoff token.

    Cross-domain-safe handoff. Staff are on the main-app domain; the portal often
    has its own domain/cookie, so the main app cannot set the portal cookie
    directly. Flow:
      1. Staff endpoint calls Portal_Session::create_impersonation_session(
         $portal_user_id, $staff_user_id, $site_id) -> returns a single-use handoff
         token. This inserts a single-use HANDOFF row - pure transport, carrying
         the target portal user, the site and the staff id, and excluded from the
         device-session list; it does NOT set a cookie and does NOT touch the
         contact's last_login. Unclaimed handoffs are collected on the next call.
      2. Staff JS opens the claim URL in a new tab (target=_blank):
         Rsx_Portal::Route('Portal_Impersonate_Controller::claim', ['t'=>$token]).
      3. The portal claim route (#[Auth('public')]) calls
         Portal_Session::claim_impersonation($token): validate + burn the token
         (the transport row is consumed), then stamp the impersonated portal
         identity onto THE CLAIMING BROWSER'S OWN session - minting it if that
         browser has none - and redirect to the dashboard. Any portal identity
         already in that browser is replaced; the staff login on the same session
         is untouched. An expired/used token renders an "invalid link" page.
         THIS is what makes the flow cross-domain-safe: the claiming browser may
         be on the portal domain with its own cookie jar and its own row.
    Never put the real session_token in a URL; the handoff token exists for exactly
    this reason (single-use, ~60s TTL).

    Framework API (Portal_Session):
      create_impersonation_session($portal_user_id, $impersonator_user_id, $site_id): string
      claim_impersonation($handoff_token): bool   // validate+burn, stamp this browser
      stop_impersonation(): void                  // clear the portal properties
      is_impersonating(): bool                    // current session is impersonated
      get_impersonator_user_id(): ?int            // the staff id (audit/UI)
      cli_set_impersonator_user_id(?int): void    // test seeding
    JS mirror (UI affordance only): Rsx_Portal.is_impersonating(),
    Rsx_Portal.impersonator_user_id() - read from window.rsxapp.portal. stop()
    leaves the staff member's own staff login untouched: it lives in different
    columns on the same row.

    APPLICATION RESPONSIBILITY - read-only is NOT enforced by the framework.
    The framework only EXPOSES is_impersonating(); the app MUST enforce read-only.
    Two duties:
      1. Block writes. Guard every MUTATING portal endpoint on the impersonation
         flag. A blanket pre_dispatch POST block does NOT work - all Ajax endpoints
         are POST, including reads (datagrid/profile/model fetch), so a blanket
         block breaks the portal's ability to even load. Guard per write endpoint:

             #[Ajax_Endpoint]
             public static function reply(Request $request, array $params = []) {
                 if (Portal_Permission::is_read_only()) {
                     return response_unauthorized('This is a read-only session; '
                         . 'changes are disabled.');
                 }
                 // ... normal write ...
             }

         The template app adds an app-level Portal_Permission::is_read_only()
         (returns Portal_Session::is_impersonating()) and guards every portal write
         (settings change_password / terminate_session, notifications mark_read /
         mark_all_read, request reply, invitation accept / decline). A real app must
         guard ALL of its writes - unguarded endpoints remain writable.
      2. Show a read-only experience. Render a persistent banner and disable submit
         controls when Rsx_Portal.is_impersonating() (the template adds the banner
         with an "Exit read-only view" link to Portal_Impersonate_Controller::stop).
         The server check is the boundary; the JS is affordance only.

    Replacing the staff member's own portal identity in that browser is acceptable
    and expected (the new tab shares the browser's one session). Permission to
    impersonate is the app's call - the template gates begin_portal_impersonation
    on Permission::has_role(User_Model::ROLE_MANAGER).

URL GENERATION
    Mandatory - never hardcode portal URLs. Same surface in PHP and JS:
      Rsx_Portal::Route('Portal_Login_Controller')          // /_portal/login
      Rsx_Portal::Route('Portal_Project_View_Action', 123)  // id param
      Rsx_Portal::Route('...Action', ['id'=>1,'tab'=>'x'])  // named + query
      Rsx_Portal::url($action, $params)                     // absolute
    JavaScript: Rsx_Portal.Route(...), Rsx_Portal.is_portal(), Rsx_Portal.user()
    (the current portal user payload), Rsx_Portal.is_impersonating() (see
    IMPERSONATION). Integer param -> 'id'; array -> named params; extras become the
    query string.

CONFIGURATION
    Framework defaults live in config/rsx.php; an app layers overrides via
    rsx/resource/config/rsx.php. Keys under 'portal':
      domain                       dedicated host, or null to use the prefix
      prefix                       URL prefix in prefix mode (default '/_portal')
      session_lifetime_days        portal session lifetime (default 30)
      invitation_expiry_days       invitation code validity (framework default 7;
                                   the template app overrides to 14)
      password_min_length          minimum portal password length (default 8)
      password_reset_expiry_hours  reset token validity (default 1)

    There is NO framework key for the portal's site, deliberately (see PORTAL
    SESSIONS). A mono-site app keeps its own - the template uses
    'portal.site_id' in rsx/resource/config/rsx.php and reads it in
    Portal_Main::init() - and a multi-tenant app has no such key at all.

ONBOARDING (SIGNUP MODEL)
    Portal accounts are created by INVITATION ONLY - this is the framework's
    expected default, and there is no open self-registration. A staff user
    invites a contact; a single-use, expiring invitation code is emailed to that
    address; the recipient clicks the link and sets a password
    (Portal_Register_Controller validates the code before allowing registration).

    Because the invitation is delivered to the user's own mailbox, clicking it
    already proves control of the address. Portal accounts are therefore created
    ALREADY VERIFIED (is_verified = true), and there is deliberately NO separate
    email-verification step. can_login() still requires is_verified, which
    invitation signup satisfies.

    An application that chooses to add a non-invite (open) signup path takes on
    responsibility for verifying the email address itself before setting
    is_verified - the framework does not ship an open-signup verification flow.

    Self-service access lookup (Portal_Request_Access_Controller, /request-access,
    public): the login page links here ("Create one now"). It does NOT create an
    account (invite-only); it looks the email up and routes the visitor: an active
    invitation -> re-send the invitation email (refreshes expiry); an existing account
    -> "you already have an account, sign in"; neither -> "contact {brand} to be added".
    {brand} is config('rsx.name').

    INVITATION LIFECYCLE (sample template app)
        The template app tracks each invitation with an explicit status_id on
        Portal_Invitation_Model - status is the authoritative validity signal
        (used_at/expires_at remain for timing):
          PENDING  live; can be registered/accepted.
          USED     an account was created via it, or it was accepted/declined.
          EXPIRED  past its window (default 14 days). An hourly task,
                   Portal_Invitation_Service::expire_stale (Schedule '0 * * * *'),
                   flips stale PENDING invites to EXPIRED so links fail gracefully
                   and admin screens read accurately.
          REVOKED  an admin cancelled it (per-client members table Cancel action ->
                   Frontend_Clients_Controller::portal_revoke_invite).
        Transitions: create -> PENDING; register/accept/decline -> USED; cron ->
        EXPIRED; admin -> REVOKED; resend refreshes expiry AND reactivates to PENDING.

        Following a link never dead-ends on "invalid" unless the code is bogus or
        REVOKED. Portal_Register_Controller routes by state:
          - REVOKED                 -> "invitation cancelled" page.
          - an account already exists -> redirect to login (message=account_exists;
                                      the login page offers "forgot password"); a
                                      still-live invite is consumed.
          - PENDING (live)          -> registration form; on submit creates the
                                      account + the invited client membership.
          - EXPIRED (no account)    -> "expired" page whose Create Account button
                                      re-enters with allow_expired. An EXPIRED invite
                                      yields an ACCOUNT ONLY (verified, but NO client
                                      membership - the admin must re-invite for
                                      access). Only a live PENDING invite grants
                                      membership; EXPIRED and REVOKED do not.
        The 14-day window (config rsx.portal.invitation_expiry_days) is reflected in
        the invitation email copy and the members table.

        Post-auth redirect: when an invite is tied to a client, a successful
        register (new account, membership granted) or login (returning account that
        has access) lands on that client's workspace (Portal_Workspace_Overview_Action)
        rather than the dashboard; the invited client is carried to the login screen
        as ?client=<id>. An already-authenticated visit to /login or /register
        redirects straight through the same way.

ACCESS MODEL (ACCOUNT vs PER-CLIENT ACCESS)
    Account and access are SEPARATE layers:
      - Portal_User_Model is the ACCOUNT/identity: login + self-service password
        (the firm never manages portal passwords). One account per email per site.
      - Portal_Membership_Model (app) is the many-to-many PER-CLIENT access layer:
        one account can hold many client memberships. Authorization is
        membership-based (Portal_Permission).

    Invitations are PER-CLIENT:
      - New person (no portal account) -> the registration link onboards the
        account AND joins the invited client (the invitation metadata carries
        contact_id/client_id/role_id; Portal_Register_Controller creates the
        membership and links the contact on registration).
      - Existing portal account -> a PENDING per-client invitation the logged-in
        user must ACCEPT (no auto-add). The portal dashboard surfaces pending
        invitations with Accept (creates the membership) / Decline (consumes the
        invite). Pending invites are matched to an account by the invited email
        and/or its linked contact_id.

    Staff controls (per-client members table):
      - "Disable Access" REMOVES that client's membership. The account, contact,
        and login all persist - this is NOT an account suspension.
      - "Resend Invite" re-sends a pending invitation and refreshes its expiry.
      - "Cancel Invite" REVOKES a pending invitation (portal_revoke_invite) so its
        link stops working (shows the "cancelled" page) instead of lingering.

    Account-level suspend is a DISTINCT, de-emphasized GLOBAL "ban this account
    entirely" action on the global Portal Users admin screen
    (portal_user_suspend / portal_user_reactivate). Force-password-reset is NOT a
    staff action - login/password is the external user's self-service concern.

    Zero memberships: a clientless portal account may still sign in; the template
    default shows a "no active client access" empty state on the dashboard (plus
    any pending-invitations panel). There is no hard membership gate.

NAVIGATION (MY WORKSPACES + WORKSPACE DETAIL)
    The template ships a membership-driven navigation shell over the access model.

    My Workspaces home (Portal_Dashboard_Action): a two-column dashboard. The left
    column lists the caller's client workspaces (one per Portal_Membership) with the
    client name + role badge, each linking to that workspace's detail page; the right
    column is the GLOBAL "What's New" activity feed (the notification feed is not
    per-client this phase). The pending-invitations panel sits full-width above the
    columns; the "no active client access" empty state is preserved.

    Workspace area (Portal_Workspace_Layout, a nested @layout): the per-client area is
    a SUBLAYOUT - the portal analogue of the staff Settings_Layout. A persistent
    engagement (client) name header plus a left vertical pills nav - Overview /
    Requests / Documents - wraps a $sid="content" body that swaps per pill. Each pill
    is its own SPA action (@layout('Portal_Layout') @layout('Portal_Workspace_Layout')):

        Portal_Workspace_Overview_Action   @route('/workspace/:id')
        Portal_Workspace_Requests_Action   @route('/workspace/:id/requests')
        Portal_Workspace_Documents_Action  @route('/workspace/:id/documents')

    Parametrized sublayout: Spa reuses a layout instance by class name, so the single
    Portal_Workspace_Layout persists across tabs AND across workspace ids. It reads the
    :id from on_action(url, action_name, args) (args.id) - on_action fires after the
    sub-action is already mounted into $content, so the layout must NOT render() (that
    would wipe the action); it fills the header text + pill hrefs via DOM writes and
    re-loads the header only when the :id changes (mirrors how Settings_Layout updates
    only its nav in on_action).

    Overview (the default tab) shows a short summary plus key client "vitals" (status,
    role, engagement type, primary contact, client-since, member-since) - demo/
    placeholder values from portal-safe client fields, customized per-app in real use.
    Documents is the firm-shares-to-client document area (see DOCUMENTS below).
    Requests is the firm <-> client conversation-thread area: a thread list (active /
    closed) plus a thread view (timeline + composer + document buckets) at
    Portal_Request_Thread_Action @route('/workspace/:id/requests/:thread_id') - see
    REQUESTS above.

DOCUMENTS (FIRM -> CLIENT SHARE)
    A "document" is just a File_Attachment_Model attached to a Client under the
    'documents' category (no new document model). Reuses the existing file, share,
    invite and notification primitives - it does not reinvent them.

    SHARING MODEL (current - client-level, for demo simplicity): documents are shared at
    the CLIENT level. A document is "shared with the client" once ANY Shared_Item_Model
    row exists for it (item_type='File_Attachment_Model', item_id=attachment id); once
    shared it is visible to and downloadable by EVERY portal user of that client.
    Visibility is therefore membership-based - it does NOT depend on which contact the
    share names. Inviting a specific contact shares the document with the whole client
    AND emails that contact a notification; the per-contact Shared_Item rows only record
    who was invited/emailed. A newly added member immediately sees every already-shared
    document (no per-member backfill). End-user applications will likely replace this
    with a more granular per-document / per-contact sharing model - the per-contact share
    rows are retained precisely so that evolution is straightforward.

    DEMO AUTO-SHARE (dev sites only): on a dev site, and never during the test suite,
    Rsx\Lib\Portal_Demo_Autoshare auto-shares every uploaded document with its client so
    the portal Documents tab is populated without manual sharing. No-op in real
    deployments (guarded on Rsx::is_dev_site()).

    Staff side (Frontend_Clients_Controller, on the client Portal page's Documents tab):
        documents_list({id})       - the client's 'documents' attachments + each one's
                                     shares (who it's shared with, has_portal_account).
        documents_add({client_id,key}) - attach an uploaded file (browser uploads to
                                     /_upload first, then passes the key) to the client.
        documents_share({client_id, attachment_id|key, contact_ids[], message?}) -
                                     SET-BASED reconcile: make the document's share list
                                     exactly contact_ids. Contacts newly in the set are
                                     shared (a Shared_Item is created) and, per recipient:
                                       * WITH a portal account: emit a 'document_shared'
                                         portal notification + send the
                                         Portal_Shared_Content_Email.
                                       * not-yet-invited: trigger the SAME per-client
                                         invite path portal_bulk_invite uses (invitation +
                                         registration email) so they can register (joining
                                         the client) and view it, plus the shared email.
                                     Contacts DROPPED from the set have their Shared_Item
                                     removed; an empty set removes all shares. The staff
                                     Share dialog pre-checks current shares and confirms
                                     the add/remove diff before calling this.
        documents_unshare({shared_item_id}) - delete one share (used by tests).
        document_delete({client_id, attachment_id|key}) - delete all shares of the
                                     attachment then detach it from the client.

    Portal side (Portal_Documents_Controller, the workspace Documents tab):
        list({client_id}) - the client's shared docs for that workspace. Fail-closed:
        membership-gated via Portal_Permission::has_client_access (the workspace is taken
        from a membership check, never trusted params). Returns every 'documents'
        attachment of the client that has been shared with the client (has at least one
        Shared_Item); uploaded-but-unshared documents are excluded.

    File access (serving the thumbnail + download to a portal user):
    Rsx\Handlers\Portal_File_Access_Handlers registers BOTH file.thumbnail.authorize
    and file.download.authorize gates. The gate allows a logged-in STAFF user (manages
    the files) OR a logged-in PORTAL user who is a MEMBER of the document's client, when
    the attachment is a 'documents' attachment that has been shared with the client (any
    Shared_Item exists). Everyone else (anonymous, a non-member, or an unshared document)
    gets a 403. Registering these gates tightens the previously ungated
    /_download//_thumbnail//_inline endpoints to deny-by-default.

    Membership gate: each tab action runs its own three-state (loading ->
    Universal_Error_Page_Component -> content) off Portal_Workspaces_Controller::get(),
    which fails closed for a non-member (membership re-checked via
    Portal_Permission::has_client_access), so a non-member hitting ANY tab lands on the
    access-denied error state rather than the row.

    Endpoint: Rsx\Portal\Workspaces\Portal_Workspaces_Controller - portal-authed
    (pre_dispatch on Portal_Permission). list() returns the caller's workspaces
    (client_id, name, role_id, role_label, status_label); get({id}) returns a single
    workspace header + an Overview 'vitals' block for a client the caller is a member
    of. The user is always taken from the session; only portal-safe fields are exposed.

SAMPLE APPLICATION (THE SHIPPED REFERENCE TEMPLATE)
    Everything in /rsx/ is a working REFERENCE APPLICATION, not framework core - a
    runnable B2B SaaS starter that demonstrates the portal end to end and is meant to be
    customized or replaced per app. The framework (the Core/Portal classes and helpers
    documented above) is the contract; /rsx/ is one concrete, opinionated build on it.

    What it ships
      - Staff side: a CRM (clients, contacts, projects), user management, and the per-
        client "Portal" admin page (Clients_Portal_Action) with tabs Members / Documents /
        Requests / Announcements / Projects.
      - Portal side: invite-only onboarding + self-service access lookup, the My
        Workspaces dashboard (workspaces list + global "What's New" feed + Action-needed +
        pending-invitation panels), and the per-client workspace sublayout (Overview /
        Requests / Documents). Auth pages: login (with "Create one now"), register,
        password reset.
      - App models layered on the core: Portal_Membership_Model (per-client access),
        Portal_Invitation_Model, and the request-thread models.

    How SHARING behaves in the template
      - Documents are shared at the CLIENT level (see DOCUMENTS): a document with ANY
        Shared_Item is visible + downloadable to EVERY member of that client; the staff
        Share dialog edits that member set (set-based reconcile with an add/remove
        confirmation). This is the deliberately simple demo model; a real app will likely
        adopt a more granular per-document/per-contact model (the per-contact share rows
        are kept so that change is easy).
      - Request-thread documents are membership-gated (any client member may read a
        thread 'attachment'); review state (Pending/Accepted/Rejected) is tracked
        separately and does not gate read access.
      - Inviting a contact to a document/thread shares it with the whole client and
        additionally emails that one contact.

    DEV-ONLY conveniences (NOT production behavior)
      - Demo auto-share (Rsx\Lib\Portal_Demo_Autoshare): on a dev site only, and never
        during the test suite, every uploaded client document is auto-shared with the
        client so the portal is populated without manual sharing. No-op in real
        deployments (guarded on Rsx::is_dev_site()).
      - Debug-site login auto-fill (config('rsx.default_user.*')) pre-fills credentials on
        the staff and portal login pages.
      - Seeded demo clients / contacts / portal users / threads exist only in the dev
        database. The admin@test.com demo account is intentionally wired to a contact for
        illustration; it is not a coherent end-user identity.
    None of these run in production - they exist so the template is explorable out of the
    box. Strip them when building a real application.

NOTES
    - The portal stack shares nothing with the main app's session, dispatch, or
      routing. Mixing Session and Portal_Session is always a bug.
    - Signup is invite-only by default (see ONBOARDING); the invitation proves
      email ownership, so accounts are created verified with no separate
      email-verification flow.
    - Messages and screens must enforce site scoping; Portal_Session resolves
      the site and Portal_User_Model rows are per site_id.
    - There is exactly one Portal_Main and one Portal_Spa_Controller per app.
