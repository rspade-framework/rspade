RSX_UPSTREAM(1)                   RSpade Manual                   RSX_UPSTREAM(1)

NAME
    rsx_upstream - pull RSpade framework updates into a downstream app while
    preserving your application code and any deliberate local system changes

SYNOPSIS
    Update the framework to the latest published release:
        php artisan rsx:framework:pull

    Preview what an update would bring (no changes):
        php artisan rsx:framework:pull --diff

    See exactly which owned-zone files you have changed (no changes):
        php artisan rsx:framework:pull --diff-system-changes

    Report the installed release + whether an update is available:
        php artisan rsx:framework:status

    Standalone tamper check of the framework tree:
        php artisan rsx:framework:verify

DESCRIPTION
    The RSpade framework core lives in ./system. In a downstream application it
    is VENDORED - ordinary git-tracked files inside your own app repository. It
    is NOT a git submodule and there is no gitlink. rsx:framework:pull refreshes
    those files from the distribution repository (rspade_system) and then COMMITS
    its own system/ changes as one dedicated framework-update commit; a pre-commit
    hook (installed by the post-update mechanism) keeps system/ out of your
    ordinary app commits (see COMMIT MODEL).

    Because system/ is tracked in your app repo, framework history finally lands
    in your history: `git log -- system/` shows what each update delivered as its
    own commit, and the full upstream history remains browsable at the
    rspade_system Gitea repo (see WHERE UPSTREAM HISTORY LIVES).

    The updater never merges. There is no `rspade_upstream` git remote, no
    `.gitattributes merge=ours` strategy, and no stash/merge/abort ritual. It
    clones the distribution into a temp checkout and reconciles your working tree
    file by file. It runs BEFORE Laravel boots (via the artisan pre-boot
    interception, self-healed from bin/framework-pull-upstream.sh.dist), so a
    framework broken badly enough that PHP will not start can still be repaired
    with a single command.

    Unlike Laravel, which has no notion of updating its own vendored framework in
    place, RSpade owns this end to end: it knows which files it authored, records
    every write it makes to a tracked framework file, and can therefore tell a
    genuine local edit from its own churn WITHOUT guessing (see TAMPER GATE).

THE UPDATE FLOW
    A normal `rsx:framework:pull` performs these steps in order:

    1. Gates. The command refuses (and does nothing) when any of these hold:
         - .rspade-forked-framework is present (you took full ownership; see
           rsx:man framework_fork),
         - IS_FRAMEWORK_DEVELOPER=true in .env (this is the monorepo; framework
           developers use plain git),
         - APP_ENV=production (update and test in development, then deploy the
           reviewed result).

    2. Fetch. A cached BARE clone of the distribution is kept at
       /tmp/rspade_upstream.git and fetched (cloned on first run). It lives
       OUTSIDE the app tree because it is pure re-derivable data: losing it (a
       reboot, a /tmp sweep) costs exactly one re-clone, and every consumer
       tolerates its absence. The new tip and, when resolvable, the currently-
       installed release commit are checked out into a temp directory for
       three-way comparison. The cache makes repeat runs and
       `rsx:framework:status` fast and offline-tolerant. Its location has one
       source of truth: Framework_Maintenance::upstream_cache_dir().

    3. Tamper gate. `rsx:framework:verify --json` runs (see TAMPER GATE). A
       MODIFIED or EXTRA file under a framework-owned zone aborts the update with
       a file list and the --diff-system-changes / --force explanation, because
       the sync would destroy content that is only on this box. A MISSING file
       never aborts: absence holds nothing, so restoring it is free and simply
       happens (see RESTORE IS NOT AN OVERRIDE). If verify cannot even run (the
       framework is too broken), the run aborts unless --force is given - a
       --force run doubles as the repair path.

    4. Owned-zone sync. The framework-OWNED zones are hard-synced from the new
       release with `rsync --delete`: whatever the release ships is exactly what
       lands, and any local edit there is removed. The owned zones are:
           app/RSpade/  vendor/  node_modules/  bin/  docs/  database/
           config/      resources/  supervisor/
           artisan      .rspade-release.json  .gitignore
       Individual FILES are first-class here, not a special case - any single
       file may be owned and is then synced exactly like a directory.
       The last five were added 2026-08-11. Each is framework property with an
       app-side equivalent elsewhere, so a lost file self-heals here instead of
       being mistaken for a deliberate deletion by the three-way pass:
           database/    framework migrations + the framework .migration_whitelist,
                        immutable once shipped. YOUR migrations live in
                        rsx/resource/migrations/ with their own whitelist.
           config/      framework config. YOUR overrides live in
                        rsx/resource/config/ and are merged over it.
           resources/   the Laravel view skeleton (error pages).
                        YOUR views live in rsx/.
           supervisor/  the framework's own service definitions.
           .gitignore   framework-tree hygiene. Tweaking it locally used to freeze
                        the file forever, so that box silently stopped receiving
                        every future upstream ignore rule.
       public/ is deliberately NOT owned - it is the docroot, where your app
       legitimately places static assets.
       storage/, your .env, and the system/rsx symlink are NEVER touched by the
       sync. This erases .upstream override files, use-header rewrites, and stale
       build artifacts by construction; the next build recreates whatever your
       class overrides need.

    5. Reconcile the mutation-marker store (the reconciling prune). Run at the
       EARLIEST pristine moment - immediately after the owned-zone sync, before
       the three-way pass and the rebuild. It drops only the markers whose recorded
       content no longer matches disk and KEEPS every marker that still attests the
       current tree; see TAMPER GATE AND MUTATION MARKERS below for why this is a
       prune and not a wipe. Uses `php artisan rsx:framework:prune_mutations`; if
       PHP is broken (a --force repair) it degrades to a wholesale reset.

    6. Three-way pass. Everything else in system/ (config, the Laravel skeleton,
       etc.) is reconciled per file against the installed release (old) and the
       new release (new):
           disk == old, new differs           -> take new (updated)
           disk == old, absent in new          -> delete (removed upstream)
           disk changed, upstream unchanged    -> keep yours (preserved, reported)
           disk changed AND upstream changed   -> CONFLICT: keep yours + report;
                                                  --force takes upstream
           new file upstream                   -> add
           your local-only addition            -> kept
       Nothing here ever blocks; conflicts are reported, never silently
       clobbered without --force.

       Output: the routine outcomes (kept / preserved / updated / added) are
       COUNTED into one summary line, never enumerated per file - a reconcile
       touches thousands of files nobody has to think about, and listing them
       buries what matters. Every CONFLICT is always named individually. The
       complete per-file log is written to
       storage/rsx-framework/last_pull_report.txt - whose path is printed BOTH
       with the reconciliation summary and again in the final
       `=== Update complete ===` block, because the reconciliation section is
       exactly the part that scrolls away; --verbose streams it to the console
       instead.

    7. Changelog. `git log old..new` from the temp clone is printed and a dated
       section is PREPENDED to rsx/resource/framework_update_history.dat (see
       UPDATE HISTORY FILE).

    8. Commit. The updater commits its OWN system/ changes (+ the history file)
       as one dedicated framework-update commit - BEFORE the rebuild, so what
       lands in history is the PRISTINE release exactly as synced (see COMMIT
       MODEL). Any remaining working-tree changes are app-side, left for you.
       --no-commit leaves the framework changes uncommitted instead, and warns.

    9. Rebuild (unless --no-rebuild):
           rsx:env:heal            (re-symlink / reconcile .env; non-fatal)
           rsx:clean --silent --_no-system-reset
                                   (caches only: the updater manages system/
                                    itself, and build tooling never touches git
                                    state; the tamper gate in step 3 already
                                    verified the tree.
                                    --_no-system-reset is a framework-INTERNAL
                                    flag: argv-stripped pre-boot, listed in no
                                    help output - see the `--_` convention)
           rsx:manifest:build --_no-check-schema-updates-pending
                                   (the build normally prints the pending-
                                    migration notice as its last line; the pull
                                    emits that notice ONCE itself, at the end)
           php artisan migrate --framework-only --force
                                   (failure ABORTS LOUD with the full migrate
                                    output - the update is incomplete until the
                                    migration error is resolved and you re-run)
           rsx:bundle:compile
           rsx:framework:post_update   (env heal -> upstream_changes check ->
                                        dependency reconciler; non-fatal)
       The rebuild's manifest pass re-applies + re-records class-override churn on
       top of the pristine tree; because the prune (step 5) already ran, that fresh
       churn is retained, not wiped. The churn itself stays LOCAL - the commit is
       already made, and the updater's own commit actively NORMALIZES any override
       pair out of the tree it records (see COMMIT MODEL).

       A FAILING REBUILD NO LONGER COSTS THE UPDATE. The release is in history by
       this point, so the repair is a REBUILD - fix what the build rejects and let
       the dev-mode auto-rebuild proceed, or run rsx:manifest:build - never a
       re-pull. This matters most for a release whose own build-time enforcement
       rejects not-yet-migrated app code: under the old commit-after-rebuild order
       the synced release sat uncommitted, and the next app commit's pre-commit
       hook reset it away, so the migration that would fix the build could never be
       committed. That deadlock is now structurally impossible.

    10. Post-update (see ENVIRONMENT UPDATES). bin/post-update.sh runs as a
       SUBPROCESS - the freshly-synced copy, so new behavior lands on the same
       pull that ships it - then migrate:status_notice gives a final advisory if
       migrations are pending.

ENVIRONMENT UPDATES
    Durable "make this environment correct" work does NOT live in the updater (a
    running bash script cannot safely edit itself, and a change to it lags one
    pull). It lives in bin/post-update.sh, which executes every numbered script in
    bin/environment_updates/ at the end of a successful pull. Each script is
    self-detecting, idempotent, SILENT when already applied, and non-fatal.

    THE PULL IS NOT THE ONLY TRIGGER. system/ is vendored, so a plain `git pull`
    DELIVERS a new environment update but runs nothing - an environment that never
    runs a framework update would carry the scripts and none of their effects. Two
    non-pull triggers close that gap, both entering through the same
    bin/post-update.sh:

        A SUCCESSFUL rsx:manifest:build, in DEVELOPMENT mode only (sealed
        debug/production builds must never self-modify), skipped while maintenance
        mode is up, serialized on the ENVIRONMENT_UPDATES named write lock, and
        non-fatal. Because the pull raises the maintenance window around its own
        rebuild, that skip is exactly what keeps a pull applying the updates ONCE.
        This is the bootstrap-safe trigger - a build runs in every environment
        regardless of hooks, clone age, or how the code arrived.

        The post-commit hook installed by environment_updates/050 (detached, never
        blocks or fails a commit). Git never distributes .git/hooks, so this is a
        latency shortener only: it presupposes one of the other two triggers has
        already run once.

    post-update.sh itself also sets git core.fileMode false (both contexts), which
    silences mode-bit churn on the vendored framework tree. The numbered scripts
    shipping today:

        010  the Claude Code status line - augment-only into .claude/settings.json,
             pointing at system/bin/statusline.sh; a developer's own custom status
             line is reported and left alone. The renderer deliberately EXCLUDES
             system/ from the changed-file count it shows on a downstream app: the
             framework tree is the updater's, and counting its churn as "your
             changes" is noise. (In the monorepo, system/ IS the work, so it counts.)
        020  the pre-commit hook (RSPADE-PRECOMMIT-V1) - see COMMIT MODEL. Never
             clobbers a foreign hook.
        030  the one-time storage relocation - moves system/storage to
             <project>/storage and drops the marker (see `rsx:man
             storage_directories`). It MERGES entry-by-entry into an existing
             destination rather than replacing it, so a partially-relocated box
             completes cleanly; only a genuine FILE-vs-directory collision stops it.
        040  the Claude Code git guard - registers system/bin/claude-git-guard.sh
             as a PreToolUse hook on Bash. It blocks a bare `git` and redirects to
             `php artisan rsx:git`, the transparent proxy that owns system/ safety
             and service quiescing (`rsx:man rsx_git`). Fail-open, augment-only,
             foreign hooks preserved. It also REMOVES the retired pre-pull-guard
             registration it superseded - that guard told the agent to run rsx:clean
             then pull, which deadlocks on a live box because the class-override
             churn returns before the pull's index write can land.
        050  the post-commit hook (RSPADE-POSTCOMMIT-V1) - spawns post-update.sh
             detached after a commit, so the environment updates apply without
             waiting for the next build or pull. Never blocks or fails a commit;
             a foreign post-commit hook is reported and left alone.

    Adding your own is not supported - the directory is a framework-owned zone and
    is hard-synced on every pull.

COMMIT MODEL
    system/ is OWNED by the updater and is committed ONLY by it. Each pull makes
    one dedicated framework commit of everything under system/ (plus
    rsx/resource/framework_update_history.dat), path-scoped so your in-flight app
    work - staged or not - is never swept into it. The commit runs BEFORE the
    rebuild, so it records the PRISTINE DISTRIBUTION STATE exactly as synced -
    pristine by construction, which is why it needs no authorization gate of its
    own (the tamper gate's job is refusing to OVERWRITE hand edits at sync time).

    Three properties follow, and they are the whole reason for the ordering:

        A failed rebuild is harmless. The release is already in history, so every
        later rsx:clean / pre-commit-hook reset lands ON the new release instead
        of reverting it, and the repair for a bad build is a rebuild.

        Framework runtime churn is ALWAYS-LOCAL. The class-override
        .php <-> .php.upstream renames (and the other rewrites the manifest pass
        performs) are regenerate-on-demand state - uncommitted but VISIBLE
        system/ modifications that rsx:clean resets and the next build
        regenerates, exactly like every other rebuild-churn path. The updater's
        commit KEEPS it that way by construction (see THE COMMIT'S TREE below):
        every sidecar is normalized out and the release copy staged in its place,
        so a pair that was already on disk before the pull cannot ride along. They
        are not HIDDEN (the retired skip-worktree + *.php.upstream devices were),
        and the mutation-marker ledger still authorizes them for the tamper gate.

        Sister environments converge. A pristine commit is byte-identical for the
        same release everywhere, so two boxes pulling it with different app
        override sets no longer produce diverging framework commits - a whole
        class of system/ merge conflict disappears.

        Subject:  Framework update <old12> -> <new12> (N upstream commits)
        Body:     the FULL upstream changelog for old..new - every commit's subject
                  AND body, the same canonical text written to
                  framework_update_history.dat. Your app's git history is the audit
                  record, so `git log` alone answers "what changed in the framework
                  and why" without opening the .dat. Capped at 64KB (by SIZE, not
                  commit count); if it truncates it says how many bytes were elided
                  and points at the .dat, which is never capped. Agent-attribution
                  lines are filtered out.
        Trailers: Framework-Update-Range: <old>..<new>
                  Committed-By: rsx:framework:pull

    THE COMMIT'S TREE IS BUILT IN A THROWAWAY INDEX, AND THEN PROVEN.
    `git commit -- <paths>` cannot be used: with a pathspec git rebuilds the tree
    from HEAD plus the WORKING TREE content of the named paths and IGNORES THE
    INDEX - and the working tree is the one thing that must not be trusted here,
    because it carries this box's class-override pairs. The same semantics are
    reproduced by hand in a temporary index (GIT_INDEX_FILE; the developer's own
    index is never read or written, so in-flight app work is untouchable by
    construction rather than by pathspec):

        1. seed the throwaway index from HEAD
        2. add the system/ pathspec into it
        3. NORMALIZE THE INDEX INTO THE RELEASE (normalize_commit_index), two passes:

             a. Override pairs. Each `X.php.upstream` is dropped from the index and
                the RELEASE copy of `X.php` staged in its place (hashed through the
                same attribute path a plain `git add` would use, so byte fidelity
                holds). A sidecar whose base the release no longer ships is simply
                dropped. Pairs that pre-dated the pull are covered too - the
                normalization is over what is ON DISK, not over what this run
                authored.

             b. Foreign paths. EVERY tracked path under system/ that
                .rspade-release.json does not list is untracked from the commit.
                system/ is rsynced from the distribution with --delete semantics
                (owner ruling, 2026-08-18): "any tracked files in the destination
                not in the framework distribution must be untracked and deleted
                from git." It is a vendored, machine-owned, read-only tree, so
                there is no such thing as a local addition history may carry - no
                allowlist, no escape hatch. What this removes in practice is
                machine-generated box state an earlier `add -f -A` swept in
                (fossil CLI-test storage trees, route-pattern caches,
                bootstrap/cache/*.php, .env.replaced_by_healer - 7,480 paths on one
                field box). The run prints the count and a sample.

                THE WORKING TREE IS NOT TOUCHED. Untracking is a statement about
                history; those files are live local state. The disk-side purge is a
                peer's next rsx:git pull reset (`clean -fdq -- system`), and that is
                the intended outcome.

        4. ASSERT THE RESULT IS THE RELEASE - assert_index_matches_release compares
           the staged path set against .rspade-release.json (excluding the inventory
           itself, .env, and storage/** - the same exclusions pass (b) applies, by
           construction: both go through one partition helper). ALL THREE findings
           are FATAL and refuse the commit: a release path MISSING from it, a
           `*.upstream` path IN it, and an EXTRA path the release does not ship.
           EXTRA is empty by construction after pass (b), so a non-empty EXTRA means
           the normalization itself failed - which is exactly the silent structural
           fault this assertion exists to stop. An inventory that cannot be read
           asserts nothing.
        5. write-tree + commit-tree + update-ref - exactly the tree that was built.

    BASELINE REPAIR ON AN ALREADY-CURRENT BOX. "Up to date" is a claim about the
    MARKER, not about history, so the up-to-date branch also compares HEAD's
    system/ path set against the inventory (same partition, same exclusions). When
    they disagree the run falls through to a COMMIT-ONLY repair - no sync, no
    rebuild, no maintenance window, working tree untouched - building the same
    throwaway-index commit under its own subject:

        Framework baseline repair <release_id>: system/ re-stated as the release

    with the same Committed-By: rsx:framework:pull trailer. It needs no --force,
    which matters: --force is a tamper-gate override that would also overwrite
    accepted committed drift. Without this, a marker-current box carried its
    tracked sidecars and foreign paths in shared history until the next release
    happened along. A clean baseline reports "up to date" and exits, as always.

    A REPAIR ONLY EVER GOES FORWARD. The repair re-states the committed tree to
    match the ON-DISK marker, so aiming it at a STALE marker untracks everything
    the newer release added - which is precisely the 2026-08-18 field misfire.
    Before repairing, the marker's date is compared against the distribution tip's;
    when the marker is OLDER the run says so and falls through to the ordinary
    FORWARD sync instead. Resolving the installed release from that same marker
    (see UPDATE HISTORY FILE) already makes this unreachable; the guard is the
    second line, and it costs two `sed`s.

    No hook runs on that plumbing path (which is what --no-verify +
    RSPADE_FRAMEWORK_COMMIT=1 were arranging anyway), and a run whose only
    difference from HEAD was the local churn produces an identical tree and commits
    nothing.

    Pre-commit guard. A pre-commit hook (keyed RSPADE-PRECOMMIT-V1) runs
    rsx:clean - which downstream resets system/ to its last commit, REMOVING
    UNTRACKED FILES under system/ as well (the framework tree is machine-written,
    so an untracked file there is churn or foreign by definition; a stale
    class-override .php.upstream leftover is the canonical case - owner ruling
    2026-08-12; gitignored files such as the system/.env symlink are untouched) -
    and then unstages any system/ path still staged, so a framework change can
    never ride an app commit and the two histories stay separate. The reset is
    INTEGRITY-GATED: rsx:clean runs rsx:framework:verify first and, on
    unauthorized (hand-made) framework modifications, refuses the reset and
    exits 1 instead of silently destroying them (class-override churn, committed
    drift, and a missing release manifest all pass; rsx:clean --force skips the
    check and discards unconditionally). The hook treats that failure as a warning, not a
    commit blocker - the unstage step still protects the commit; the refusal
    output tells you the tree is tampered. If nothing is left to
    commit afterward it aborts and says so. The hook is installed by the
    post-update mechanism (bin/post-update.sh ->
    bin/environment_updates/020_precommit_hook.sh), which the updater runs at the
    end of every successful pull, NOT by the updater itself; behavior contract
    unchanged. The updater's own commit bypasses it via RSPADE_FRAMEWORK_COMMIT=1
    + --no-verify; a merge commit (MERGE_HEAD present) is also exempt so
    resolving a pull that carries another environment's framework commit never
    strips it. A FOREIGN pre-commit hook (no marker) is never overwritten - the
    installer reports the skip and leaves it for you to merge.

    system/ must never be gitignored. An ignore rule over the vendored tree masks
    drift detection and re-opens the tracked-but-ignored bootstrap failure class,
    so the updater strips a root-.gitignore line that ignores system/ wholesale
    and warns if some other rule (global excludes) still hides it. Commit hygiene
    is the hook's job, not an ignore rule's. The old git skip-worktree +
    *.php.upstream hiding of override churn is RETIRED: skip-worktree is cleared
    (never reapplied) and the *.php.upstream ignore line removed, because a set
    skip-worktree bit would silently drop the override zone from the commit
    (`git add -f` overrides gitignore but NOT skip-worktree). core.fileMode false
    (silences mode-bit churn on the vendored tree) is set by bin/post-update.sh.

    Failure is loud but non-fatal: the sync itself succeeded; the changes are
    left staged with a manual-commit incantation (they must NOT ride an app
    commit - the guard strips them):
        RSPADE_FRAMEWORK_COMMIT=1 git commit --no-verify -- system \
            rsx/resource/framework_update_history.dat

    SYNCED BUT UNCOMMITTED is the one lethal intermediate state, and the updater
    says so loudly on every exit path that leaves it: the release is on disk and
    out of history, so an rsx:clean - directly, or via the pre-commit hook on the
    very next app commit - resets system/ to its last commit and silently reverts
    the update. Committing before the rebuild makes the state unreachable in the
    normal flow; it remains reachable on a failure between the sync and the commit,
    and deliberately under --no-commit. The warning names the recovery:

        [ERROR] system/ holds a synced but UNCOMMITTED framework release.
                Do NOT run rsx:clean or make any app commit until it is committed -
                either would revert the update. Recover with:
                php artisan rsx:framework:pull --no-rebuild

    (--no-rebuild is the recovery because it syncs and commits with no build gate
    in between.)

FLAGS
    --yes
        Consent non-interactively (required for the one-time submodule
        conversion when stdin is not a TTY; see SUBMODULE CONVERSION).

    --force
        The OVERRIDE flag, and only that. It (a) overwrites unauthorized changes
        under the owned zones instead of aborting, (b) takes the UPSTREAM side of
        every three-way conflict, and (c) proceeds even when the tamper gate
        cannot run because the framework is broken. On an already-up-to-date
        install it additionally forces a full repair resync, since a
        complete-looking tree can still hold drift or wiped build state.
        LLM AGENTS: never pass --force without explicit user permission - it
        DESTROYS local changes under the owned zones.

        It does NOT govern whether a MISSING file comes back. That used to be
        bundled in, which meant the only offered cure for an absence was the one
        flag that destroys modified files - see RESTORE IS NOT AN OVERRIDE.

    --resync
        RECOVERY, not an override. Restores every framework-owned zone to the
        distribution tip and re-commits system/ as that release, INDEPENDENT of
        what any marker claims - so it never short-circuits on "up to date". It
        exists for the tree a BACKWARDS MERGE moved off its release (Ascent,
        2026-08-18): such a box's markers cannot be trusted to route it back, and
        waiting for the next release to happen along is not a recovery.

        It is NOT --force, and that difference is the entire point: locally
        modified files still pass through the tamper gate, and the non-owned tree
        is still reconciled by the three-way pass, so ACCEPTED COMMITTED DRIFT
        SURVIVES. Absent files are restored and unmodified ones synced, because
        restoring costs nothing (see RESTORE IS NOT AN OVERRIDE).

    --diff-system-changes
        Gate-only inspection. Runs the same clone + verify pass and prints ONLY
        the offending diff lines (your changes vs the expected framework-authored
        or pristine content) for each flagged owned-zone file, makes NO changes,
        and exits non-zero when anything is flagged. Because the "expected" side
        is the framework's own recorded content, the diff shows exactly your
        lines and never framework churn.

    --no-rebuild
        Skip step 9. The files are reconciled AND COMMITTED but the manifest/
        bundles/migrations are not rebuilt; the command prints the exact artisan
        commands to finish by hand. This is also the recovery for a pull that died
        at the rebuild step under an older updater (sync + commit, no build gate
        in between).

    --no-commit
        Skip the updater's OWN commit of its system/ changes (step 8). The
        changes are left STAGED for you to commit manually - and they must NOT
        ride an ordinary app commit (the pre-commit guard strips system/ paths);
        use RSPADE_FRAMEWORK_COMMIT=1 git commit --no-verify -- system ... . The
        run ends with the synced-but-uncommitted warning, because that is exactly
        the state it leaves behind. See COMMIT MODEL.

    --check-foreign-changes
        Local-only drift probe: print any uncommitted changes under system/ and
        exit (1 if dirty, 0 if pristine). No gates, no network, no PHP, no
        changes - the shared "did anything change under system/ that shouldn't
        have" check (rsx:clean --reset-system shells out to it).

    --diff
        Preview only. Prints the changelog (git log) and diffstat the update
        WOULD bring and exits, making zero changes.

    --verbose
        Stream the FULL per-file reconciliation to the console instead of the
        counted summary (step 6). The same detail is always written to
        storage/rsx-framework/last_pull_report.txt regardless.

    --upstream-url=<url>
        Override the distribution URL (default
        ssh://git@git.internal.hanson.xyz/brianhansonxyz/rspade_system.git,
        branch master). Rarely needed.

RESTORE IS NOT AN OVERRIDE
    Owned zones are CONVERGENT state, not diffed state: every pull leaves them
    equal to the release, and a run that finds them short simply makes them whole.
    A missing file is never read as an instruction. rsx:clean runs immediately
    before the sync and reverts every machine-made change to system/, so past that
    point an absence is damage or a violation of the read-only rule - and the
    class-override rename (X.php moved aside to X.php.upstream) is the one
    innocent explanation, exempted exactly as the tamper gate exempts it.

    The two categories have OPPOSITE risk profiles, so they get opposite answers:

        MODIFIED / EXTRA owned file   local content the sync would destroy
                                      -> tamper gate; --force required
        MISSING owned file            nothing at stake
                                      -> restored, reported, no flag

    Restoring is free, so it is not a decision anyone has to make. Bundling it
    into --force meant the tool routed operators through the one flag that
    DESTROYS modified files in order to solve the problem that endangers none -
    and a box whose --force could not satisfy the check had no way forward at all
    (Ascent, 2026-08-11: 15 framework files, 13 of them migrations, lost from a
    current install while every command reported the tree healthy).

    This applies to the whole of system/, not only the owned zones: the three-way
    pass re-adds a release file that is absent from disk with no override, and
    names each one. What the updater CANNOT restore (a path outside both passes,
    or one the release does not carry) is reported separately with honest advice
    - never as "try --force", which would be a lie.

    A completeness check runs even on an up-to-date install, because "up to date"
    is a claim about the marker, not about the tree. If it finds repairable
    absences the run proceeds into the ordinary passes and converges; if it finds
    only unrepairable ones it says so and settles as up to date.

TAMPER GATE AND MUTATION MARKERS
    The gate distinguishes a file YOU changed from a file the FRAMEWORK changed
    without any regex heuristic - it is marker-based BY CONSTRUCTION.

    Release inventory. Every published release carries system/.rspade-release.json
    written by bin/publish:
        {release_id: <source monorepo SHA>, date, files: {rel_path: sha256}}
    covering every shipped file (a symlink-to-file is hashed by its target's
    content; .git, .env, directory symlinks, and the manifest itself are
    excluded). Each release therefore self-describes its own pristine state, so
    the gate is fully offline and needs nothing stored at update time.

    Mutation markers. The framework legitimately rewrites some of its own tracked
    files at runtime. Each such write is recorded at mutation time by
    App\RSpade\Core\Framework\Framework_Mutations into the gitignored store
    storage/rsx-framework/ (which SURVIVES rsx:clean): an index mutations.json
    of {path, mechanism, post_write_sha256} PLUS a byte-exact SHADOW copy of the
    framework-authored content of each mutated file. The recorded mechanisms are:
        - php_fixer            use-header rewrites when a framework file imports
                               an overridden class (App\RSpade\... -> Rsx\...)
        - class_override_rename / selfheal / restore
                               the .php.upstream rename pair for class overrides
        - composer_dump        vendor/composer/ classmap regeneration
        - model_codegen        model docblock regeneration
        - file_write           the generic content-write choke point

    The one gate rule (no special cases):
        expected(path) = the shadow copy if a marker exists, else the
                         release-inventory pristine content.
        Tamper iff sha256(disk) != sha256(expected).
    A .php.upstream rename expects the original path ABSENT and the .upstream
    file present with the marker-recorded content. An untracked extra file under
    an owned zone (not a marker, not a .upstream) is tamper - it would otherwise
    be silently deleted by the sync.

    Classification and exit:
        - Mismatch/extra under an OWNED zone -> UNAUTHORIZED. Aborts the pull
          (exit 1) unless --force; overwritten by the owned-zone sync.
        - MISSING under an owned zone -> reported and RESTORED by the sync. Never
          aborts: there is no content to destroy (see RESTORE IS NOT AN OVERRIDE).
          rsx:framework:verify still lists it as unauthorized, because as a
          read-only integrity report "the release ships this and it is not here"
          is exactly what you want to see.
        - Mismatch anywhere ELSE in system/ -> LOCAL CHANGE. Allowed; handled by
          the three-way pass, reported, never blocks.
        - Any of the above whose path git reports as IDENTICAL to the committed
          state -> COMMITTED DRIFT. Reported, never blocks (owner ruling
          2026-08-05): the change is already committed, so the rsx:clean reset
          restores exactly what is on disk and history holds it. Untracked and
          IGNORED files are not committed and keep flagging. When git cannot
          answer at all (not a repo, git absent), classification is unchanged.

    Why a file is flagged: it differs from BOTH the release and the framework's
    own recorded output for it, i.e. something other than the framework wrote it.
    `--diff-system-changes` shows precisely those lines.

    Reconciling the store on update (the prune, not a wipe). Once the owned-zone
    sync has restored a pristine tree, the update RECONCILES the marker store
    instead of blindly deleting it (`rsx:framework:prune_mutations`, step 5 above).
    Each marker is re-checked against disk and KEPT only while it is still true:
        - present marker -> keep iff its shadow exists AND sha256(disk) ==
          sha256(shadow) == post_write_sha256; otherwise drop it (and its shadow).
        - absent marker (a renamed-away .php) -> keep iff the file is still absent;
          drop it if the file reappeared.
    Why reconcile rather than wipe: a downstream box is LIVE - cron, workers and
    web requests boot artisan continuously, and each boot runs the dev auto-rebuild.
    A boot firing between the sync and the reset can legitimately re-apply the
    framework's own churn AND record it; a blind wipe would then destroy those valid
    records, and the pull's own idempotent rebuild - finding the churn already
    applied - would record nothing, leaving an EMPTY ledger that false-flags all of
    that churn on the next verify (the field failure that motivated the prune). A
    marker whose recorded content still matches disk is exactly as good as one the
    rebuild would have written, whenever it was written, so keeping it dissolves the
    race. Running the prune right after the sync shrinks (does not rely on) the
    window. The prune needs a working PHP; a --force repair on a broken tree
    degrades to the old wholesale reset (safe there - no concurrent boots are
    rebuilding, and the forced rebuild re-records from scratch).

UPDATE HISTORY FILE
    rsx/resource/framework_update_history.dat is committed and lives under rsx/,
    so the owned-zone sync and three-way pass NEVER touch it. Each update prepends
    a dated section, newest first. The first line of each section is
    machine-readable and is how the updater resolves "old" for the next changelog:

        ## RSPADE-UPDATE <ISO8601Z> from=<old_sha|BASELINE> to=<new_sha>
        Date: <human date>

        Changelog (<old12>..<new12>):
          <abbrev> <date> <subject>
          ...

        Files changed:
          <diffstat>

    IT IS A LOG, NOT STATE (2026-08-18). The installed release is resolved from ONE
    authority - system/.rspade-release.json - by matching its release_id against
    the cached distribution history; no match makes the run a BASELINE (no
    changelog; conservative three-way) and records a `from=BASELINE` section. The
    `to=` of the newest section here is READ for exactly one purpose: to WARN,
    naming both values, when it contradicts the marker. It decides nothing, and
    corrupting or deleting this file changes nothing else about a run.

    Why: the two files sit on opposite sides of the system/ boundary and therefore
    MERGE INDEPENDENTLY. A backwards merge took a peer's system/ (marker: the old
    release) while the app-tree history.dat kept ours (the current one). OLD_SHA
    came from the log, matched the distribution tip, the run reported "up to date"
    - and then the committed-baseline repair re-stated the tracked tree against the
    ON-DISK marker, untracking 7,503 paths including genuine newer-release files
    (Ascent, 2026-08-18). Two authorities that can disagree is not redundancy; it
    is a coin toss with no referee. The marker travels inside the tree it
    describes, so the marker wins.

SUBMODULE CONVERSION (one-time)
    Apps created before the vendored topology carried system/ as a git submodule
    of rspade_system. The FIRST `rsx:framework:pull` that runs the new script and
    detects a .gitmodules entry `path = system` offers a one-time conversion. It:
        - de-initializes and un-tracks the system/ submodule,
        - strips the submodule.system section from .gitmodules (removing the file
          if it becomes empty) and deletes .git/modules/system,
        - preserves a REAL system/.env (a symlinked one is recreated by env heal),
        - materializes the current release as ordinary files under system/,
        - recreates the system/rsx -> ../rsx symlink,
        - materializes system/ and lets the updater commit it (vendor/ and
          node_modules/ are included; the single large commit size is expected).
    Conversion requires explicit consent: interactive Y/n, or --yes when stdin is
    not a TTY. It runs in BASELINE mode (there is no old tree to compare against),
    so the three-way pass is conservative and never deletes; a
    `from=BASELINE` history section is written. The updater then commits the
    vendored system/ tree (see COMMIT MODEL).

BASELINE MODE
    A run is a baseline whenever the installed commit cannot be resolved (no
    history file, unknown release_id, or a fresh conversion). In baseline mode the
    updater has no "old" tree, so it cannot tell a local edit from an upstream
    one: it ADDS new files, leaves any file that differs from upstream untouched,
    keeps local-only files, and NEVER deletes. It records a `from=BASELINE`
    section; the next update has real history and reconciles normally.

STATUS AND VERIFY COMMANDS
    php artisan rsx:framework:status
        Reports the installed release (release_id + date from
        .rspade-release.json), the last update (newest history section), and
        update availability by fetching the cached distribution clone and
        comparing the installed commit against the tip (with a pending diffstat).
        Degrades gracefully offline / with no cache. On the framework-development
        tree (no .rspade-release.json) it prints "Not an installed release".

    php artisan rsx:framework:verify [--json] [--diff] [--base-dir=<dir>]
        The standalone tamper check the pull gate uses. Exit 1 iff there are
        unauthorized owned-zone findings; local changes elsewhere are a warning
        (exit 0), as is committed drift (a finding git reports as identical to
        HEAD). --json emits the machine shape (unauthorized / local_changes /
        framework_churn / committed_drift); --diff prints disk-vs-shadow diffs
        for marked files; --base-dir points the check at another tree (a test
        seam - the pull never uses it).

        Class-override artifacts never gate. The override machinery's own
        mutations - the `X.php` -> `X.php.upstream` rename pairs and the
        `use`-import rewrites pointing framework files at app override classes
        - are recognized by two independent layers: the marker ledger (primary,
        event-attested; self-heals every manifest build via the steady-state
        `.upstream` sweep), and a structural pass that authorizes them with no
        ledger at all: a rename pair passes iff the `.upstream` bytes are
        byte-identical to the pristine release file (sha256 vs inventory); a
        use-rewrite passes iff the file differs from pristine ONLY in plain
        `use` import lines (pristine bytes resolved by proof from the cached
        distribution clone, hash-validated, fail-closed). Authorized findings
        report as `[INFO] ... framework churn` (JSON key `framework_churn`)
        and never affect the exit code. Any non-import edit, or a `.upstream`
        that differs from pristine, is a real finding as before.

WHERE UPSTREAM HISTORY LIVES
    Two places, both real git history:
        - Your app repo: after your first update, `git log -- system/` shows the
          framework changes each update brought into your repository.
        - The distribution repo: full upstream framework history is browsable at
          git.internal.hanson.xyz/brianhansonxyz/rspade_system (the same repo the
          updater clones). The cached clone at /tmp/rspade_upstream.git also
          holds it locally, for as long as /tmp survives.

TROUBLESHOOTING
    "Unauthorized changes detected under framework-owned zones"
        You (or a tool) modified a file the framework owns exclusively. Inspect
        with `--diff-system-changes`. If the change was a mistake, discard it and
        re-run. If you truly mean to overwrite it with the release version, re-run
        with `--force` (it DESTROYS the local change). To keep framework
        customizations permanently, use a class override in rsx/ (rsx:man
        class_override) instead of editing app/RSpade directly, or fork the
        framework (rsx:man framework_fork).

    "N file(s) shipped in this release were MISSING from system/ - RESTORED"
        Framework files were not on disk and have been put back. Nothing is
        required of you; the message exists so a real loss is never silent. If the
        list contains migrations, run `php artisan migrate` - a box that lost them
        has been running a release of framework code against an older schema while
        `migrate` said "Nothing to migrate". Worth asking how they went missing: a
        `git clean -fd system`, a bad restore, or a merge with an environment a
        release behind (see rsx:man rsx_git).

    "N file(s) ... are OUTSIDE what this updater can restore"
        Advisory, never fatal. Either the release no longer carries those paths (a
        stale marker from a release whose inventory over-promised - harmless, and
        it clears on the next update) or they sit outside both the owned-zone sync
        and the three-way pass. If you deleted them deliberately, nothing needs
        doing; otherwise restore from your own history:
            php artisan rsx:git checkout -- system/<path>
        --force does not help here and does not claim to: it governs the tamper
        gate, not the sync's reach.

    "Cannot verify framework integrity - the framework may be broken"
        The verify command could not run (PHP will not boot, missing autoloader,
        etc.). This is exactly the repair case: re-run with `--force`. The
        owned-zone sync restores pristine framework files and the rebuild puts the
        tree back together. Never pass --force on an agent's behalf without the
        user's explicit permission.

    Three-way CONFLICT reported, file kept local
        Both you and upstream changed a non-owned system/ file. Your version was
        kept and the conflict was reported. Merge the upstream change by hand, or
        re-run with `--force` to take the upstream version.

    "Framework migrations FAILED"
        A framework migration errored during the rebuild; the full output is
        printed and the update is incomplete. Resolve the migration error and
        re-run `rsx:framework:pull` - the reconcile is idempotent.

    Offline / cannot reach the distribution repo
        `rsx:framework:status` shows the last cached state when the fetch fails.
        `rsx:framework:pull` needs to reach the distribution to fetch the new tip;
        run it where the repo is reachable.

    Forked-framework marker
        `.rspade-forked-framework` disables automatic updates. Remove it only if
        you intend to return to managed updates (rsx:man framework_fork).

FOR FRAMEWORK DEVELOPERS
    bin/publish generates system/.rspade-release.json (the release inventory) into
    every rspade_system release and vendors the freshly-published rspade_system
    tree into rspade_project's system/ as ordinary files (no `git submodule add`,
    no `rspade_upstream` remote wiring). The updater clones by URL. Keep
    OWNED_DIRS/OWNED_FILES in the pull script in lockstep with
    Framework_Mutations::owned_zones().
