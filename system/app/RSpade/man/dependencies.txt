NAME
    dependencies - layered dependency management for RSpade applications
    (rsx:composer and rsx:npm)

SYNOPSIS
    php artisan rsx:composer require <package>[:constraint] [flags]
    php artisan rsx:composer remove <package>
    php artisan rsx:composer provides
    php artisan rsx:composer <any composer command>

    php artisan rsx:npm install <package>[@version] [flags]
    php artisan rsx:npm uninstall <package>
    php artisan rsx:npm provides
    php artisan rsx:npm <any npm command>

DESCRIPTION
    An RSpade project is two layers of code that ship differently: the
    framework core in /var/www/html/system (vendored tracked files in your
    repo, maintained by rsx:framework:pull) and your application in
    /var/www/html/rsx (your own fork). Third-party dependencies follow the
    same split.

    The framework curates a committed base set - system/vendor (composer) and
    system/node_modules (npm) - and ships it to you already installed. You never
    run composer or npm inside system/; that directory is read-only, exactly like
    node_modules or the Linux kernel.

    Your application layers ADDITIONAL packages at the project root:

        /var/www/html/composer.json  ->  /var/www/html/vendor
        /var/www/html/package.json   ->  /var/www/html/node_modules

    rsx:composer and rsx:npm are framework-aware wrappers that manage that root
    layer for you. They exist so downstream applications have a supported,
    self-service way to add packages without ever touching the framework's own
    manifests.

    Unlike a stock Laravel project, where you have one composer.json and one
    node_modules and there is nothing above you, an RSpade app sits ON TOP of a
    framework that already supplies a large dependency set. The wrappers make
    that stack behave like one logical environment: the framework wins every
    name collision, packages the framework already provides are recorded rather
    than duplicated, and a framework update reconciles your layer automatically.

    NOTE ON THE TEMPLATE APP: this repository's own /rsx/ starter template keeps
    ZERO application-layer dependencies by rule - anything the template needs is
    added at the framework level. The commands documented here exist for YOUR
    downstream application, which is free to layer whatever it needs.

THE TWO LAYERS
    Framework layer (system/, read-only to you)
        Managed by the framework maintainer with plain `composer require` /
        `npm install` run inside system/. The resulting system/vendor and
        system/node_modules trees are committed and delivered to you by
        rsx:framework:pull. You consume them; you never install into them.

    Application layer (project root, yours)
        Managed EXCLUSIVELY by rsx:composer / rsx:npm. The root composer.json,
        package.json, and their lock files are part of your application - commit
        them alongside /rsx/. Packages you add here are additive on top of the
        framework set.

    Both layers coexist at runtime with no configuration on your part:

        PHP  - the framework's composer autoloader registers first, then
               system/bootstrap/app.php conditionally requires the root
               vendor/autoload.php if it exists. Framework classes resolve
               first; your app-layer packages fill in the rest.

        JS   - esbuild compiles bundles with cwd = system/, and Node's standard
               upward module walk resolves system/node_modules FIRST, then
               /var/www/html/node_modules. No NODE_PATH juggling is needed.

PRECEDENCE RULES
    The framework always wins. For any package present in both layers, the
    framework's copy is the one that loads (autoloader order for PHP, module
    resolution order for JS). This is why the wrappers refuse to install a
    duplicate of something the framework already provides - a second physical
    copy in your root tree would never be the one that loads, so installing it
    would only mislead you.

    Concretely, when you `require`/`install` a package the wrapper classifies it:

        1. On the framework's EXPOSED surface (see FRAMEWORK-PROVIDED PACKAGES):
           recorded as provided-by-framework. Nothing is installed.

        2. Installed in the framework tree but NOT exposed (an internal framework
           dependency): refused with guidance to request exposure.

        3. Neither: a genuine app-layer package. Installed for real at the root.

COMMANDS
    Both wrappers pass any command line through to the real tool unchanged.
    Read-only verbs (composer show/why/outdated/validate, npm ls/view/outdated,
    ...) run verbatim at the project root. Only the mutating verbs below are
    intercepted, plus the RSpade-specific `provides` verb.

  rsx:composer require <package>[:constraint] [flags]
    Add one or more PHP packages to the application layer.

    A genuinely new package is installed for real (after the replace map is
    regenerated so composer solves against the framework's pins):

        $ php artisan rsx:composer require league/csv
        ./composer.json has been updated
        Running composer update league/csv
        ...
        Package operations: 1 install, 0 updates, 0 removals
          - Installing league/csv (9.16.0)

    After this, `use League\Csv\Reader;` works from your /rsx/ code with no
    system/ changes.

    A package on the framework's exposed surface is RECORDED, not installed:

        $ php artisan rsx:composer require guzzlehttp/guzzle
        [OK] 'guzzlehttp/guzzle' provided by framework at 7.15.2 - recorded (nothing installed).

    An internal (installed-but-not-exposed) framework package is refused with no
    side effects:

        $ php artisan rsx:composer require symfony/console
        'symfony/console' is an internal framework dependency, not part of the supported surface.
        Open a request to the framework maintainer to expose it. (No changes made.)

    Requesting an exposed package with a constraint the framework's version does
    not satisfy also hard-fails (see CONSTRAINTS AND LIMITATIONS):

        $ php artisan rsx:composer require guzzlehttp/guzzle:^6.0
        'guzzlehttp/guzzle' is provided by the framework at 7.15.2, which does not satisfy your requested constraint '^6.0'.
        Require it without a version constraint to accept the framework's version, or open a request to the framework maintainer.

    If several packages are named at once, validation runs FIRST across all of
    them; if any one is refused, nothing is recorded and nothing is installed.

  rsx:composer remove <package>
    If the package is a provided-by-framework recording, the recording is
    removed:

        $ php artisan rsx:composer remove guzzlehttp/guzzle
        [OK] 'guzzlehttp/guzzle' provided-by-framework recording removed.

    Otherwise it is delegated to real `composer remove` at the root.

  rsx:composer install [args]
  rsx:composer update [args]
    Regenerate the replace map (keeping it current against the framework set),
    then pass through to composer at the root. Use `install` to materialize the
    root vendor tree from the committed lock file.

  rsx:composer provides
    List the framework's exposed composer packages, the version the framework
    currently ships, and whether your app has recorded each:

        $ php artisan rsx:composer provides

        Framework-provided composer packages (requestable via rsx:composer require):

        +---------------------------------+-------------------+----------+
        | Package                         | Framework Version | Recorded |
        +---------------------------------+-------------------+----------+
        | ezyang/htmlpurifier             | v4.19.0           | no       |
        | giggsey/libphonenumber-for-php  | 9.0.11            | no       |
        | guzzlehttp/guzzle               | 7.15.2            | yes      |
        | laravel/framework               | v10.48.29         | no       |
        | nikic/php-parser                | v5.6.1            | no       |
        | sokil/php-isocodes              | 4.2.1             | no       |
        +---------------------------------+-------------------+----------+

  rsx:npm install <package>[@version] [flags]  (alias: i)
    The npm mirror of `rsx:composer require`. A new package installs for real at
    the root; an exposed package records; an internal framework package is
    refused. Aliases and messages match the composer side:

        $ php artisan rsx:npm install js-cookie
        added 1 package, and audited ... packages in 1s

        $ php artisan rsx:npm install dompurify
        [OK] 'dompurify' provided by framework at ^3.2.7 - recorded (nothing installed).

        $ php artisan rsx:npm install esbuild
        'esbuild' is an internal framework dependency, not part of the supported surface.
        Open a request to the framework maintainer to expose it. (No changes made.)

    With NO package arguments, `rsx:npm install` passes through to materialize
    the root node_modules from the lock file.

    A newly installed JS package still reaches the browser exactly as documented
    in `rsx:man npm`: declare it in an Asset Bundle's `'npm' => [...]` array. The
    esbuild resolution order (system/node_modules first, then the project root)
    means the bundle mechanism is identical regardless of which layer a package
    lives in.

  rsx:npm uninstall <package>  (aliases: remove, rm, un)
    Remove a provided-by-framework recording, or delegate to real npm uninstall:

        $ php artisan rsx:npm uninstall dompurify
        [OK] 'dompurify' provided-by-framework recording removed.

  rsx:npm update [args]
    Pass through to npm update at the root.

  rsx:npm provides
    List the framework's exposed npm packages, versions, and recorded status:

        $ php artisan rsx:npm provides

        Framework-provided npm packages (requestable via rsx:npm install):

        +------------------------+-------------------+----------+
        | Package                | Framework Version | Recorded |
        +------------------------+-------------------+----------+
        | dompurify              | ^3.2.7            | yes      |
        | google-libphonenumber  | ^3.2.42           | no       |
        +------------------------+-------------------+----------+

FRAMEWORK-PROVIDED PACKAGES
    Some framework dependencies are useful enough to application code that the
    framework formally EXPOSES them: you may depend on them, and the wrapper
    records that dependency instead of installing a duplicate.

    The exposed lists live in config/rsx.php under the `dependencies` key:

        'dependencies' => [
            'exposed_composer' => [
                'laravel/framework',
                'guzzlehttp/guzzle',
                'giggsey/libphonenumber-for-php',
                'ezyang/htmlpurifier',
                'sokil/php-isocodes',
                'nikic/php-parser',
            ],
            'exposed_npm' => [
                'dompurify',
                'google-libphonenumber',
            ],
        ],

    Recording semantics
        Requiring an exposed package writes a declaration - the package name and
        the framework version at the time of recording - into your root manifest:

            composer.json   ->  extra.rsx.provided
            package.json    ->  rsx.provided

        Nothing is installed; the framework's copy already loads. The recording
        is a declared coupling: it states "my application relies on this
        framework-provided package," which is exactly what the reconciler reads
        after a framework update (see POST-UPDATE RECONCILIATION).

    The forever-commitment posture
        Exposing a package is a standing commitment. An exposed package is
        expected to remain available indefinitely at a compatible major version -
        default tooling exists forever. If a breaking change or a retirement ever
        does happen, it is not silent: it ships with an upstream_changes document
        (Category 2 - see `rsx:man upstream_changes`), and the post-update
        reconciler surfaces it against your recorded dependencies. You inherit
        the framework's upgrade cadence for these packages, but you are never
        surprised by it.

THE REPLACE MAP
    The root composer.json carries a large auto-generated "replace" map: every
    package in system/vendor/composer/installed.json listed at its exact version.
    This is composer's own documented mechanism for telling the solver "these are
    already supplied - do not install them again." It lets an app-layer
    `composer require` resolve against the framework's pinned versions without
    duplicating any package, and makes an incompatible app-layer demand fail
    loudly at solve time instead of silently double-installing.

    The replace map is MACHINE-GENERATED and MUST NOT be hand-edited. The
    wrappers regenerate it before every real install/update, and the post-update
    reconciler regenerates it after every framework pull. Any manual edit is
    overwritten on the next of those events.

POST-UPDATE RECONCILIATION
    Every successful `php artisan rsx:framework:pull` runs a reconciler at the
    end (the hidden internal command rsx:framework:post_update_dependency_check;
    you never invoke it directly). It is PURELY LOCAL and does no network access,
    so a pull stays offline-capable. It does two things:

    1. Regenerate the replace map against the possibly-updated framework set. If
       it changed, that is routine information, not a warning:

           Framework dependency baseline refreshed (app-layer composer replace map regenerated).

    2. Cross-check every package you recorded as provided-by-framework against
       what the framework now ships. Two problems produce a notice; both are
       findings, never a failing exit code:

       removed - the framework no longer provides a package you recorded:

           The framework no longer provides 'sokil/php-isocodes' (you recorded it at 4.2.1). Run: php artisan rsx:composer require sokil/php-isocodes  to adopt it into your application layer.

       major_change - the framework moved a recorded package across a major
       version boundary (the only drift a forever-commitment posture treats as
       potentially breaking):

           Framework-provided 'guzzlehttp/guzzle' moved 7.15.2 -> 8.0.0 (major version change). Review your usage; see pending upstream_changes documents. Re-record with: php artisan rsx:composer require guzzlehttp/guzzle

    npm recordings are checked the same way; the remedy command in an npm notice
    is `rsx:npm install <package>`. When everything is clean and the map did not
    change, the reconciler is completely silent (no news is good news).

VERSION CONTROL GUIDANCE
    Downstream applications:

    ALWAYS commit your root manifests and lock files:

        /var/www/html/composer.json
        /var/www/html/composer.lock
        /var/www/html/package.json
        /var/www/html/package-lock.json

    They ARE your application's dependency layer - the reconciler and the wrappers
    read and rewrite them, and they must travel with your /rsx/ code.

    Committing the installed trees themselves - /vendor and /node_modules - is
    RECOMMENDED, consistent with the framework's own commit-everything philosophy
    (the framework commits system/vendor and system/node_modules for exactly this
    reason: reproducible, network-independent deployments). It is, however, YOUR
    application team's choice; if you prefer to rebuild them from the committed
    lock files (`rsx:composer install`, `rsx:npm install`) at deploy time, that is
    a supported workflow too. The manifests and locks are non-negotiable; the
    trees are your call.

CONSTRAINTS AND LIMITATIONS
    Single-class-load reality (PHP)
        PHP loads exactly one class of a given name per process. For any
        framework-provided package the framework's copy is the one that loads,
        so you cannot pin a DIFFERENT version of an exposed package in your app
        layer - you inherit the framework's version and its upgrade cadence,
        period. This is not a wrapper limitation; it is how PHP autoloading
        works. The recording mechanism makes that inheritance explicit rather
        than pretending you have independent control.

    Internal framework dependencies are not requestable
        A package that is installed in the framework tree but NOT on an exposed
        list is an internal implementation detail. The wrapper refuses it rather
        than let you couple to something the framework has not committed to keep
        stable. If you genuinely need one, open a request to the framework
        maintainer to add it to the exposed list; do not work around the refusal.

    Exotic version constraints on exposed packages hard-fail
        When you request an exposed package WITH a version constraint, the
        wrapper checks the framework's installed version against it. A constraint
        the framework version does not satisfy - or an exotic constraint the
        checker cannot evaluate - hard-fails with guidance to install unpinned
        (accept the framework's version) or open a request. Requesting an exposed
        package WITHOUT a constraint always accepts the framework's version and
        records cleanly.

TROUBLESHOOTING
    "'X' is an internal framework dependency, not part of the supported surface."
        You tried to require/install a package the framework has installed but
        has not exposed. It is not requestable by design. Either you do not
        actually need it (the framework already uses it internally and its
        classes are on the autoloader), or you should open a request to the
        maintainer to expose it. Do not attempt to install a second copy at the
        root - the framework's copy is the one that would load anyway.

    A real install fails with a solver / dependency conflict
        Your genuinely-new app-layer package demands a version of something the
        framework already pins (via the replace map) that is incompatible with
        the framework's version. Composer reports this at solve time as a version
        conflict. Options: choose a version of your package compatible with the
        framework's pins; drop the conflicting requirement; or, if the conflict
        is over a package that SHOULD be shareable, open a request to expose (and
        possibly bump) it at the framework level. There is deliberately no way to
        force a second, conflicting copy to load past the framework's.

    "The framework no longer provides 'X' ..." after a pull
        A framework update removed a package you had recorded as
        provided-by-framework. The reconciler is telling you to adopt it into
        YOUR layer: run the `rsx:composer require X` (or `rsx:npm install X`)
        command it prints, which installs a real app-layer copy now that the
        framework no longer supplies one. Check for an accompanying
        upstream_changes document describing the change.

    "Framework-provided 'X' moved A -> B (major version change)" after a pull
        The framework bumped a recorded package across a major version. Review
        your usage of it, read the pending upstream_changes document that
        accompanies the change, and re-record against the new version with the
        printed `rsx:composer require X` / `rsx:npm install X` command once you
        have verified your code against the new major.

    "'X' provided by framework ... does not satisfy your requested constraint"
        See CONSTRAINTS AND LIMITATIONS. Require the package without a version to
        accept the framework's copy, or open a request to expose a different
        version.
