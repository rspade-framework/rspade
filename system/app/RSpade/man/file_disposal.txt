NAME
    file_disposal - time-delayed file disposal: retention window, recovery API,
    scheduled destruction, and orphan sweeps for file attachments

SYNOPSIS
    // Delete = enter the retention window (recoverable), NOT immediate destruction
    $attachment->delete();

    // Recover within the window
    $model->get_deleted_attachments('documents');   // this model's recently-deleted
    File_Attachment_Model::get_deleted_files($fileable, $category);
    $attachment->undelete();                          // restore (throws once destroyed)

    // Out-of-band immediate erasure (GDPR / rollback)
    $attachment->force_destroy();

DESCRIPTION
    Deleting a file attachment never immediately destroys the bytes. RSpade's file
    layer runs a three-state lifecycle:

        live  ->  deleted_at (recoverable)  ->  destroyed_at (tombstone)

    delete() SOFT-deletes the attachment into a RETENTION WINDOW: it stays in the
    database (SoftDeletes; the fileable link is kept) and its deduplicated backing
    blob is preserved, but it drops out of normal queries. It is recoverable via
    undelete() for rsx.files.deleted_retention_days (default 30). After the window,
    the daily disposal task permanently DESTROYS it - stamping destroyed_at (the row
    PERSISTS FOREVER as an audit tombstone, only its claim on the blob released) and
    releasing the blob once no attachment still pins it.

    Unlike Laravel, where deleting a model deletes the row, an RSpade file delete is
    always a reversible retention step; permanent destruction is a separate,
    scheduled, hook-gated act. App code should NEVER hard-delete an attachment or a
    blob - delete() means "enter retention"; force_destroy() is the only immediate
    erasure and is reserved for GDPR-style requests and internal rollback.

RETENTION-AWARE REFCOUNT
    The blob store is content-deduplicated: many attachments may share one
    File_Storage_Model blob. A blob is PINNED by any attachment that is LIVE or
    SOFT-DELETED-BUT-NOT-DESTROYED. Only once EVERY attachment referencing a blob is
    destroyed are the bytes released. A recoverable (retained) attachment therefore
    keeps its blob alive - "release the last reference" counts retained references,
    not just live ones. Any refcount query uses
    withTrashed()->whereNull('destroyed_at').

RECOVERY API
    File_Attachment_Model::get_deleted_files($fileable = null, $category = null)
        Static. The attachments currently in the retention window (soft-deleted, not
        destroyed), tenant-scoped, optionally narrowed to a fileable owner and/or a
        category. The enumeration a "Recently Deleted" UI is built on.

    $model->get_deleted_attachments(string $category)
        On any Rsx_Model_Abstract: this model's recently-deleted attachments in a
        category (the companion to get_attachment()/get_attachments()).

    $attachment->undelete(): void
        Restore out of the retention window (clears deleted_at). THROWS if the
        attachment has already been permanently destroyed, or if its backing bytes
        are gone.

    $attachment->force_destroy(): void
        Permanently destroy NOW, bypassing BOTH the retention window and the
        destroy.hold gate. Stamps deleted_at + destroyed_at (the tombstone row
        persists) and releases the blob immediately if nothing else pins it. Does
        NOT fire the file.attachment.destroyed hook (out-of-band erasure, not the
        scheduled lifecycle).

DESTRUCTION HOOKS (app integration seam)
    The daily destroy pass fires two events per attachment, in the framework event
    vocabulary (see rsx:man event_hooks). Register handlers with #[OnEvent].

    file.attachment.destroy.hold  (a GATE, before stamping)
        Uses the framework gate convention: a listener returns TRUE to PERMIT
        destruction; ANY non-true value HOLDS the attachment (skipped this run,
        re-examined next run). Use for a legal hold, an in-flight operation still
        referencing the blob, an export mid-stream. NOTE: this is the inverse of the
        "return true to hold" phrasing some designs use - here true = allow, matching
        every other RSpade gate (e.g. file.download.authorize).

    file.attachment.destroyed  (an ACTION, after stamping, per attachment)
        Payload = the attachment row. Fired OUTSIDE the blob-lock critical section. A
        THROWING listener ABORTS that one attachment's destruction (row left
        un-stamped, retried next run) - destruction never half-happens relative to an
        app integration. Handlers must be idempotent (a retry re-fires).

SCHEDULED TASKS (File_Disposal_Service)
    All #[Exclusive]; every blob-touching pass serializes on the shared
    RsxLocks::named_write_lock('FILE_BLOB_DISPOSAL') so no two can interleave a
    refcount check with another's unlink. That is a WEB-CLUSTER lock (the blob store
    is shared across the fleet, so a box must not unlink a blob another box just
    referenced) held for the whole pass, however long it runs - see `rsx:man locks`. All are keyset-paginated for bounded
    memory over hundreds of thousands of rows.

    sweep_unclaimed_uploads   #[Schedule('every 6 hours')]
        The CLAIM WINDOW. An upload arrives UNATTACHED and is reachable only by its
        unguessable key until app code claims it with attach_to()/add_to(); this task
        bounds how long that key stays useful. Anything still unattached past
        config('rsx.attachments.unattached_claim_window_hours') (default 24) is
        SOFT-deleted - it enters the ordinary retention window (recoverable via
        undelete(), blob still pinned), never destroyed outright. Never touches:
        attached rows, handler-backed (WP-A) rows, rows already soft-deleted. A
        window of 0 (or null) disables the sweep.

        This is the successor to the bound the retired _file_attachments.session_id
        stamp implied. Claimability is now a property of the attachment (unclaimed +
        same site), so the window is what keeps an abandoned key from lingering
        indefinitely. See rsx:man file_upload (THE CLAIM WINDOW).

    run_daily_disposal   #[Schedule('0 2 * * *')]
        (a) DESTROY pass: attachments with deleted_at older than the retention window
            and destroyed_at NULL -> destroy.hold gate -> destroyed action -> stamp
            destroyed_at.
        (b) BLOB-RELEASE pass: for blobs referenced by attachments destroyed within
            rsx.files.disposal_lookback_days (default 60), recompute the
            retention-aware refcount and release at zero (unlink the blob + its
            rendition + thumbnail caches; the search-index row cascades on the storage
            delete).

    run_monthly_deep_sweep   #[Schedule('0 2 * * 0')] + first-Sunday guard
        Classic cron cannot express "first Sunday", so it fires every Sunday and
        returns early unless the day-of-month is 1..7. Full reconciliation, no time
        window: (a) release every storage blob with a zero retention-aware refcount;
        (b) stream-walk blob_root() and unlink files older than
        rsx.files.disk_orphan_min_age_days (default 14) that have no storage row (the
        age guard protects a just-written blob whose row commits after the file
        lands); (c) soft-delete stale plain-local unassigned uploads. External (WP-A
        handler-backed) attachments and their bytes are never swept.

    run_monthly_deep_sweep accepts ['force' => true] to bypass the first-Sunday guard
    for a manual or test run: rsx:task:run File_Disposal_Service run_monthly_deep_sweep.
    Note its unassigned-upload pass (c) uses the much older disk_orphan_min_age_days
    bound; the 6-hourly claim-window sweep is the tight one, and the monthly pass is
    the backstop that also reconciles blobs and disk.

CONFIG (config('rsx.files.*'))
    deleted_retention_days     30   recoverable window before permanent destruction
    disposal_lookback_days     60   blob-release pass window (daily task)
    disk_orphan_min_age_days   14   age guard for the monthly disk / unassigned sweep

CONFIG (config('rsx.attachments.*'))
    unattached_claim_window_hours
                               24   how long an UNATTACHED upload stays claimable
                                    before sweep_unclaimed_uploads soft-deletes it;
                                    0/null disables the sweep

INTERACTIONS / PITFALLS
    - delete() is a SOFT delete. SoftDeletes installs a global scope, so ordinary
      File_Attachment_Model queries exclude retained rows; use withTrashed() to see
      them. Refcount checks MUST use withTrashed()->whereNull('destroyed_at').
    - A destroyed attachment is a TOMBSTONE: the row persists with its metadata, its
      file_storage_id nulled (the FK claim released so the blob's storage row can be
      deleted).
    - A migration that creates attachments via the model must run AFTER the retention
      columns exist - adding SoftDeletes made deleted_at load-bearing at model boot.
    - Rejected uploads (create_from_upload strict reject) use force_destroy(), never a
      plain delete(), so a bad upload never lingers in retention.
    - CLI tools rsx:file:delete and rsx:storage:cleanup are explicit admin erasures:
      they force_destroy() / route through the retention-aware release, not delete().
