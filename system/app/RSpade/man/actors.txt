ACTORS(7)                    RSpade Framework Manual                    ACTORS(7)

NAME
actors - the actor model layer: who signs in, who stamped a record, and how their
name and profile link are produced

SYNOPSIS
    // A model that signs in or can be named in an audit column
    class Contractor_Model extends Rsx_Site_Actor_Model_Abstract
    {
        public function get_printed_name(): string { ... }
        public function get_view_profile_url(): ?string { ... }
    }

    // Server side: resolve authorship for display
    $data['get_created_by_author'] = $record->get_created_by_author();

    // Client side: render it
    <Record_Author $author=this.data.record.get_created_by_author />

DESCRIPTION
An ACTOR is anything that can sign in or stamp authorship - the entity a
created_by_id/created_by_type or updated_by_id/updated_by_type pair points at.

Every RSpade table carries those two polymorphic pairs, and Rsx_Model_Abstract::save()
fills them automatically (see the stamp matrix in rsx:man model_normalization). That
makes "who wrote this?" answerable on any record in the system. The actor layer is the
other half of the deal: it guarantees that whatever the pair points at can always answer
"what is your name?" and "where can this viewer see you?".

The framework ships three actors:

    User_Model          a staff membership in one site       (site-scoped)
    Portal_User_Model   a client-portal account, per site    (site-scoped)
    Login_User_Model    the cross-site login identity        (NOT site-scoped)

They stay separate identities on purpose - a staff person and a portal client are not
the same kind of thing, and consolidating them would flatten a real distinction.
Authorship is polymorphic instead.

RSX PHILOSOPHY
The problem the layer solves is one nobody notices until it bites. A record says it was
created by "type 2, id 17". Some screen wants to print that. Without a shared contract,
every screen invents its own resolution - one reads first_name/last_name, another falls
back to email, a third hard-codes a link to a page the viewer may not be allowed to see,
and a fourth crashes the day someone deletes a user.

RSpade answers it the way it answers everything else: ONE way to do it, declared once, on
the model. Extend an actor abstract and you inherit soft deletes, you are forced to
implement two methods, and every authorship display in the application - including the
framework's own <Record_Author> widget - works for your model with no further wiring.

Compare with Laravel, which has no notion of this at all: authorship is
`$table->foreignId('created_by')`, a belongsTo to whatever the app's User model happens
to be, and the display is whatever each Blade file feels like doing.

THE TWO ABSTRACTS
Actors do not share one base class, because staff and portal users are site-scoped while
the login identity is deliberately cross-site, and PHP has no multiple inheritance. So
there are two:

    Rsx_Actor_Model_Abstract        extends Rsx_Model_Abstract
    Rsx_Site_Actor_Model_Abstract   extends Rsx_Site_Model_Abstract

Choose by the TABLE's shape, never by taste:

    the table has site_id       ->  Rsx_Site_Actor_Model_Abstract
    the table does not          ->  Rsx_Actor_Model_Abstract

Extending the site abstract installs the site global scope, the forced site_id on write,
and the site write locks. Putting those on a cross-site identity table is wrong; omitting
them on a site-scoped table is a cross-tenant read leak.

The canonical contract docblock - the long-form version of this man page - lives on
Rsx_Actor_Model_Abstract. Rsx_Site_Actor_Model_Abstract points back at it.

There is NO shared interface. The manifest indexes classes, not interfaces, so an
interface here could not be imported by the code that needs it (the namespace linter
would strip the use statement). Code that must accept either kind tests both class names:

    if ($actor instanceof Rsx_Actor_Model_Abstract
        || $actor instanceof Rsx_Site_Actor_Model_Abstract) { ... }

SOFT DELETES ARE MANDATORY
Both abstracts `use SoftDeletes`, and the table must have a deleted_at column.

This is not a preference. An actor that could be hard-deleted would leave every audit
column that ever named it pointing at nothing, and no later code could recover the name -
the row is gone. Historical authorship must stay readable forever, so the identity row
stays forever.

Two mechanisms keep the mandate:

    $actor_soft_deletes     a #[Sealed] declaration on both abstracts. Redeclaring it in
                            a subclass - the natural way someone tries to opt out - is a
                            manifest-build FATAL (SEALED-01).

    ACTOR-01                a manifest rule that verifies every concrete descendant of
                            the actor layer still resolves the SoftDeletes trait, and
                            that every class the stamp can name extends the actor layer.

get_printed_name(): string
The human-readable name of this actor, for display anywhere authorship is shown.

    MUST return a non-empty string. There is no "no name" answer - a blank audit column
    is indistinguishable from an unattributed record. Cascade through what the model has
    (full name -> email -> a stable "User #17") but always return something.

    MUST work on a TRASHED record, without throwing and without going empty. That is what
    soft deletes are FOR.

    MUST render a deleted actor IDENTICALLY to a live one. Do not append "(deleted)",
    "(inactive)", or any marker. The model states the name and nothing else; a widget or
    screen that wants to decorate deleted authorship reads trashed() itself.

    MUST NOT perform authorization. A name is not a permission decision.

Example (User_Model):

    public function get_printed_name(): string
    {
        $full_name = $this->get_full_name();
        if ($full_name !== '') {
            return $full_name;
        }
        $email = trim((string) $this->email);
        if ($email !== '') {
            return $email;
        }
        $login_user = $this->login_user;
        if ($login_user) {
            return $login_user->get_printed_name();
        }
        return 'User #' . (int) $this->id;
    }

get_view_profile_url(): ?string
A URL where the CURRENT VIEWER can see this actor, or null.

    MAY return null, and often should. Null means "there is no such page, or you may not
    see it". Callers render the printed name as plain text.

    MUST resolve permission through the auth gates, never a hand-rolled role test. The
    one call is:

        Auth_Gates::accessible_route($target, $realm, $params)

    which returns the URL when the surface exists in this install AND every gate declared
    ON THE DESTINATION passes for the current session - and null otherwise. So a link can
    never promise a page the viewer would be bounced from; adding a gate to the
    destination automatically tightens every link to it; and naming a screen a downstream
    app has removed degrades to plain text instead of throwing.

    MAY return a DIFFERENT URL per realm for the same record. Branch on
    Rsx_Portal::is_portal_request().

    MUST NOT be memoized on the instance. The answer is about who is ASKING, not about
    the record. Callers that need to avoid repeated resolution memoize per request AND
    per viewer - which is what get_created_by_author() does.

Example (User_Model): own record -> the profile screen every signed-in staff user can
reach; anyone else -> the user-management detail screen, which is gated
'can_manage_users'; portal realm -> null.

    public function get_view_profile_url(): ?string
    {
        if (Rsx_Portal::is_portal_request()) {
            return null;
        }
        if ((int) $this->id === (int) Session::get_user_id()) {
            $own = Auth_Gates::accessible_route('Settings_Profile_Display_Action', Auth_Gates::REALM_STAFF);
            if ($own !== null) {
                return $own;
            }
        }
        return Auth_Gates::accessible_route(
            'Settings_User_Management_View_Action',
            Auth_Gates::REALM_STAFF,
            (int) $this->id
        );
    }

WHAT THE FRAMEWORK ACTORS ANSWER TODAY
    User_Model
        name    full name -> email -> login identity's email -> "User #id"
        url     staff realm: own profile / user-management detail (gated)
                portal realm: null

    Portal_User_Model
        name    email -> "Portal User #id"  (portal_users has no name columns - the
                person's name is app data; an app override returns it)
        url     portal realm, own record: the portal account screen
                anything else: null (RSpade ships no per-portal-user staff screen)

    Login_User_Model
        name    email -> "Login User #id"
        url     null, permanently - there is no login-identity screen in RSpade

DISPLAYING AUTHORSHIP
Server side, on any model:

    $record->get_created_by_author()   ->  ['name' => string, 'url' => ?string] | null
    $record->get_updated_by_author()   ->  same

null means the record is unattributed (or the pair is half-set, which is hand-written
data the framework says nothing about).

Client side, the framework component:

    <Record_Author $author=this.data.record.get_created_by_author />

It renders the name, hyperlinked when url is non-null and plain text when it is null.
Content between the tags is the placeholder for a null author (default "Unknown"):

    <Record_Author $author=x>System</Record_Author>

Worked example - the template app's client view page:

    // rsx/models/client_model.php, inside fetch()
    $data['get_created_by_author'] = $client->get_created_by_author();

    <!-- rsx/app/frontend/clients/view/Clients_View_Action.jqhtml -->
    <span>Created <%= Rsx_Time.format_date(_client.created_at) %>
          by <Record_Author $author=_client.get_created_by_author /></span>

WHY IT IS EXPLICIT AND NOT AUTOMATIC
get_created_by_author() is asked for, not ridden along on every toArray(). Resolving an
author costs a query and discloses a name; doing it on every serialization would tax and
expose paths that never display authorship.

There is deliberately NO Ajax endpoint for "who wrote record X". That would be a new
identity-lookup surface over arbitrary records, gated by nothing the record's own fetch()
already decided. The controller or fetch() that already loaded the record asks for the
pair and ships it with the rest of the row.

The N+1 a list page would otherwise pay is absorbed by a per-request memo keyed on the
VIEWER plus the actor, so a datagrid of 200 rows written by 3 people costs 3 lookups -
and an identity switch inside one process (a test, a queued task) still gets fresh
answers.

ADDING YOUR OWN ACTOR
1. Table: give it deleted_at (plus site_id if it is tenant-scoped).
2. Model: extend the matching abstract; implement the two methods.
3. That is all. Soft deletes, the audit pairs, and <Record_Author> already work.

If you OVERRIDE one of the three framework actors (the standard class-override pattern -
a same-named class in rsx/models/ replacing the framework file), your replacement MUST
extend the same actor abstract. ACTOR-01 fails the manifest build if it does not, because
the stamp will still write that class name into audit columns and every authorship
display would then die at read time, far from the change.

#[Sealed]
A marker-only attribute (NEVER define the attribute class - the rule reads it by name
from the AST, per framework convention). Placed on a PROPERTY, it declares that property
the sole property of the class that declared it: no descendant may redeclare it, at any
depth.

    #[Sealed]
    public static bool $actor_soft_deletes = true;

PROPERTIES ONLY. Methods already have `final`, which PHP enforces itself; a second
mechanism there would be a dual implementation. PHP has no `final` for properties, so a
subclass can silently redeclare one and detach itself from a value the parent's logic
depends on. That is the gap #[Sealed] fills, and the only one.

What is flagged is a REDECLARATION - not reading, not writing. `static::$prop = x` is
untouched; `public static $prop = x;` in a subclass body is the violation. Redeclaring
with the same value is still a violation: the declaration lives in exactly one place.

Enforced by SEALED-01, a cross-file AST-based manifest-build rule. A violation is FATAL
and re-fires on every build until fixed. It honors @SEALED-01-EXCEPTION at file level and
on/above the offending declaration.

COMMON PITFALLS
Extending the wrong abstract. Pick by whether the table has site_id, not by whether the
model "feels" tenant-ish. Getting it wrong is either a broken cross-site identity or a
cross-tenant leak.

Returning an empty string from get_printed_name(). A blank name reads as "no author" on
every screen. Always fall through to something.

Adding "(deleted)" in get_printed_name(). Owner ruling: the model never decorates.
Decorate in the widget or the screen if you want it.

Memoizing get_view_profile_url() on the instance. Two viewers in one process get the same
answer, and one of them is wrong. Memoize per viewer or not at all.

Hand-rolling the permission test inside get_view_profile_url(). Use
Auth_Gates::accessible_route(); it reads the gates off the DESTINATION, so the link and
the page can never disagree.

Calling can_access() instead of accessible_route() for a screen that might not exist.
can_access() THROWS on an unknown target (correct for page code naming a surface it knows
is there); accessible_route() returns null (correct for framework code naming a screen a
downstream app may have removed).

Reaching for an Rsx_Actor_Model_Interface. There isn't one, on purpose - see THE TWO
ABSTRACTS above.
