NAME
    sms - Queue-based SMS delivery with dev-site safety and opt-out management

SYNOPSIS
    use App\RSpade\Core\Sms\Rsx_Sms;

    // Queue an SMS (transactional always delivers)
    Rsx_Sms::send('+15555550123', 'Your code is 4821', Rsx_Sms::TRANSACTIONAL);

    // Opt-out (STOP) management
    Rsx_Sms::block_all('+15555550123');            // block all non-transactional
    Rsx_Sms::block('+1555...', Rsx_Sms::MARKETING);
    Rsx_Sms::is_blocked('+1555...', Rsx_Sms::MARKETING);

DESCRIPTION
    The RSpade SMS system mirrors the email system (see man email): a one-call
    facade that QUEUES every message to the sms_queue table - never sends inline -
    plus a background task that drains the queue. It is framework-core
    infrastructure.

    ** REAL OUTBOUND DELIVERY IS NOT WIRED YET. ** Rsx_Sms::send() persists a queue
    row; the send task (Sms_Queue_Service::send_pending_queue) marks each pending
    message HELD_BACK - it records the intended SMS (the body is stored verbatim) for
    developer review or an app-side "SMS Transaction Log", and sends nothing to any
    provider. Wiring a real provider is on the backlog.

    Unlike email, SMS has no template/subject/rendered HTML - `body` is the content.

    Models (framework-core, overridable via the class-override pattern):
        App\RSpade\Core\Models\Sms_Queue_Model      - the queue
        App\RSpade\Core\Models\Sms_Recipient_Model  - per-number blocklist + stats

SENDING SMS
    Rsx_Sms::send($to, $body, $category = NOTIFICATION, $related_type = null,
                  $related_id = null): Sms_Queue_Model

        $to           destination phone number (E.164 recommended, e.g. +15555550123)
        $body         message text
        $category     TRANSACTIONAL | NOTIFICATION | MARKETING
        $related_*    optional polymorphic reference to what triggered the SMS

    send() resolves the site from the EXPERIENCE of the request - the staff Session
    site on a staff request or in CLI (site 0 when sessionless), the site the app
    declared for the portal on a portal request - enforces
    the blocklist for non-transactional categories, applies dev-site redirection,
    queues the row, and (on web requests) kicks a prompt background drain via
    Task::dispatch('Sms_Queue_Service','send_pending_queue').

    A sessionless send (from a #[Task] or CLI) resolves to site 0 (the Default site);
    call Session::set_site_id($site_id) first to target a specific tenant's
    blocklist/queue.

    The site is not cosmetic: it stamps the queue row AND drives the opt-out lookup
    (Sms_Recipient_Model::is_blocked($site_id, ...)). Asking the staff facade on a
    portal request would file the message under the wrong tenant and consult the
    wrong blocklist, so the resolution forks the same way Rsx_Mail's does.
    See: rsx:man portal (EXPERIENCE FORKS).

CATEGORIES
    TRANSACTIONAL (1)  Always delivers. Ignores opt-out preferences (codes, alerts).
    NOTIFICATION  (2)  Respects opt-out. Default.
    MARKETING     (3)  Respects opt-out.

    Constants: Rsx_Sms::TRANSACTIONAL / NOTIFICATION / MARKETING, matching
    Sms_Queue_Model::CATEGORY_*.

BLOCKLIST / OPT-OUT (STOP)
    Per-number preferences live in sms_recipients (unique per site_id + number).
    send() skips non-transactional SMS to opted-out numbers, recording a BLOCKED row
    for the audit trail.

        Rsx_Sms::block_all($number)          // STOP: block all non-transactional
        Rsx_Sms::block($number, $category)   // block one category
        Rsx_Sms::unblock($number, $category)
        Rsx_Sms::is_blocked($number, $category)

    A carrier "STOP" reply handler (app-side) should call block_all(); "START"
    should unblock. Transactional SMS is never blocked.

DEV SITE SMS SAFETY
    On dev sites (Rsx::is_dev_site()), outbound numbers are gated to prevent
    accidental delivery to real people, mirroring EMAIL_DEV_*:

        SMS_DEV_SUPPRESS_DELIVERY    render/record but never deliver
        SMS_DEV_NUMBER_WHITELIST     comma-separated numbers that deliver as-is
        SMS_DEV_CATCHALL_NUMBER      redirect everything else here (original captured
                                     in dev_original_to)

    With no catchall, messages stay queued but are not delivered. (Moot today - the
    send task holds everything back regardless.)

QUEUE PROCESSING
    Processed by the core Sms_Queue_Service task:

        php artisan rsx:task:run Sms_Queue_Service send_pending_queue

    #[Exclusive] (one drain at a time, coalesced) + #[Schedule('*/5 * * * *')] (every
    5 minutes). Requires cron:
        * * * * * cd /var/www/html && php artisan rsx:task:process

    Current behavior (until real send is wired):
    1. Picks up one PENDING record at a time (respects retry_at)
    2. Marks it STATUS_HELD_BACK ("Held (dev)") - recorded, NOT delivered.

    Status enum: 1 Pending, 2 Sending, 3 Sent, 4 Failed, 5 Blocked, 6 Held (dev).

    A second scheduled task prunes old terminal (sent/failed/blocked/held-back) rows:

        php artisan rsx:task:run Sms_Queue_Service cleanup

    #[Schedule('0 3 * * *')] (daily 3am). Deletes records older than 90 days (override
    with --days=N).

    FUTURE real-send + retry policy (documented in the send task; NOT implemented):
    attempt provider send; success -> mark_sent(); failure -> mark_failed(), where a
    provider *connect* error does not count toward the strike limit (retry no sooner
    than 5 min), a provider-returned error does, giving up after config('rsx.sms.
    retry_max') strikes (default 6). Needs a last_attempt_at column. See the backlog.

PROVIDER CONFIGURATION
    config('rsx.sms.*') - used ONCE real send is wired (not today):

        provider      the sending service. Common options:
                      twilio | aws_sns (Amazon SNS; also Amazon Pinpoint) |
                      vonage (ex-Nexmo) | messagebird (now Bird) | plivo | sinch |
                      telnyx | infobip | bandwidth. null/'log' keeps held-back.
        from_number   sending number / sender id
        credentials   provider-specific auth (Twilio SID/token, AWS key/secret/
                      region, Vonage key/secret, generic api_key/secret/token) - keep
                      secrets in .env
        retry_max / retry_backoff_minutes   retry policy for the real-send loop

SMS TRANSACTION LOG (read model)
    Sms_Queue_Model::fetch($id) (an #[Ajax_Endpoint_Model_Fetch], login-gated) loads
    one record for a developer-facing SMS log detail view - full fields, no aliasing,
    plus status_id__label/__badge and category_id__label/__badge.
