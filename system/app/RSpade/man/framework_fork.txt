# Forking the RSpade Framework

## NAME

framework_fork - Taking full ownership of the RSpade framework codebase

## SYNOPSIS

Breaking out of managed updates to directly modify framework code:

    # Mark framework as forked (disables rsx:framework:pull)
    touch .rspade-forked-framework
    git add .rspade-forked-framework
    git commit -m "Fork the RSpade framework"

    # Framework files are now yours to modify. Nothing else changes:
    # your repo already contains the entire framework under system/.

## DESCRIPTION

RSpade offers two development approaches:

1. **Managed** (default) - Framework files are maintained by
   `php artisan rsx:framework:pull`; edits under `system/app/RSpade/` are
   detected and overwritten on update
2. **Forked** - Automatic updates are disabled; the entire codebase is
   yours to modify and maintain

Because the framework is vendored - `system/` consists of ordinary tracked
files in your own application repository - your repo ALREADY contains the
full framework source, including `system/vendor/` and `system/node_modules/`.
Forking does not change your repository layout, add remotes, or switch
branches. It is purely a policy switch: the `.rspade-forked-framework`
marker tells the updater to stand down, and from then on the framework
files are simply more code in your repo.

## RSPADE'S RELATIONSHIP TO LARAVEL

RSpade is built within Laravel with minimal divergence:

- Laravel framework provides the foundation (Illuminate ORM, routing, etc.)
- RSpade-specific code isolated in `system/app/RSpade/`
- Application code lives in `./rsx`
- The surrounding Laravel structure is meant to be pristine and replaceable

**The abstraction:**
- VB6 apps run in the VB6 runtime, which runs in Windows
- RSX apps run in the RSpade runtime, which runs in Laravel

**Developer experience:**
For most developers, Laravel's existence is transparent. You work in
`./rsx`, use Laravel helpers where useful, and never touch files under
`system/`. Framework updates replace the framework-owned zones and
reconcile the rest (see rsx:man rsx_upstream).

**But you CAN break the abstraction - two tiers:**

Tier 1 (NO fork needed): local changes to `system/` OUTSIDE
`system/app/RSpade/` - `config/`, `app/Http/`, `routes/`, etc. The
updater's three-way reconcile preserves these across updates (kept when
upstream did not change the same file; conflicts are reported and kept
by default). You stay on managed updates.

Tier 2 (fork): modifying `system/app/RSpade/` itself. The updater treats
edits there as unauthorized (its tamper gate aborts, and `--force`
overwrites them), so owning RSpade core code means leaving managed
updates behind.

## WHEN TO FORK

**Stay managed if:**
- Building standard applications with RSX
- Want automatic framework updates
- Your framework-level needs fit outside `app/RSpade/` (tier 1 above)
- A core change you need could instead be requested upstream

**Fork if:**
- You need to modify RSpade core functionality permanently
- You are willing to merge upstream changes by hand from then on
- You have someone maintaining the framework modifications

**Critical decision point:**
Once forked, you own all framework changes. Upstream improvements require
manual review and porting. Reverting is possible but discards your core
modifications (see REVERTING TO MANAGED MODE).

## MANAGED VS FORKED

Managed (default):
    system/                        - Tracked files, maintained by rsx:framework:pull
    system/app/RSpade/ edits       - Detected by the tamper gate, overwritten on update
    system/ edits outside RSpade   - Preserved by the three-way reconcile
    Updates                        - php artisan rsx:framework:pull
    Update history                 - rsx/resource/framework_update_history.dat

Forked:
    system/                        - Tracked files, maintained by YOU
    Any framework edit             - Allowed and expected
    Updates                        - Manual (see UPDATING FROM UPSTREAM)
    rsx:framework:pull             - Refuses while the marker exists

## SETUP PROCEDURE

    touch .rspade-forked-framework
    git add .rspade-forked-framework
    git commit -m "Fork the RSpade framework"

That is the entire procedure. The marker:

- Disables `rsx:framework:pull` (it refuses with a clear error)
- Signals intentional framework ownership to teammates and tooling
- Lives at the project root (the updater also honors a copy at
  `system/.rspade-forked-framework`)

There is no branch to switch, no remote to add, and no nested repository
to manage.

## MAKING FRAMEWORK MODIFICATIONS

Edit anything under `system/` and commit as you would any other code:

    nano system/app/RSpade/Core/MyFeature/MyFeature.php
    git add -A
    git commit -m "Add MyFeature to RSpade core"

Notes for forked trees:

- The framework still rewrites some of its own files at rebuild time
  (Php_Fixer use-header rewrites, class-override `.php.upstream` renames,
  composer classmap regeneration). This churn is normal and harmless; it
  is the same machinery that runs in managed mode.
- `php artisan rsx:framework:verify` still works and is now your "what
  have I changed?" tool: it diffs the live tree against the last
  installed release inventory (`system/.rspade-release.json`), with
  legitimate framework churn subtracted. `--diff` shows the changed
  lines. This replaces digging through git history to reconstruct your
  divergence.

## UPDATING FROM UPSTREAM

Upstream continues releasing framework improvements. On a forked tree you
port them by hand. The upstream history lives in the rspade_system
distribution repository:

    ssh://git@git.internal.hanson.xyz/brianhansonxyz/rspade_system.git

### Reviewing what changed upstream

    # Clone the distribution once (or fetch an existing clone)
    git clone --bare ssh://git@git.internal.hanson.xyz/brianhansonxyz/rspade_system.git /tmp/rspade_system.git

    # Your installed baseline is recorded in the release inventory
    grep release_id system/.rspade-release.json

    # Browse upstream commits and diffs
    git --git-dir=/tmp/rspade_system.git log --oneline
    git --git-dir=/tmp/rspade_system.git diff <old_commit>..master -- app/RSpade/

### Porting changes

    # Take one upstream file verbatim
    git --git-dir=/tmp/rspade_system.git show master:app/RSpade/Core/Something.php \
        > system/app/RSpade/Core/Something.php

    # Or check out a full upstream tree and copy/diff selectively
    git clone /tmp/rspade_system.git /tmp/rspade_new
    diff -ru /tmp/rspade_new/app/RSpade/Core/Feature/ system/app/RSpade/Core/Feature/

    # After porting: rebuild and test
    php artisan rsx:check
    php artisan migrate --framework-only
    php artisan rsx:test --framework

Also review new mandates under `system/app/RSpade/upstream_changes/` when
porting - they describe required downstream actions that ship with
framework changes (see rsx:man upstream_changes).

## REVERTING TO MANAGED MODE

**WARNING: this discards your `system/app/RSpade/` modifications.**

    # 1. Commit everything (snapshot before the reset)
    git add -A && git commit -m "Pre-unfork snapshot"

    # 2. Remove the marker
    rm .rspade-forked-framework

    # 3. Pull with --force: restores pristine framework-owned zones,
    #    wiping core edits; your system/ edits OUTSIDE app/RSpade go
    #    through the normal three-way reconcile and survive where possible
    php artisan rsx:framework:pull --force

    # 4. Review and commit the result
    git status
    git commit -am "Return to managed framework updates"

Because everything was committed in step 1, your discarded modifications
remain recoverable from git history.

## DEPLOYMENT

Identical to a managed app: the repository is self-contained (framework,
`system/vendor/`, `system/node_modules/` all tracked), so a checkout plus
the standard build/serve setup is a complete deployment. There is no
separate framework install step in either mode.

## BEST PRACTICES

1. **Document every divergence** - keep a FRAMEWORK_CHANGES.md listing
   each core modification and why it exists.
2. **Minimize divergence** - prefer tier-1 changes (outside app/RSpade/)
   or an upstream feature request over forking.
3. **Use rsx:framework:verify** - run it before and after porting
   upstream changes to keep an exact picture of your divergence.
4. **Port upstream regularly** - the further you drift, the harder each
   manual merge becomes.
5. **Test after every port** - `rsx:check` plus the framework test suite
   (`rsx:test --framework`) catch most breakage immediately.

## TROUBLESHOOTING

### "Framework is in forked mode" error from rsx:framework:pull

The marker exists. If forking was unintentional:

    rm .rspade-forked-framework
    php artisan rsx:framework:pull

### Lost track of modifications

    php artisan rsx:framework:verify --diff

Shows every divergence from the installed release, with framework-authored
churn already subtracted.
