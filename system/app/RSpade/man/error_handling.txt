NAME
    error_handling - RSpade fail-loud philosophy and error primitives

SYNOPSIS
    shouldnt_happen("impossible condition");        // PHP and JS
    throw new Rsx_Caller_Exception("bad usage");    // report at caller
    throw new Rsx_File_Exception($msg, file: $f, line: $n);
    return response_error(Ajax::ERROR_NOT_FOUND, 'User not found');
    rsx_dump_die($value);                           // debug dump + halt

DESCRIPTION
    RSpade error handling is built on one rule: fail loud, never silent.
    Errors must be immediately visible during development instead of being
    swallowed by a fallback path that lets the program limp on with corrupt
    or unauthorized state. There is ONE deterministic way for an operation
    to work; when it can't, it throws.

    This page documents the framework error PRIMITIVES and the philosophy
    behind them:

    - shouldnt_happen()      - assert an impossible condition (both languages)
    - Rsx_Caller_Exception   - report the error at the CALLER's location
    - Rsx_File_Exception     - report the error at an arbitrary file:line
    - response_* helpers     - structured Ajax/web error responses
    - rsx_dump_die()         - debug dump that halts execution
    - the exception-handler chain that turns a thrown exception into a
      formatted response

    For the Ajax-specific error CONTRACT (the always-HTTP-200 response
    envelope, Ajax::ERROR_* codes on the wire, and every client-side
    display path), see:

        php artisan rsx:man ajax_error_handling

    This page covers the primitives and the philosophy; ajax_error_handling
    covers the request/response protocol. They are complementary, not
    duplicates.

CORE PHILOSOPHY
    Fail Loud, Not Silent
        - Errors surface immediately, at their true origin.
        - NO silent fallbacks, NO alternative code paths, NO "just in case"
          try/catch.
        - Exception handlers ONLY format an error for display. They never
          provide alternative functionality or a recovery path.
        - One deterministic way to do things - no redundant systems.

    No Silent Fallbacks (security-critical)
        Never continue after a security failure. Let the operation throw;
        do not catch it and substitute the raw input.

            // WRONG - unsanitized data continues after failure
            try {
                $clean = Sanitizer::sanitize($input);
            } catch (Exception $e) {
                $clean = $input;   // DISASTER
            }

            // RIGHT - fail loudly, let it throw
            $clean = Sanitizer::sanitize($input);

    No Defensive Coding for Core Classes
        Core framework classes (Rsx, Rsx_Manifest, Rsx_Storage, everything
        under app/RSpade/Core/Js/) are ALWAYS present - the build system
        guarantees it. Never guard their existence.

            // WRONG
            if (typeof Rsx_Manifest !== 'undefined') { Rsx_Manifest.define(); }

            // RIGHT
            Rsx_Manifest.define();

    When try/catch IS appropriate
        Catch only EXPECTED failures: file uploads, external API/network
        calls, user-input parsing. The catch block FORMATS the error - it
        never wraps a framework operation to hide it. Database and framework
        operations are never wrapped "just in case"; a schema error is a bug
        and must surface.

    These rules are mechanically enforced. rsx:check flags fallback/legacy
    naming (PHP-FALLBACK-01, JS-FALLBACK-01) and defensive existence checks
    for core classes (JS-DEFENSIVE-01). See: php artisan rsx:man code_quality

SHOULDNT_HAPPEN()
    Call shouldnt_happen() when the code reaches a condition that CANNOT
    occur if everything is working correctly - a broken assumption or
    corrupted state. Any time you would write a comment like "this shouldn't
    happen", call this function instead of silently returning or continuing.

    Behavior (PHP)
        Defined in app/RSpade/helpers.php:105. ALWAYS throws
        \RuntimeException. The message names the caller's file:line
        (path made relative to base_path()) plus the optional detail:

            Fatal: shouldnt_happen() was called at rsx/models/foo.php:42
            This indicates a sanity check failed - the code is not behaving
            as expected.
            Details: <your message>
            Please thoroughly review the related code ...

        The $message argument is optional; omit it and the "Details:" line
        is dropped.

    Behavior (JS)
        Defined in app/RSpade/Core/Js/error.js:44. Same message format,
        derived from the stack trace. Logs a boxed SANITY CHECK FAILURE
        block to the console, then throws an Error whose .name is
        'SanityCheckFailure'. (JS cannot halt the process the way PHP does,
        so it throws to break the current execution flow.)

    When to use
        - A class/file that must exist after a build step does not.
        - A DB lookup returns null for an id that session state guarantees.
        - A required array key is missing after validation already passed.
        - A component lifecycle invariant is violated.

    Examples
        // PHP
        $user = User_Model::find($user_id);
        if (!$user && $user_id > 0) {
            shouldnt_happen("User {$user_id} should exist per session data");
        }

        // JS
        if (!this.template_rendered) {
            shouldnt_happen('ready() called before template render');
        }

    Do NOT use shouldnt_happen() for expected failures (bad user input,
    missing permission, resource genuinely not found). Those are normal
    outcomes - use the response_* helpers or a domain check, not a sanity
    assertion.

RSX_CALLER_EXCEPTION
    App\RSpade\Core\Debug\Rsx_Caller_Exception extends \RuntimeException.
    It reports the error at the CALLER's location instead of where the
    exception is constructed. Use it in utility/helper methods where the
    bug is in how the caller USED the utility, not in the utility itself -
    so the stack-trace file:line the developer sees points at their own
    code.

    Constructor:
        new Rsx_Caller_Exception(
            string $message = '',
            int $frames_back = 1,   // 1 = immediate caller (default)
            int $code = 0,
            ?Throwable $previous = null
        )

    It walks back $frames_back frames and overrides the exception's file
    and line to the caller's. For a utility buried one extra call deep,
    pass $frames_back = 2 (etc.). If the target frame does not exist (a
    shallow stack), the file/line gracefully remain the construction site.

    Example (from Rsx::Route validation):
        // Thrown inside Rsx.php, but the error points at the blade/template
        // line that asked for a controller that does not exist.
        throw new Rsx_Caller_Exception("Class {$class_name} not found in manifest");

RSX_FILE_EXCEPTION
    App\RSpade\Core\Debug\Rsx_File_Exception extends \RuntimeException.
    It reports the error at an EXPLICIT file:line, different from where the
    exception is thrown. Use it when the error logically belongs to another
    file - a parsed template, a linted source file, a validated config -
    that your detecting code is inspecting.

    Constructor:
        new Rsx_File_Exception(
            string $message = '',
            int $code = 0,
            ?Throwable $previous = null,
            ?string $file = null,   // named args recommended
            ?int $line = null
        )

    Pass $file/$line as named arguments; they override the exception's
    file/line so error handlers (and the developer error preview) point at
    the real source location. Common uses: custom parser/linter syntax
    errors, template-compilation errors, config-file validation.

        throw new Rsx_File_Exception(
            "Unexpected token in template",
            file: $template_path,
            line: $token_line
        );

    Choosing between them:
        shouldnt_happen()     - an impossible internal state (always
                                RuntimeException; you did not expect to be
                                here at all).
        Rsx_Caller_Exception  - the immediate caller misused this code;
                                blame their line.
        Rsx_File_Exception    - the fault lives in a third file you are
                                processing; blame that file:line.

RESPONSE HELPERS
    For request handlers (Ajax endpoints and web controllers) the fail-loud
    equivalent of "throw" is RETURNING a structured error response. These
    helpers (app/RSpade/helpers.php) build an
    App\RSpade\Core\Response\Error_Response carrying an Ajax::ERROR_* code:

        response_error($code, $metadata = null)
            Base helper. $code is an Ajax::ERROR_* constant; $metadata is a
            string message or a structured array.

        response_form_error($message, array $field_errors = [])
            ERROR_VALIDATION with a summary $message plus per-field errors
            (['email' => 'Required']). The client applies each error to the
            matching form field.

        response_unauthorized(?$message)   ERROR_UNAUTHORIZED
            Authenticated but lacking permission. Context-aware: on a web
            request from a logged-OUT user it 302-redirects to login
            (threading the requested URL via Login_Redirect); logged-in but
            unpermitted yields 403; Ajax/API yields the JSON error.

        response_not_found(?$message)      ERROR_NOT_FOUND
        response_auth_required(?$message)  ERROR_AUTH_REQUIRED (not logged in)
        response_fatal_error(?$message, array $details = [])   ERROR_FATAL

    Ajax::ERROR_* constants (app/RSpade/Core/Ajax/Ajax.php):
        ERROR_VALIDATION     'validation'
        ERROR_NOT_FOUND      'not_found'
        ERROR_UNAUTHORIZED   'unauthorized'
        ERROR_AUTH_REQUIRED  'auth_required'
        ERROR_FATAL          'fatal'
        ERROR_GENERIC        'generic'
        ERROR_SERVER         'server_error'    (client-generated)
        ERROR_NETWORK        'network_error'   (client-generated)

    The same constants exist on the JS Ajax class, so client code branches
    on the code it receives:

        try {
            const project = await Project_Controller.get(id);
        } catch (e) {
            if (e.code === Ajax.ERROR_NOT_FOUND) { /* handle */ }
            else { throw e; }   // let the global handler flash it
        }

    Uncaught Ajax rejections are auto-logged and surfaced in a flash/modal
    by the global handler - so an endpoint returning response_error() never
    fails silently even when the caller writes no catch. The full envelope,
    every code, and every client display path live in ajax_error_handling.

    Permission facade throws instead of returns: Permission::require_role()
    / require_permission() throw AjaxUnauthorizedException (403) rather than
    returning a response - use them where a guard clause should abort. See
    php artisan rsx:man acls.

EXCEPTION HANDLER CHAIN
    A thrown exception becomes a formatted response through a config-driven,
    priority-ordered chain of responsibility - NOT scattered inline
    try/catch. Rsx_Exception_Handler (registered as Laravel's exception
    handler in bootstrap/app.php) reads config('rsx.exception_handlers'),
    sorts by each handler's get_priority() (LOWER number runs first), and
    calls handle($e, $request) on each until one returns a non-null
    response. If none responds, Laravel's default handling proceeds.

    Default handlers (config/rsx.php), by priority:
        10    Cli_Exception_Handler            terminal-formatted output
        20    Ajax_Exception_Handler           JSON error envelope
        25    Api_Exception_Handler            external-API error shape
        30    Playwright_Exception_Handler     plain-text test output
        1000  Rsx_Dispatch_Bootstrapper_Handler  404 -> RSX routing

    Every handler extends
    App\RSpade\Core\Exceptions\Rsx_Exception_Handler_Abstract. The chain
    validates each configured class exists AND is a subclass of that
    abstract, throwing a RuntimeException naming config/rsx.php otherwise
    (fail loud on misconfiguration).

    Extensibility: an app adds its own handler by appending its class to
    config('rsx.exception_handlers') with a priority that slots it into the
    chain. This is the sanctioned way to customize how exceptions render -
    the handler FORMATS the error for its context; it does not recover or
    reroute application logic.

DEBUGGING
    rsx_dump_die(...$values)
        The preferred temporary-debug primitive (app/RSpade/helpers.php,
        delegating to Debugger). Dumps each value with file:line location
        and a stack trace, then halts execution. Use liberally while
        debugging; remove when done. Never wrap it in try/catch - the whole
        point is that its output is unconditionally visible.

            rsx_dump_die($user);
            rsx_dump_die($request, $params, $result);

    console_debug($channel, ...$values)
        Channel-filtered debug output; stripped in production. See
        php artisan rsx:man console_debug.

RSX VS LARAVEL
    - Sanity assertions: shouldnt_happen() (throws \RuntimeException with
      caller location) instead of ad-hoc abort()/assert()/silent returns.
    - Error responses: return response_error(Ajax::ERROR_*, ...) instead of
      response()->json([...], 4xx). RSpade Ajax always returns HTTP 200 and
      encodes success/failure in the body (see ajax_error_handling); do not
      hand-set HTTP error status for Ajax.
    - Exception -> response: one config-driven priority chain over
      Rsx_Exception_Handler_Abstract instead of Laravel's render()/report()
      overrides scattered per exception type.
    - Blame-shifting exceptions: Rsx_Caller_Exception / Rsx_File_Exception
      relocate the reported file:line - Laravel has no built-in equivalent.

COMMON PITFALLS
    - Using shouldnt_happen() for EXPECTED failures (bad input, missing
      permission). Those are normal - use a response_* helper or a domain
      check. shouldnt_happen() is for the impossible only.
    - Catching an exception to substitute a default/fallback value. This is
      the exact anti-pattern the philosophy forbids; rsx:check flags the
      fallback/legacy variants of it.
    - Guarding core-class existence (typeof X !== 'undefined',
      class_exists('Rsx_...')). Core classes are guaranteed; JS-DEFENSIVE-01
      flags it.
    - Wrapping DB/framework operations in "just in case" try/catch. Let them
      bubble to the handler chain, which formats them properly.
    - Hand-setting HTTP 4xx/5xx on Ajax endpoints. Return response_error();
      the framework wraps it as HTTP 200 with a failure body.
