RSX_GIT(1)                          RSpade Manual                          RSX_GIT(1)

NAME
    rsx_git - a transparent git proxy that owns system/ safety and service quiescing

SYNOPSIS
    php artisan rsx:git <any git subcommand> [args...]
        [--rsx-raw] [--rsx-no-maint] [--rsx-include-system] [--rsx-help]

DESCRIPTION
    rsx:git is git. Every subcommand, flag, exit code, stdin, and TTY behavior (editors,
    pagers, interactive `rebase -i` / `add -p`) passes through unchanged. Only the
    --rsx-* flags below belong to the wrapper, and they are stripped before git sees
    them, so git's own --force / -f / --hard can never collide with one.

    What it adds is ownership of the things plain git cannot see on a downstream box.

WHY IT EXISTS
    Three processes mutate the working tree during any git operation on a live RSpade
    container, and plain git is defended against none of them:

    1. The container's fixperms loop chmods/chowns every newly created file - including
       files inside .git/ (objects, index, lockfiles) - racing git's own writes. This is
       also why every clone runs with core.fileMode false.
    2. The JIT manifest rebuild re-applies the class-override pass (.php <->
       .php.upstream renames, use-rewrites, composer autoloader regeneration) on ANY web
       request that touches the manifest, re-dirtying system/ within about a second of
       any clean.
    3. .git/index.lock contention from concurrent status/build processes.

    The consequence: system/ cannot be held clean for the instant a pull or merge needs
    it, so a pull carrying framework-update commits races and aborts. The escape used to
    be a hand-rolled dance (clear skip-worktree, checkout HEAD -- system, clean -fd
    system, merge in one command) re-derived by every agent, every time.

    rsx:git owns the invariant instead: THE APP NEVER SEES OR COMMITS system/ CHURN, AND
    TREE-REWRITING OPS RUN QUIESCED. One choke point, exactly as rsx:framework:pull owns
    the unsafe framework-update git dance.

    It is intercepted PRE-BOOT in system/artisan, so invoking it is never itself what
    triggers a manifest rebuild, it works on a broken or half-synced tree, and it runs
    while the maintenance gate is up. It appears in no `php artisan list` output - there
    is no Laravel command behind it.

TREATMENT BY SUBCOMMAND
    Four treatments. Anything not named here is plain git.

    PATHSPEC EXCLUSION - status, diff, add
        system/ and every submodule gitlink are excluded with a pathspec
        (`-- :/ ':(exclude,top)system' ...`), so GIT produces the output: native color,
        native pager, native exit codes, byte-clean --porcelain. The wrapper never
        filters a stream.

        The gitlink list is DERIVED at runtime from `git ls-files --stage` (mode
        160000), never hardcoded - each app has its own submodules.

        A human `status` prints a one-line stderr footer naming how many paths it hid.
        --porcelain and -z suppress every wrapper notice entirely.

    COMMIT - commit
        Any staged system/ path is unstaged first, whatever staged it. If that unstage
        FAILS (index.lock contention, essentially always) the commit is REFUSED and
        nothing reaches git - it used to warn and commit anyway, which reduced the first
        line of the one-writer defense to a suggestion. The operator's staging is left
        exactly as it was; retry the same command. `-a` is REWRITTEN,
        not decorated: pathspecs on `git commit` mean "commit ONLY these paths, bypassing
        the index", which is a different operation, so `-a` becomes an excluding
        `git add -u -- :/ <excludes>` followed by a plain commit. A short-flag cluster is
        parsed correctly: -am becomes -m, while -madd is left alone (that `a` is part of
        the message).

    MAINTENANCE CYCLE - pull, merge, rebase, cherry-pick, revert, checkout, switch,
    restore, clean, reset --hard|--merge|--keep, stash pop|apply
        rsx:maintenance:enable --reason="rsx:git <op>"
          -> clear skip-worktree on system/
          -> reset system/ to HEAD, then `clean -fdq -- system` (so incoming framework
             changes apply cleanly)
          -> PHASE 0 (pull/merge only): read the release marker on both refs and decide
             which side's system/ tree is the framework (see PHASE 0 below)
          -> run the operation (held open with --no-commit when Phase 0 decided), then
             restate the winning system/ tree wholesale and commit
          -> rebuild once (rsx:clean + rsx:manifest:build)
          -> pending-migration notice (advisory; silent when the schema is current)
          -> rsx:maintenance:disable

        The disable runs from an EXIT/INT/TERM trap, so a failure or a Ctrl-C never
        leaves maintenance stuck on. The rebuild happens BEFORE services return.

        THE RESET INCLUDES A CLEAN, AND DELIBERATELY CARRIES NO -x. `reset` and
        `checkout -- <path>` act on TRACKED paths only, so "reset system/ to HEAD" used
        to leave every UNTRACKED file in place - and an untracked file is exactly what a
        class-override sidecar is whenever the committed tree still names the file
        `X.php`. A peer's framework-update commit that TRACKS `X.php.upstream` then
        collided with it and git refused the whole merge ("untracked working tree files
        would be overwritten by merge"), deterministically on every re-run
        (2026-08-18). No `-x`: gitignored state under system/ - the .env deployment
        symlink, ignored build/vendor trees - is not churn and survives untouched, the
        same line rsx:clean's reset draws.

        A successful op ends with the same migrate:status_notice the framework
        updater prints - one line naming the pending-migration count and the
        command to run, nothing when there is nothing to run, and never a failure
        of the git operation.

        Ops that rewrite nothing are deliberately excluded: `checkout -b` / `switch -c`
        (a branch created at HEAD), a dry-run `clean`, `restore --staged` alone, and a
        plain `reset`. Stopping the world for those would be noise.

        A DRY RUN IS DETECTED IN EVERY SPELLING. The classifier compared whole
        arguments, so `clean -nd` - which is `-n -d` - was invisible and a preview took
        the full maintenance window and system/ reset. Short-flag CLUSTERS are now
        scanned letter by letter, and a letter that consumes the rest of its cluster as
        a VALUE ends the scan (`clean -e <pattern>`), so a pattern is never read as a
        flag.

    PASSTHROUGH - push, fetch, remote, tag, config, log, show, branch, blame, rev-parse,
    apply, and every subcommand the proxy has never heard of
        Remote and ref-only ops do not touch the working tree, so they cycle nothing.

        THE OPERATION RUNS FROM THE PROJECT ROOT. The project-root `artisan` shim does
        `chdir(__DIR__ . '/system')` before including the real one, so every
        `php artisan rsx:git ...` used to reach git with cwd = system/ no matter where
        the operator was standing - and git resolves a relative pathspec against cwd, so
        `rsx:git log -- rsx/foo.php` matched NOTHING and exited 0, a silent wrong answer
        from an audit command (2026-08-18). The shim's own chdir is undone; the project
        root is the anchor every relative pathspec a human types is written against. A
        cwd the caller genuinely chose (running the script directly) is preserved.

        log and show deliberately do NOT get the exclusion. They display COMMITS, not
        working-tree churn; filtering them would hide framework-update history, which is
        the opposite of helpful.

THE system/ RESET, AND ITS INTEGRITY GATE
    Before discarding drift, the proxy runs `rsx:framework:verify`. If system/ carries
    UNAUTHORIZED (hand-made) modifications it REFUSES the whole operation before touching
    anything, and points at `rsx:clean --force` as the deliberate discard. Silently
    throwing away a hand-edited framework file is exactly what that gate exists to
    prevent.

    Note the proxy performs the reset itself rather than calling rsx:clean. rsx:clean
    skips its own system/ reset whenever the maintenance flag is up
    (Clean_Command::framework_update_in_progress) - which is precisely the state the
    cycle is in.

PHASE 0 - THE FRAMEWORK RELEASE IS DECIDED BEFORE THE MERGE
    system/ is a vendored tree with exactly ONE writer (rsx:framework:pull), so which
    release it holds is a single fact - stamped in system/.rspade-release.json - not a
    per-file question a three-way merge is entitled to answer. On `pull` and `merge` the
    proxy reads that marker on BOTH refs before anything is merged:

        git show HEAD:system/.rspade-release.json          | sed -n 's/..."date"...'
        git show origin/master:system/.rspade-release.json | sed -n 's/..."release_id"...'

    One `git show` plus one `sed` per side. No checkout, no php. ISO-8601 UTC dates
    compare lexically, so the decision is a string comparison:

        newer date wins           that side's system/ tree is THE framework, wholesale.
        same release_id           nothing to decide about the release; the restate still
                                  runs (it is what erases a peer's stray deletions) and
                                  says NOTHING - a routine merge is not an event.
        equal date, different id  REFUSE AND ASK. Nothing can order two releases stamped
                                  at the same instant and the wrong guess loses one, so
                                  the operation aborts having changed nothing.
        marker missing/unparseable
                                  the tree cannot be decided: the operation runs as PLAIN
                                  git, with a loud warning saying so. Never a silent
                                  guess - and conflicts under system/ then reach you like
                                  any other conflict.

    THE RESTATE. The merge itself is held open with --no-commit, and before it is
    committed the winner's tree replaces system/ entire:

        git rm -r -q --cached -- system
        git checkout <winner> -- system
        git clean -fdq -- system            (NO -x: gitignored build/vendor state and the
                                             .env deployment symlink are not the release
                                             and are not ours to delete)
        git add -A -- system

    `rm --cached` drops every stage of an unmerged entry, so a conflict under system/
    needs no separate handling - it is discarded with everything else. The merge commit
    therefore carries ONE side's framework tree rather than a per-file blend of two.
    rsx/resource/framework_update_history.dat travels with it: it is an app-tree file
    that merges independently and can otherwise contradict the marker it describes.

    A fast-forward (and a rebase) leaves no merge to commit into, so a restate that
    actually changed something is committed on its own, the way the updater commits
    system/ (RSPADE_FRAMEWORK_COMMIT=1 + --no-verify).

    WHEN LOCAL WINS, THE STALE BOX IS NAMED. It will keep re-sending its old tree until
    somebody pulls there, so the committer of the newest system/-touching commit on the
    losing side is read and reported with the release and how far behind it is.

    WHAT THIS REPLACED. Until 2026-08-18 system/ conflicts were resolved per file to the
    "incoming" side (with a rebase --ours/--theirs inversion, and a patch that kept local
    content when incoming had none). All of it answered a whole-tree question one file at
    a time, and none of it could see the shape that actually loses code: a NON-conflicting
    incoming deletion, which git applies silently and no conflict resolver is ever invoked
    for. That shape cost framework files in the field on 2026-08-11 and moved a box back a
    full release on 2026-08-18.

A PULL IS SILENT ABOUT system/ FILE CHANGES.
    The framework SYNCS system/. A pull pulls in framework changes, and files appearing,
    changing and disappearing is what that looks like, so the proxy does not narrate
    them. It once did - classifying every deleted path against the release inventory, and
    naming every incoming system/ commit the updater had not stamped - and that was a
    monitor, not a protection: it spoke on the routine case (one peer's entirely correct
    update arrived as 617 deletions under a remedy that was a no-op) while changing
    nothing.

    The protection is on the WRITE side, where it belongs: the updater's commit is
    asserted against the release inventory before it lands (rsx:man rsx_upstream, COMMIT
    MODEL), `rsx:git commit` REFUSES rather than commit a staged system/ path it could
    not unstage, and the pre-commit hook backs both. `php artisan rsx:framework:verify`
    is the explicit, on-demand integrity audit for when an operator actually wants one.

A MERGE MAY NEVER MOVE THE INSTALLED RELEASE BACKWARDS - NOW A POST-CONDITION.
    After the operation the PRE-op release marker
    (`show <pre-op HEAD>:system/.rspade-release.json`) is still compared against the
    POST-op one on disk, and a demonstrably OLDER post-op marker is an ERROR naming both
    releases and their dates. No file list is consulted at any point.

    Since Phase 0 this is UNREACHABLE BY CONSTRUCTION: the winning release is chosen
    before the merge and restated after it. What it reports is therefore no longer "a
    peer sent an old tree" - it is "the reconciliation itself is wrong", which is a
    framework bug and deserves the same volume as the loss it used to catch. It costs two
    marker reads, so it stays on.

    Same release_id is no change; otherwise the ISO-8601 UTC `date` fields order the two
    markers by plain string comparison, and anything they cannot order reads as forward.
    An unreadable marker on either side says nothing: this is an invariant check, not an
    audit.

    The remedy, if it ever fires: `php artisan rsx:framework:pull --resync`, which
    restores the distribution tip without --force (rsx:man rsx_upstream).

    APP CONFLICTS HALT, WITH MAINTENANCE LEFT ON.
        This is the one deliberate exception to same-action-same-outcome: a real conflict
        in your own files is not scriptable. The proxy stops, lists the conflicted paths,
        and leaves the maintenance window UP - services are down specifically so the
        merge can be resolved without traffic hitting a half-merged tree.

        Services return when the merge lands:

            <resolve the files>
            php artisan rsx:git commit
            php artisan rsx:maintenance:disable

        rsx:maintenance:disable REFUSES while the repository has unmerged paths (it names
        them, and names --force). That single guard is what holds the halt in place - one
        mechanism, not two. A resolved-but-uncommitted merge is fine; only unmerged index
        entries block.

FAIL-OPEN
    This wrapper sits in front of every git call for every downstream app, so a wrapper
    bug must never brick git. Any unexpected internal failure falls through to plain git
    with the original argv. If maintenance mode cannot be raised, the git operation runs
    anyway with a warning. If the rebuild fails, it is reported and services still come
    back. The integrity gate above is the ONE place the proxy refuses instead of
    proceeding.

THE INDEX: ONE DELIBERATE REFRESH, AND NOTHING ELSE
    Every READ the proxy makes runs with --no-optional-locks. A plain `git status`
    refreshes and REWRITES the index, taking .git/index.lock to do it, so an unflagged
    probe makes the wrapper a contender against the very operation it is wrapping. See
    RESIDUALS for the measurement. Writes are unflagged, deliberately.

    Note the flag is not a blanket cure: git honours it for the status-shaped refresh,
    while `git diff` refreshes and writes the index regardless (git 2.43). The proxy
    passes it on both anyway - the point is to never be the one taking a lock it did not
    have to.

    That flag had a consequence nobody costed at the time: on a box whose ctimes churn (a
    fixperms loop, an inotify sweep), NOTHING refreshes the index any more, and it goes
    permanently stat-stale. A stale index is one half of `fatal: stash failed` (see
    RESIDUALS). So a tree-rewriting op now runs ONE deliberate

        git update-index --refresh -q

    before the caller's command, and only there. Its exit code is ignored: rc=1 only means
    genuinely modified files exist, and the clean entries were refreshed anyway. Reads
    still never write the index.

STASH-FAILED CLASSIFICATION AND RETRY
    The wrapper's own index-writing calls retry on lock contention with bounded backoff
    (5 attempts, ~0.2s to 0.8s apart), then give up loudly. Three wordings are classified
    as contention: `index.lock`, `Unable to write index`, and - conditionally - the
    generic `fatal: stash failed`.

    `stash failed` is CONDITIONAL because it has two causes wearing one message, and the
    difference decides whether retrying is sane:

        .git/index.lock EXISTS right now  ->  contention. Retry with backoff.
        no lock file                      ->  DETERMINISTIC. Retrying is pure delay;
                                              take the escape below instead.

    The proxy therefore looks at the lock file rather than trusting the wording, and never
    claims contention it did not observe. (It got this wrong once: a downstream box with no
    lock, no concurrent git and a clean status was told five times that another process
    held the lock. See RESIDUALS.)

    YOUR command is re-issued under exactly that classified contention: git aborted in its
    pre-merge save_state() because the internal `git stash create` lost the index.lock
    race. That failure happens before any work is done - no MERGE_HEAD, HEAD unmoved - so
    re-issuing is idempotent. It is gated twice: the classification must say contention AND
    git must have left no operation in progress, so a genuine conflict fails on attempt one
    and is never re-run behind your back. Nothing else is ever retried.

    While a tree-rewriting op runs, its stderr passes through a tee so the wrapper can
    classify it. stdout stays wired straight to the terminal (editors, pagers and git's
    own TTY detection are unaffected); the deliberate cost is that git suppresses its
    progress meters on those ops.

THE SCRATCH-WORKTREE ESCAPE (pull and merge)
    When the direct op is deterministically unable to run - `stash failed` with no lock,
    and git left no operation in progress - a pull or merge is not abandoned. It is done
    somewhere it works:

        git worktree add <tmp> -b rsx-git-escape-<pid> HEAD
        git -C <tmp> merge --no-edit --no-commit <ref>
                                                (Phase 0 decided the release before this,
                                                 and the winner's system/ tree is restated
                                                 in the scratch worktree exactly as it
                                                 would be here - the 2026-08-18 backwards
                                                 merge came through this path)
        git merge --ff-only rsx-git-escape-<pid>
        worktree removed, branch deleted

    A linked worktree has its OWN index and checks out no submodules, so the merge is
    unaffected by whatever this tree's index believes. The way home is a fast-forward,
    which takes git's checkout_fast_forward path and never calls save_state at all - so it
    lands even while this tree is dirty.

    The ref is resolved honestly: for `merge` it is the first positional argument (or the
    upstream branch for a bare `git merge`); for `pull` the fetch is re-issued with the
    pull's own positional arguments and FETCH_HEAD is read afterwards, so the escape can
    never merge a FETCH_HEAD left behind by an older fetch.

    Three outcomes other than success, all of which leave THIS working tree untouched:

    APP CONFLICT IN THE SCRATCH MERGE
        Reported by name and stopped. Unlike the normal app-conflict halt, maintenance
        comes DOWN: that halt exists so a conflict left in THIS tree can be resolved
        without traffic, and here the conflict went away with the scratch worktree.

    THE FAST-FORWARD IS REFUSED
        "Your local changes to the following files would be overwritten by merge" - the
        incoming change touches a file you have genuinely modified. This is the one case
        where "commit or stash first" is true advice, and it is the only place the proxy
        gives it.

    THE REF CANNOT BE IDENTIFIED
        The escape is not attempted, and says so.

    The cleanup (worktree removed, branch deleted) runs on every exit path. There is no
    second EXIT trap - the maintenance cleanup owns EXIT.

    One diagnostic rides along: if `git diff-index HEAD` reports ONLY gitlinks (`:160000`)
    while `git status` is clean, those submodule paths are named. That is dirt the merge
    machinery may count while `git stash create` cannot save it - reported as an observed
    fact when it is seen, never assumed.

OVERRIDE FLAGS
    --rsx-raw
        No exclusion. Show and stage the true tree including system/. For framework
        debugging: "what does git actually think is dirty?"

    --rsx-no-maint
        Skip the maintenance enable/disable pair. Use when you have already bracketed a
        batch of operations with your own rsx:maintenance:enable ... disable, or when you
        know the op is safe on a live box.

    --rsx-include-system
        Deliberately stage/commit a system/ change. For an intentional framework edit you
        mean to keep.

    --rsx-help
        Wrapper usage.

IN THE FRAMEWORK MONOREPO
    rsx:git is EXACTLY git: no exclusion, no maintenance cycle, no system/ handling, and
    nothing announced. There, system/ is the AUTHORED framework source rather than a
    vendored tree - hiding it from status, refusing to stage it, or resetting it to HEAD
    before a pull would destroy the work being done. Detected from
    IS_FRAMEWORK_DEVELOPER=true in .env.

    For the same reason the Claude Code redirect below is never installed there.

THE REDIRECT (downstream)
    system/bin/claude-git-guard.sh is registered as a Claude Code PreToolUse hook on Bash
    by environment_updates/040_claude_git_guard.sh. It blocks a bare `git` from the Bash
    tool and names the rsx:git equivalent. It matches `git` invoked as a COMMAND (at a
    statement start, allowing leading VAR=value assignments and sudo), so
    `php artisan rsx:git ...` and a `git` inside a quoted string pass through.

    Fail-open: any parse failure, a missing proxy script, or a monorepo checkout exits 0
    (allow). It supersedes the retired pre-pull guard, which told the agent to run
    rsx:clean and then pull - a sequence that DEADLOCKS on a live box, because the
    class-override churn reappears before the pull's index write can land. The installer
    removes that registration.

    KNOWN GAP: an IDE's internal git calls do not go through a shell and cannot be
    intercepted. A stray system/ churn line in the IDE's source-control panel is that,
    not a bug.

RESIDUALS - `fatal: stash failed`
    THE MECHANISM. A NON-FAST-FORWARD merge whose index does not match HEAD makes git's
    save_state() (builtin/merge.c) shell out to `git stash create`. When parent and child
    disagree about that index, the child fails - exit 1, empty stderr - and the merge dies
    with the generic `fatal: stash failed` having performed no work.

    THE 2x2, MEASURED ON GIT 2.43 (2026-08-12), with a genuinely clean worktree:

        stale index + lock held   ->  `fatal: stash failed`
        fresh index + lock held   ->  `fatal: stash failed`
        stale index, no lock      ->  the merge SUCCEEDS
        fresh index, no lock      ->  the merge succeeds

    Contention reproduces on demand: `git stash create` failed 29 times out of 40 while a
    concurrent index-refreshing reader ran, and 0 times out of 40 when that reader used
    --no-optional-locks. It is NOT the fixperms chmod loop - 0 failures out of 40 under
    induced chmod churn inside .git/, re-verified.

    TWO CLAIMS PREVIOUSLY MADE HERE WERE WRONG, AND ARE RETRACTED:

    "A clean worktree never reaches the stash path at all."
        False. The path is reached whenever git's merge machinery believes the index
        differs from HEAD, and a merely STAT-STALE index does exactly that on a tree whose
        content is identical to HEAD. A clean worktree is no protection.

    "The operator workaround is to commit or stash tracked changes before merging."
        False as general advice: it does not help a stale index or a lock, and a
        downstream box (field report, 2026-08-12) failed every pull and merge with a
        status-clean tree. It IS true in exactly one place - when the escape's fast-forward
        reports that your local changes to specific files would be overwritten - and that
        is the only place the proxy now says it.

    WHAT THE FIELD FAILURE ACTUALLY LOOKED LIKE. Every pull and merge failing, every time,
    with no .git/index.lock present, no concurrent git process, and `git status` clean.
    Plain `git pull` failed identically, so the proxy was not the cause - but it was the
    thing misreporting it. The residue that box could see was dirty submodule gitlinks;
    on git 2.43 those are invisible to BOTH `git stash create` (which sets
    ignore_submodules and returns empty) and to merge's save_state, so the gitlink
    mechanism is version-dependent at best and is never assumed here - only reported by
    name when `diff-index` shows gitlinks that `status` does not.

    WHAT SHIPS AGAINST IT (see the three sections above): every proxy read runs
    --no-optional-locks; the tree-rewriting path performs one deliberate
    `update-index --refresh`; `stash failed` is classified on the EVIDENCE of a lock file
    rather than on its wording; contention is retried; and a deterministic failure is
    escaped by merging in a scratch worktree and fast-forwarding the result in.
