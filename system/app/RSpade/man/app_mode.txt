APP_MODE(3)                 RSX Framework Manual                 APP_MODE(3)

NAME
    app_mode - Application execution modes and the sealed production build

SYNOPSIS
    Environment (.env):
        RSX_MODE=development|debug|production

    Lifecycle commands:
        php artisan rsx:prod:enable [--debug]
        php artisan rsx:prod:refresh [--debug]
        php artisan rsx:prod:disable
        php artisan rsx:prod:verify

    Convenience alias (delegates to the above):
        php artisan rsx:mode:set dev|debug|prod

    Build engine + packaging:
        php artisan rsx:prod:build [--force] [--authorized]
        php artisan rsx:prod:export [--path=./rsx-export]

DESCRIPTION
    RSpade runs in one of three modes. RSX_MODE (read from the project-root
    .env) is the authoritative source of truth for the mode, independent of
    Laravel's APP_ENV.

    development
        The default. Dev mode is production-worthy for low traffic: the
        manifest rebuilds automatically on file changes and bundles compile
        JIT on the web request. Everything is live the instant a file is
        saved. Full debugging: console_debug() works, inline sourcemaps,
        debug info in window.rsxapp.

    debug and production ("prod modes")
        Both are SEALED builds. A sealed build is compiled ONCE by an
        explicit command (rsx:prod:enable / rsx:prod:refresh) and then
        treated as IMMUTABLE. The framework will NOT auto-rebuild the
        manifest or JIT-compile a bundle in a prod mode; if a build artifact
        is missing it fails loud instead of silently degrading to JIT
        compilation.

        debug is a production-like LOCAL test build: unminified, sourcemaps
        survive, console_debug() still works. Use it to reproduce a
        production-specific issue with readable code.

        production (strict prod) is the fully optimized deployment build:
        minified, sourcemaps gone, console_debug() stripped from the output.

    The word "sealed" is literal: rsx:prod:enable writes a seal file that
    pins the exact build on disk, and the framework then refuses obviously
    wrong mutations of the build assets (see GUARDS). Two byte-identical
    codebases produce byte-identical build assets (see DETERMINISM), which
    is what makes a sealed build safe to compile once and distribute across
    a cluster.

MODE COMPARISON
    Behavior                    development  debug        production
    --------                    -----------  -----        ----------
    Auto manifest rebuild       Yes          No           No
    Auto bundle JIT compile     Yes          No           No
    Minified output             No           No           Yes
    Inline sourcemaps survive   Yes          Yes          No
    console_debug() in browser  Yes          Yes          No (stripped)
    Debug block in window.rsxapp Yes         Yes          No
    CDN assets                  External URL Cached local Cached local
    Sealed / immutable build    No           Yes          Yes
    Error if artifacts missing  No           Yes          Yes

    Note the two things that are NOT true of any mode: nothing merges the
    per-bundle JS/CSS into a single file (bundles are always the vendor/app
    split), and nothing inlines CDN assets into a bundle. See CDN ASSET
    HANDLING and BUNDLE OUTPUT.

THE SEALED BUILD LIFECYCLE
    A prod build has an explicit lifecycle managed by four commands. Each is
    a thin, single-purpose entry point; the actual compilation is one shared
    engine (rsx:prod:build).

    rsx:prod:enable [--debug]
        Compile a fresh sealed build and enter prod mode. Without --debug it
        builds strict production; with --debug it builds the debug variant.

        Steps:
        1. Heal the .env symlink invariant (see ENV FILE INVARIANT).
        2. Validate the environment (strict prod only - see ENVIRONMENT
           VALIDATION). --debug skips the hard check (warn-only).
        3. Set RSX_MODE in .env and sync it into the running process so the
           spawned build subprocess inherits the right mode.
        4. Clear the old Laravel + rsx caches (and any prior seal).
        5. Run the build pipeline in an AUTHORIZED subprocess
           (rsx:prod:build --force --authorized).
        6. On success ONLY, write the seal. A failed pipeline leaves the
           system unsealed - fix the error and run enable again.

    rsx:prod:refresh [--debug]
        Rebuild the sealed assets in place. Requires an existing seal (if
        there is none it tells you to run rsx:prod:enable). Re-runs the
        pipeline and rewrites the seal. It PRESERVES the mode the build was
        sealed for unless --debug is given, which flips the sealed build to
        the debug variant. This is the command to run after pulling new code
        onto a prod box.

    rsx:prod:disable
        Leave prod mode and return to development. Removes the seal FIRST
        (so the following cache clears are not blocked by the immutability
        guard), sets RSX_MODE=development, clears the prod caches, restores
        the DEVELOPMENT composer autoloader (a plain, non-authoritative
        dump - a strict-prod build leaves a classmap-authoritative autoloader
        that must be undone so new/renamed classes resolve again), and
        pre-warms the dev bundle JIT. Idempotent: safe to run when not
        sealed.

    rsx:prod:verify
        The cluster / CI tool. Requires a seal. Recomputes the sha256 of
        every sealed asset, checks the build_key on disk against the seal,
        checks environment sanity (APP_ENV/APP_DEBUG for a strict build),
        and reports OPcache posture (advisory only). Prints a table and
        exits 0 when the build matches the seal and the environment is
        sound, 1 otherwise. Run it in a deploy health check.

    rsx:mode:set dev|debug|prod
        Kept for muscle memory. It is a thin delegator so there is exactly
        ONE implementation of each transition:
            dev, development  -> rsx:prod:disable
            debug             -> rsx:prod:enable --debug
            prod, production  -> rsx:prod:enable

THE SEAL FILE
    Location:
        storage/rsx-build/prod_seal.json

    The seal is the on-disk record of a compiled build. It is JSON:

        {
            "schema": 1,
            "rsx_mode": "production",        // or "debug"
            "build_key": "<manifest hash>",
            "git_commit": "<HEAD sha or null>",
            "created_at": "2026-07-15T...",
            "assets": [
                { "file": "build_key", "sha256": "..." },
                { "file": "bundles/Frontend__app.<hash>.js", "sha256": "..." },
                { "file": "manifest_data.php", "sha256": "..." }
                // ... every file under bundles/ ...
            ]
        }

    Asset paths are recorded relative to the build root, so the seal is
    self-contained and location-independent. The assets list covers
    manifest_data.php, the build_key file, and every file under bundles/.

    is_sealed() is true ONLY when a seal file exists AND the current RSX_MODE
    is a prod mode. That double condition means a leftover seal in a
    development checkout does not accidentally lock anything - dev is never
    sealed.

    created_at, git_commit, and the seal file as a whole are deliberately
    NOT part of any hashed build artifact. They carry the non-deterministic
    build metadata (a timestamp, a machine's git state) that the build
    artifacts intentionally exclude for byte-stability. The seal describes
    the build; it is not itself an input to the build hash.

THE DEBUG VARIANT
    debug is the "readable production" build. Relative to strict production:

        - NOT minified. The shipped JS/CSS is the compiled-but-readable
          source.
        - Inline sourcemaps SURVIVE. There is no separate sourcemap toggle:
          the compiler never adds maps, it only removes the inline
          sourceMappingURL comments carried by the source, and that removal
          happens exclusively inside minification. Since debug does not
          minify, the maps ride along.
        - console_debug() WORKS. The console_debug config block is injected
          into window.rsxapp (so the browser function has its channel
          configuration) and the call sites are NOT stripped from the
          bundle.

    Everything else matches production: it is a sealed, immutable build with
    no auto-rebuild, and CDN assets are cached locally. Build it with
    rsx:prod:enable --debug (or rsx:mode:set debug).

STRICT PRODUCTION
    Strict production is the fully optimized build. Relative to debug:

        - Minified (Terser for JS, cssnano for CSS, via the minify RPC
          server).
        - Inline sourcemaps are GONE (minification strips the
          sourceMappingURL comments - the "no minify, no maps" truth stated
          above, run forward).
        - console_debug() is neutralized two ways at once:
            1. Call sites are STRIPPED from the compiled output. The minify
               RPC request carries a strip flag (driven by
               Manifest::_should_strip_console_debug()); Terser treats
               console_debug and Debugger.console_debug as pure functions
               (pure_funcs) and deletes the calls.
            2. The console_debug config block is omitted from
               window.rsxapp, so even a call site that survived (there are
               none in app bundles) would no-op at runtime.

    Strict production is gated on a real production environment: enable
    refuses unless APP_ENV=production and APP_DEBUG=false (see ENVIRONMENT
    VALIDATION).

ENVIRONMENT VALIDATION
    rsx:prod:enable validates APP_ENV / APP_DEBUG BEFORE it changes anything.

    Strict production (no --debug) is a HARD requirement:
        - APP_ENV must be 'production'
        - APP_DEBUG must be false
    If either is wrong, enable prints the exact fixes and exits without
    touching the mode. This is intentional: a strict prod build is meant for
    a real production host.

    The debug variant (--debug) is a LOCAL test build, so an environment
    mismatch is a warning, not an error - you can build and run the debug
    variant on a development box.

    rsx:prod:verify applies the same expectation: for a strict-prod seal it
    FAILS when APP_ENV/APP_DEBUG are not production-ready; for a debug seal
    the APP_ENV row is advisory.

DETERMINISM CONTRACT
    A sealed build is deterministic: two byte-identical codebases, checked
    out at DIFFERENT absolute paths, produce an IDENTICAL build_key and
    IDENTICAL bundle filenames, byte-for-byte. This is what lets a build be
    compiled once and trusted across a cluster (or cached by CI keyed on the
    build_key).

    How it holds:

    1. File hashing branches on RSX_MODE, not APP_ENV
       (_rsx_file_hash_for_build). In a prod mode the hash is computed over
       the file's PROJECT-RELATIVE path plus its CONTENT (sha512), never the
       absolute path and never disk timestamps. The same logical file at two
       different checkout locations therefore hashes identically. (The
       development branch still uses a fast absolute-path + size + mtime
       hash - it only needs to notice local edits, and is deliberately not
       portable.)

    2. The manifest hash excludes per-file mtime/size. Those still live in
       the cache file (dev change-detection needs them) but are OUT of the
       hashed projection. The prod cache file also drops the "generated"
       timestamp and its comment (that timestamp moved to the seal). So the
       manifest_data.php produced by two identical checkouts is byte-stable,
       and build_key (the manifest hash) is content-derived.

    3. Bundle filenames are {Bundle}__{app|vendor}.{hash8}.{ext}, where the
       hash8 derives from the same relative-path + content inputs (plus the
       committed lockfile content hashes and npm declarations, already
       deterministic). Minified output is reproducible given the pinned,
       committed node_modules.

    Bonus: because build_key is content-derived and stable across checkouts,
    the full-page cache keys (fpc:{build_key}:{...}) are cluster-shareable -
    two nodes on the same build hit the same FPC entries.

GUARDS
    A sealed build is protected by developer GUARDRAILS - not a security
    boundary (see WHAT THE GUARDS DO NOT COVER). They exist to stop a
    developer from accidentally diverging or destroying the immutable build.

    Only an AUTHORIZED rebuild context may write the build assets while
    sealed. Authorization is an INVOCATION parameter and travels as a --flag
    (--authorized, read from argv by a boot-safe helper) or an explicit
    in-process call (enable/refresh mark themselves). It is NEVER an
    environment variable. A web request, a plain artisan command, or a
    tinker session can therefore never write build assets while sealed.

    The guards:

        rsx:clean refuses while sealed.
            "System is in prod mode (sealed build). Run rsx:prod:refresh to
            rebuild the assets, or rsx:prod:disable first." It refuses BEFORE
            deleting anything - it will not wipe the deployment's only copy
            of the assets.

        rsx:prod:build refuses while sealed unless authorized.
            A plain invocation is turned away and pointed at rsx:prod:refresh.

        The manifest and bundle compiler refuse to rebuild while sealed
        unless authorized, and their "artifact missing" errors name
        rsx:prod:refresh.

        Write/delete choke points assert immutability. The shared low-level
        write helpers (file_put_contents_safe, rmdir_recursive, and the
        browser-storage helper clear) call Rsx_Prod_Seal::assert_mutable()
        when the target is under storage/rsx-build. When sealed + not
        authorized, the write throws:
            "...is an immutable prod build asset (sealed prod mode); rebuild
            via rsx:prod:refresh."
        The check short-circuits cheaply when not sealed (the common path),
        so it costs nothing in dev.

    The ONLY sanctioned way to change a sealed build is rsx:prod:refresh
    (rebuild in place) or rsx:prod:disable (leave prod mode).

WHAT THE GUARDS DO NOT COVER
    The guards are guardrails, not a security boundary. They intercept the
    framework's OWN write paths. They do NOT (and cannot) stop a developer
    or process that goes around the framework:

        - Raw filesystem meddling: `rm -rf storage/rsx-build`, editing a
          bundle file by hand, `cp` over manifest_data.php. Nothing at the
          framework layer sees these.
        - Direct database writes (DB::table()->update(), raw SQL) or manual
          data changes.

    The analogy is the realtime model layer: model save()/delete() emit
    change notifications, but a raw DB::table() write bypasses the model and
    emits nothing - by design. The seal guards the framework's write
    choke points the same way; go under them and you are on your own.
    rsx:prod:verify is the backstop that DETECTS such drift after the fact
    (recomputed asset hashes will not match the seal).

BUILD ENGINE AND CACHES
    rsx:prod:build is the shared pipeline that enable/refresh/export drive.
    It is not normally run by hand (while sealed it refuses without
    --authorized). Its steps:

        1. Rebuild the manifest (forced).
        2. Compile every module bundle (forced). The minify RPC server is
           restarted before and shut down after (minification itself only
           runs in strict production; the debug variant compiles unminified).
        3. Optimize the composer autoloader (composer dump-autoload
           --optimize; strict production adds --classmap-authoritative,
           which pins the system/ PSR-4 tree). This runs BEFORE the Laravel
           caches because composer's post-dump hook clears Laravel's
           compiled files.
        4. Build Laravel caches via `optimize:cache` - run LOUD (a non-zero
           exit fails the build). Authorization is forwarded to that child
           as the --authorized flag, never via env inheritance.

    optimize:cache reality (IMPORTANT):
        RSpade's config layer reads deployment facts through env() at
        runtime. Laravel's config:cache and view:cache FREEZE env() (a
        cached config returns null for any later env() call), which is
        incompatible with how RSpade config works. Those two caches are
        therefore DROPPED from optimize:cache. Only route and event caching
        run. Do NOT reintroduce config:cache / view:cache expecting them to
        help - they would break runtime config resolution. (A dedicated
        config()-migration or a Dotenv-override design is the future path;
        see the framework BACKLOG.)

    --skip-laravel-cache skips step 4 entirely (used by the determinism
    harness so a cache build cannot perturb the asset comparison).

BUNDLE OUTPUT
    Bundles are ALWAYS emitted as a vendor/app split, in every mode:
        bundles/{Bundle}__app.{hash8}.{js|css}
        bundles/{Bundle}__vendor.{hash8}.{js|css}

    There is no single-file merge. Merging all of a bundle's JS (or CSS)
    into one file is a deferred idea, not a current behavior - do not expect
    a merged app.js/app.css. (Tracked in the framework BACKLOG.)

    The emission ORDER inside a bundle is a load-bearing contract:
    files are emitted in declared include order, class stubs sit at their
    include position, and aliases are spliced in after the stubs. This
    ordering exists to avoid temporal-dead-zone reference errors in the
    concatenated output.

CDN ASSET HANDLING
    In development, CDN assets (Bootstrap, jQuery, etc.) load directly from
    their remote URLs as declared in the bundles.

    In BOTH prod modes (debug and production), CDN assets are cached locally
    so the build does not depend on CDN availability at request time:

        - Fetched during the build and stored in:
              rsx/resource/.cdn-cache/
          (committed to git - NOT under storage/ - so the cache survives
          rsx:clean and mode switches, and CI builds are reproducible).
        - Served to the browser from /_vendor/{cached_filename}.

    Two producers populate that mirror, and both run at BUILD time:

        - Bundle cdn_assets are mirrored by the compiler as it emits them
          (step [3/5], Compiling bundles).
        - DECLARED EXTERNAL RESOURCES (*.externals.php) are mirrored by their
          own explicit step, [2/5] Mirroring external assets, which runs
          before the bundles compile. They need one: nothing renders them at
          build time - the client loads them at runtime by identifier - so
          nothing else would ever discover the URL. Entries declared
          mirror:false (a vendor endpoint serving dynamic per-client bytes) are
          skipped and keep fetching from their origin in every mode.
          See: php artisan rsx:man external_resources

    A SEALED BUILD NEVER DOWNLOADS AT REQUEST TIME. If a mirrored file is
    missing when a page asks for it, the request THROWS naming the file and the
    remedy (re-run rsx:prod:refresh) - it does not silently curl the asset. The
    loud failure is the feature: a sealed build is meant to be self-contained.

    Cached CDN assets are served SEPARATELY via /_vendor/ URLs. They are NOT
    merged or inlined into the compiled bundle files. Cache filenames derive
    from a hash of the URL, so a version bump in a bundle definition creates
    a new cache file and stops referencing the old one - no manual
    invalidation.

WINDOW.RSXAPP ACROSS MODES
    The console_debug config block is injected into window.rsxapp in
    development AND debug (this is what makes browser console_debug() work in
    debug mode). Strict production omits the block entirely.

    ajax_batching is always present but mode-dependent:
        - development: false (direct calls for easier debugging)
        - debug / production: true (batched calls for efficiency)

    Core functionality (user, site, csrf, params, etc.) is present in all
    modes.

ENV FACTS VS INVOCATION FLAGS
    RSX_MODE is a deployment ENVIRONMENT fact and lives in .env. It is NOT
    an invocation parameter. When a prod-mode command spawns a build
    subprocess, it writes RSX_MODE to .env FIRST and also syncs the value
    into the running process (putenv + $_ENV + $_SERVER + the mode cache) so
    the child - which inherits the parent's environment and whose Dotenv
    will not override an already-set var - boots on the correct mode. Without
    that sync an enable launched from a development parent would spawn a
    build that runs unminified/unstripped, and a disable launched from a
    production parent would throw "Manifest not built for production mode"
    while pre-warming dev.

    Per-invocation intent is a --flag, never an env prefix:
        - Force a rebuild:  --force
        - Authorize a sealed rebuild:  --authorized
    Do NOT prefix invocations with KEY=VALUE. This is an owner ruling; see
    the CLI invocation parameters note in Core/CLAUDE.md.

        WRONG:  RSX_FORCE_BUILD=1 php artisan rsx:prod:build
        RIGHT:  php artisan rsx:prod:build --force

ENV FILE INVARIANT (.env SYMLINK HEALER)
    RSX_MODE, and every other configuration key, is read from ONE
    authoritative file: the project-root .env
    (dirname(base_path())/.env; httpdocs/.env in deployed layouts).

    Laravel/Dotenv actually loads base_path('.env') (system/.env). The
    invariant is that system/.env is a SYMLINK to the root .env, so there is
    exactly one file and an edit to either path is the same edit. The
    prod-mode env writer (Rsx_Prod_Env) reads/writes only base_path('.env')
    and is correct precisely because of this invariant.

    Drift: a deploy or clone frequently MATERIALIZES the symlink into a real
    file. After that the two files diverge - Laravel reads only system/.env,
    so edits to the root .env become inert. A naive re-symlink would instead
    DISCARD keys that live only in system/.env.

    Healer: rsx:env:heal restores the invariant safely.

        php artisan rsx:env:heal            # heal now
        php artisan rsx:env:heal --dry-run  # report drift, change nothing

    Merge rule (root is authoritative): keys unique to system/.env are
    APPENDED to the root .env under a dated marker; keys present in BOTH with
    different values keep the ROOT value and REPORT each discarded system/.env
    value; the root file's existing lines are preserved byte-for-byte;
    system/.env is then replaced by a relative symlink (../.env). Before a
    real system/.env is replaced, a 0600 backup is written beside it
    (system/.env.replaced_by_healer; gitignored).

    It runs automatically after every framework pull, at the start of
    rsx:clean (unsealed path), and FIRST in every prod-mode transition
    (enable / refresh / disable) so the RSX_MODE write lands in the single
    healed file.

DEPLOYMENT WORKFLOW
    Typical flow:

    1. Develop (RSX_MODE=development). Changes are live on save.

    2. Reproduce a prod-specific issue locally:
           php artisan rsx:prod:enable --debug
       Readable, sealed build with working console_debug. Return with
       rsx:prod:disable.

    3. On the production host (APP_ENV=production, APP_DEBUG=false):
           php artisan rsx:prod:enable
       Compiles + seals the strict build.

    4. Verify:
           php artisan rsx:prod:verify

    5. After pulling new code onto the prod host, rebuild in place:
           php artisan rsx:prod:refresh

    6. Package a deployable elsewhere:
           php artisan rsx:prod:export
       Runs the (authorized) build and copies system/, rsx/, node_modules/,
       vendor/, storage/rsx-build/, and root *.json into the export dir.
       Excludes .env, storage/app, storage/logs,
       storage/framework/{cache,sessions,views}, storage/rsx-tmp, tests, and
       VCS/IDE dirs. The destination host must
       supply its own .env.

    7. Return to development:
           php artisan rsx:prod:disable

ERROR HANDLING
    In prod modes, missing build artifacts fail loud rather than triggering
    a JIT rebuild:

        "Manifest not built for production mode"
            The manifest cache is missing/invalid while sealed.
            Fix: php artisan rsx:prod:refresh

        "Bundle 'X' not compiled for production mode"
            A bundle is missing while sealed.
            Fix: php artisan rsx:prod:refresh

        "System is in prod mode (sealed build)."
            You ran rsx:clean (or a plain rsx:prod:build) while sealed.
            Fix: rsx:prod:refresh to rebuild, or rsx:prod:disable to leave.

        "...is an immutable prod build asset (sealed prod mode)"
            An unauthorized context tried to write under storage/rsx-build.
            This is the immutability guard doing its job.

GITIGNORE
    Add to .gitignore:
        /rsx-export/

    Each deployment generates a fresh export; it should not be committed.
    (rsx/resource/.cdn-cache/, by contrast, IS committed - it is a build
    input.)
