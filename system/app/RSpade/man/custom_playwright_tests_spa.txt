CUSTOM_PLAYWRIGHT_TESTS_SPA(1)   RSpade Manual   CUSTOM_PLAYWRIGHT_TESTS_SPA(1)

NAME
    custom_playwright_tests_spa - writing standalone Playwright tests that
    drive an RSX single-page application through its real browser lifecycle

SYNOPSIS
    A custom Playwright SPA test is an ordinary Node.js script run by hand:

        node system/app/RSpade/tests/preview/playwright/document_preview_spa.js

    It launches headless Chromium (from system/node_modules), authenticates
    with the same signed dev-auth backdoor that powers rsx:debug, drives the
    SPA, asserts on the DOM, and exits 0 (pass) or 1 (fail).

    The canonical, currently-working reference is:

        system/app/RSpade/tests/preview/playwright/document_preview_spa.js

DESCRIPTION
    rsx:debug (man rsx_debug) drives one page load and reports on it. It is
    the right tool for "does this route render, what did the console say,
    what does this element look like." It cannot follow a sequence of
    client-side SPA navigations, because after the initial document loads,
    all further routing happens inside the browser via Spa.dispatch() and
    never issues another document request rsx:debug could observe.

    When a test genuinely needs multi-step SPA interaction - navigate, click,
    assert, navigate again, assert the second screen - you write a standalone
    Playwright script. It reuses rsx:debug's mechanics (the Playwright package
    at system/node_modules, the dev-auth HMAC token, the X-Playwright-Test
    error header, the _debug_ready lifecycle signal) but keeps the page open
    and drives it directly.

    This is a thin, deliberately-manual test surface. There is exactly one
    such test in the framework tree today (document_preview_spa.js). Treat
    this page as the pattern reference; treat that file as the executable
    reference.

    Unlike a Laravel Dusk test - which extends a base TestCase, is discovered
    by PHPUnit, and speaks a fluent PHP browser DSL - an RSX Playwright test
    is plain JavaScript against the raw Playwright API. It is NOT discovered
    by the manifest, NOT run by rsx:test, and NOT run by run_all_tests.sh.
    Nothing autoloads it. You run it yourself, or a higher-level harness
    shells out to `node` on it.

HOW PLAYWRIGHT TESTS RUN
    The framework test tree (man: app/RSpade/tests/CLAUDE.md) recognizes a
    `playwright` test type living under <concern>/playwright/*.js. That type
    is special:

    - It is NOT manifest-indexed. The `playwright` path segment is excluded
      from class scanning, and .js files are never loaded as PHP tests.
    - `php artisan rsx:test --framework` runs only PHP/cli/asset tests. It
      does not run Playwright scripts.
    - run_all_tests.sh finds only shell tests under http/, cli/, and asset/.
      It does not find or run *.js under playwright/.

    Consequently a Playwright test is executed by invoking node on it:

        node <path-to-test>.js

    The script is self-contained: it reads APP_KEY from .env, mints its own
    dev-auth token, targets the running dev web server (http://localhost),
    and prints PASS:/FAIL: lines with an exit code. A CI wrapper that wants
    these in the run simply shells out to node per file and checks the exit
    code - the same PASS/FAIL/exit contract the shell runner already uses.

    Requirements to run one:
    - The dev web server must be up and serving the app (tests hit it over
      HTTP, they do not boot Laravel in-process).
    - Playwright and Chromium must be installed (rsx:debug auto-installs both
      on first use; running it once primes the environment).
    - Any data the test asserts on must already exist in the dev database.

DEV-AUTH AUTHENTICATION
    RSX has no login form to script. Instead, development builds honor a
    signed backdoor header - the identical mechanism rsx:debug uses. A request
    carrying a valid signed token is authenticated as the named user before
    dispatch; an invalid or missing token is silently ignored (the page
    simply renders unauthenticated - no error).

    The token is an HMAC-SHA256 of a JSON payload, keyed by APP_KEY:

        payload = json_encode([
            'url'     => <request URI the token is valid for>,
            'user_id' => <int user id>,
            'portal'  => <bool>,
        ])
        token   = hash_hmac('sha256', payload, APP_KEY)

    (Verified against Route_Debug_Command::generate_dev_auth_token and the
    verifiers in rsx/main.php and Portal_Dispatcher.)

    Headers sent on the authenticated request:

        X-Dev-Auth-User-Id           staff user id (main site)
        X-Dev-Auth-Portal-User-Id    portal user id (portal, instead of above)
        X-Dev-Auth-Token             the HMAC token above
        X-Playwright-Test            '1' - plain-text error pages, safe always

    Generating the token from JavaScript. PHP's json_encode escapes forward
    slashes as \/. You MUST reproduce that byte-for-byte or the HMAC will not
    match. The reference test does exactly this:

        const crypto = require('crypto');
        function dev_auth_token(url, user_id) {
            const app_key = read_app_key();   // APP_KEY line from .env
            const payload = JSON.stringify({
                url: url, user_id: user_id, portal: false
            }).replace(/\//g, '\\/');         // match PHP's \/ escaping
            return crypto.createHmac('sha256', app_key)
                         .update(payload).digest('hex');
        }

    (Alternatively, shell out to a `php -r` snippet to compute the token and
    pass it in via argv - but the in-process crypto approach above keeps the
    test a single `node` invocation.)

    URL scope. The token is bound to ONE request URI. The main-site verifier
    recomputes it against $request->getRequestUri() (path plus query string);
    the portal verifier normalizes first (see below). Because SPA navigation
    after the first load is entirely client-side, only the initial
    page.goto() URL is ever token-verified. Sign the token for exactly that
    URL. A token minted for /contacts will NOT validate a request to /engagements
    - which is one reason auth headers belong on the first request only (next
    section).

MAIN-SITE VS PORTAL BACKDOOR
    Both backdoors are FRAMEWORK CORE and symmetric:

    - The main-site (staff) verifier is Dispatcher::__handle_dev_auth(),
      called at the top of dispatch. It must run there, not in an
      application hook: the declarative #[Auth] gates are evaluated by the
      dispatcher, and a gate asking "is this caller logged in" has to see
      the identity the harness is asserting.

    - The portal verifier is Portal_Dispatcher::__handle_dev_auth(), its
      twin. Neither can be dropped or broken by an application.

    Testing a portal SPA differs from the main-site example in three ways:
    - send X-Dev-Auth-Portal-User-Id, not X-Dev-Auth-User-Id;
    - sign the token with 'portal' => true in the payload;
    - the portal verifier normalizes the URL by stripping the /_portal prefix
      BEFORE recomputing the token. Sign against the normalized (prefix-less)
      path, and validate_session (below) must be told it is a portal page.

    rsx:debug wraps all of this behind --portal / --portal-user; a hand-written
    portal test must assemble it explicitly.

RESTRICTING AUTH HEADERS TO THE FIRST REQUEST
    Attach the dev-auth headers to the INITIAL document request only. Every
    request after that authenticates via the session cookie the first response
    sets. The reference test enforces this with a one-shot flag inside a
    page.route() interceptor:

        let initial_doc_sent = false;
        await page.route('**/*', async (route, request) => {
            const url = request.url();
            if (url.startsWith(BASE_URL)) {
                const headers = { ...request.headers() };
                if (!initial_doc_sent
                    && request.resourceType() === 'document') {
                    Object.assign(headers, auth_headers);   // full dev-auth
                    initial_doc_sent = true;
                } else {
                    headers['X-Playwright-Test'] = '1';      // safe everywhere
                }
                await route.continue({ headers });
            } else {
                await route.continue();                      // e.g. CDN: untouched
            }
        });

    Why first-request-only:
    - The token is URL-scoped. It only validates the one URL it was signed for;
      re-sending it on Ajax calls to other endpoints validates nothing anyway.
    - Once the first response sets the session cookie, the cookie is the
      credential for every subsequent request - re-authenticating per request
      is redundant work, and it re-runs RsxAuth::login() needlessly.
    - X-Playwright-Test only affects error formatting, so it is safe to send on
      every request; the auth headers are the ones to restrict.

    NOTE: rsx:debug's own bin/route-debug.js applies its headers to every
    request it issues, because it performs a single navigation and never does
    client-side SPA routing. A multi-step SPA test does route client-side and
    therefore must scope the headers as shown.

LIFECYCLE EVENTS
    RSX exposes framework events that replace arbitrary sleeps with precise
    "the app is ready" signals. Two matter for SPA tests.

    _debug_ready (initial page load). Fires once, after every framework init
    phase has completed. The phases run in this order (Rsx.js _rsx_core_boot):

        framework_core_define
        framework_modules_define
        framework_core_init
        app_modules_define
        app_define
        framework_modules_init
        app_modules_init
        app_init
        _spa_init          (awaits the first SPA action's full lifecycle)
        app_ready

    Because _spa_init awaits the initial action's on_load (data fetch) and
    on_ready, _debug_ready guarantees the first screen is fully rendered WITH
    its data - the definitive signal to wait for after page.goto().

    IMPORTANT: _debug_ready exists solely for tooling like rsx:debug and these
    tests. It is explicitly marked "DO NOT use this in application code" in
    Rsx.js - application code uses the on_app_ready() phase instead.

    Wait for it like this (note the bare-global guard, next paragraph):

        await page.evaluate(() => new Promise((resolve) => {
            if (typeof Rsx !== 'undefined' && Rsx.on) {
                Rsx.on('_debug_ready', () => resolve());
                setTimeout(resolve, 15000);   // guard against a missed event
            } else {
                setTimeout(resolve, 3000);
            }
        }));

    Bare globals. The app bundle exposes Rsx and Spa as BARE globals, not
    reliably as window.Rsx / window.Spa. Guard with `typeof Rsx !== 'undefined'`
    and call Rsx / Spa unqualified, as the reference test does.

    spa_dispatch_ready (each SPA navigation). Fires after a Spa.dispatch()
    completes - the action's on_ready has run and its children are ready. The
    event carries { url, action }. Register the listener BEFORE dispatching, or
    the event fires before you are waiting and is missed:

        async function spa_navigate(path) {
            const ready = page.evaluate(() => new Promise((resolve) => {
                Rsx.on('spa_dispatch_ready', () => resolve());
            }));
            try {
                await page.evaluate((p) => { Spa.dispatch(p); }, path);
            } catch (e) { /* context may be destroyed mid-transition */ }
            await ready;
        }

    (A companion spa_dispatch_start { url } event fires at the top of a
    dispatch, if you need to observe the transition beginning.)

SESSION VALIDATION
    On each SPA dispatch, Rsx.validate_session() calls the server and compares
    build_key, session_hash, and the current user against window.rsxapp. On any
    mismatch it triggers a transparent full reload via location.replace().

    In a dev-auth test the session established by the backdoor can carry a
    session_hash that does not match the one embedded in the initially-rendered
    page, producing a false-positive reload that destroys your SPA context
    mid-test. Neutralize it immediately after the first load, before any
    SPA navigation:

        await page.evaluate(() => {
            if (typeof Rsx !== 'undefined') Rsx.validate_session = async () => true;
        });

    Do this AFTER _debug_ready (so Rsx exists and the first action is rendered)
    and BEFORE the first Spa.dispatch(). This is a test-environment accommodation
    only; real sessions validate normally.

SPA NAVIGATION
    Use browser navigation ONLY for the initial load, and 'commit' rather than
    'networkidle' (the SPA fires many async requests during component lifecycle;
    rely on _debug_ready, not the network settling):

        await page.goto(`${BASE_URL}${ROUTE}`, { waitUntil: 'commit' });

    For everything after, call Spa.dispatch() directly through page.evaluate().
    Do NOT click sidebar links from the evaluation context - jQuery's overridden
    .click() (which prevents default and routes the SPA) does not fire reliably
    through Playwright's bridge. Spa.dispatch() is deterministic.

    Context destruction. A SPA transition replaces the content area and can
    destroy Playwright's execution context, so a page.evaluate() running during
    a transition may throw "Execution context was destroyed". This is expected -
    wrap such calls in try/catch. State installed via page.addInitScript()
    survives these transitions (it re-runs on every real page load, which is
    also a useful signal: if your init script re-runs mid-test, a full reload
    happened where you expected an SPA transition).

    Confirming you authenticated. After the initial load, check that an SPA
    action is present - if auth failed, dispatch never ran:

        const on_page = await page.evaluate(() =>
            typeof Spa !== 'undefined' && !!(Spa.action && Spa.action()));

    From there, reach into the live action with its component API - e.g.
    Spa.action().$sid('select') for a scoped child element - and assert on the
    rendered DOM or poll with page.waitForFunction() until an async render
    (pdf.js, a chart, a datagrid fetch) settles.

THE REFERENCE TEST
    system/app/RSpade/tests/preview/playwright/document_preview_spa.js is a
    complete, currently-passing example of every pattern above. It:

    - reads APP_KEY from .env and mints its own dev-auth token (with the \/
      escaping fix);
    - scopes auth headers to the first document request;
    - goes to /dev/document_preview with waitUntil: 'commit';
    - waits on _debug_ready, then patches validate_session;
    - confirms Spa.action() is present (auth succeeded);
    - selects the sample PDF, then page.waitForFunction()s until pdf.js has
      drawn a non-empty canvas and the "Page 1 of N" indicator reports N > 1;
    - clicks Next and asserts the indicator advances;
    - asserts the extracted-text textarea is populated;
    - prints PASS:/FAIL: lines and sets exit code 0/1.

    Copy it as the skeleton for a new SPA test and swap the route, the user,
    and the specific DOM assertions.

COMMON PITFALLS
    Auth headers on every request
        The token is URL-scoped and the cookie authenticates after the first
        response, so re-sending dev-auth headers is at best redundant. Scope
        them to the initial document request (see RESTRICTING AUTH HEADERS).

    HMAC mismatch: forgetting the \/ escaping
        PHP json_encode writes "\/" for "/". If your JS token is computed from
        an unescaped JSON string, the HMAC never matches and the page renders
        unauthenticated (no error). Apply .replace(/\//g, '\\/').

    Signing the token for the wrong URL
        The main-site verifier checks against getRequestUri (path + query); the
        portal verifier strips /_portal first. Sign for the exact initial URL
        (normalized for portal). SPA navigations after the first load are not
        token-verified.

    Using window.Rsx / window.Spa
        The bundle exposes Rsx and Spa as bare globals. Guard with
        `typeof Rsx !== 'undefined'` and reference them unqualified.

    Registering spa_dispatch_ready after dispatching
        Register the listener before calling Spa.dispatch(), or the event fires
        before you are waiting.

    validate_session false-positive reloads
        A dev-auth session's hash can differ from the rendered page's, forcing a
        location.replace() mid-test. Patch Rsx.validate_session to return true
        after the first load (see SESSION VALIDATION).

    Hostname guard hard-fatals before auth
        In development mode, Rsx_Env_Hostname_Guard throws a RuntimeException on
        every web request whose Host header is neither loopback
        (localhost/127.*/::1) nor an exact match for APP_URL's host. A BASE_URL
        pointing at a mismatched or typo'd hostname 500s for reasons unrelated
        to your test. The reference test uses http://localhost precisely to stay
        inside the loopback exemption; prefer it unless a real host is required.

    Browsing localhost changes what the HOST-derived helpers answer
        Rsx::get_hostname() reports the browsed host, so on localhost
        Rsx::is_dev_site() and Rsx::is_debug_site() are both FALSE. Any
        environment-scoped #[Auth] gate built on them (the template's
        'dev_tools' is the shipped example) therefore DENIES under a
        localhost test while passing in a real browser on the APP_URL host.
        rsx:debug avoids this by browsing the APP_URL host with a Chromium
        host-resolver rule pointing it at loopback; a hand-written test that
        needs those gates to pass must do the same
        (--host-resolver-rules="MAP <app-host> 127.0.0.1") instead of using
        the bare loopback URL.

    Session cookies and plain http
        Session cookies are Secure in every mode EXCEPT development, where the
        flag follows the request scheme (Rsx_Session_Cookie). A plain-http
        loopback test therefore holds a session in development mode and only
        there - do not expect a debug/production-mode build to authenticate
        over http.

    Playwright require path
        Playwright is installed under system/node_modules, not the project root.
        From a script outside system/, require it by absolute path:
        require('/var/www/html/system/node_modules/playwright').

    Expecting rsx:test or run_all_tests.sh to run it
        Neither discovers Playwright .js files. Run the script directly with
        node (see HOW PLAYWRIGHT TESTS RUN).

    waitUntil: 'networkidle' as the ready signal
        The SPA keeps issuing async requests; networkidle is unreliable. Use
        'commit' for the goto and wait on _debug_ready / spa_dispatch_ready.
