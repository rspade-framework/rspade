NAME
    turnstile - Cloudflare Turnstile human verification (widget + validator)

SYNOPSIS
    # .env - the only switch. Both keys are required when enabled.
    TURNSTILE_ENABLED=true
    TURNSTILE_SITE_KEY=1x00000000000000000000AA
    TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA

    <!-- The form: drop the widget in, above the submit button. -->
    <Turnstile_Input />

    // The endpoint: FIRST statement of the POST branch.
    use App\RSpade\Core\Turnstile\Rsx_Turnstile;

    Rsx_Turnstile::validate($request);          // native #[Route] POST
    Rsx_Turnstile::validate($request, $params); // #[Ajax_Endpoint]

DESCRIPTION
    Turnstile is Cloudflare's CAPTCHA replacement: instead of asking a human
    to read distorted text, it runs a silent background challenge in the
    browser and mints a token the server exchanges for a verdict. RSpade
    ships it as two halves that are designed to be used together and are
    impossible to half-wire: a core component that renders the widget and
    owns the transport, and a validator the endpoint calls.

    The design goal is that an endpoint never asks whether the feature is
    on. The widget ALWAYS posts a fixed field, __turnstile - the sentinel
    'inactive' while the feature is off, a Cloudflare token while it is on -
    and validate() is written to demand the right one either way. So the
    call site is unconditional, has no `if (config(...))` around it, and
    keeps working when an operator flips the switch.

    Nothing about this is derived from the application mode. Development,
    debug and production behave identically; only config('rsx.turnstile
    .enabled') decides. An install that enables the feature with one of the
    two keys missing throws rather than degrading, because both degradations
    (a widget rendered against no site key, or every token failing
    verification against no secret) look like a bug in the form rather than
    a bug in the .env.

    Laravel differences: there is no package to install, no service provider
    to register, no middleware to attach to a route group, and no validation
    rule to add to a $rules array. The widget is a jqhtml component that is
    globally available because it lives in the core bundle, the validator is
    one static call, and the framework itself detects an endpoint that
    forgot to make that call (see THE COMPLETENESS GUARD) - a class of
    mistake a middleware-based integration cannot see at all.

HOW TURNSTILE WORKS

    Two keys, one round trip. The SITE key is public and identifies your
    application to the widget; the SECRET key is server-only and is the
    credential for the verdict lookup. The exchange:

        1. The page loads Cloudflare's api.js and renders a widget bound to
           the site key.
        2. The widget runs its challenge and produces a token. Tokens are
           SINGLE-USE and expire after 300 seconds.
        3. The form posts the token to your endpoint.
        4. Your endpoint posts {secret, response: token, remoteip} to
           https://challenges.cloudflare.com/turnstile/v0/siteverify and
           receives {success, hostname, error-codes, metadata}.

    RSpade owns steps 1, 2 and 4. You own step 3 only to the extent of
    putting <Turnstile_Input /> in the form and validate() in the handler.

    HOW api.js REACHES THE PAGE. Through the external-resources registry, like
    every other external URL in RSpade - never a hand-written <script> tag.
    system/app/RSpade/Core/Js/turnstile.externals.php declares the identifier
    'turnstile', and Turnstile.js does nothing but

        await Rsx.load_external('turnstile');

    before rendering a widget. The declaration is also where Turnstile's
    Content-Security-Policy needs are stated: the frame it opens, the host it
    calls, the styles it injects - plus mirror:false (Cloudflare serves
    challenge-specific bytes, so a sealed build must NOT serve a local copy)
    and the readiness handshake (the URL's onload=__rsx_turnstile_onload names
    a global the loader defines and Cloudflare calls). The page's policy
    permits challenges.cloudflare.com because that file says so, in every mode.
    Nothing here needs configuring.
    See: php artisan rsx:man external_resources, php artisan rsx:man csp

CONFIGURATION

    system/config/rsx.php:

        'turnstile' => [
            'enabled'    => env('TURNSTILE_ENABLED', false),
            'site_key'   => env('TURNSTILE_SITE_KEY'),
            'secret_key' => env('TURNSTILE_SECRET_KEY'),
            'verify_timeout_seconds' => 30,
        ],

    enabled
        The ONLY input that decides whether the feature is active.
        Application mode has no bearing on it: a development box with
        enabled=true runs real verification, and a production box with
        enabled=false runs none. Default false, so a fresh install is off.

    site_key
        PUBLIC. Exported to the browser as window.rsxapp.turnstile, and ONLY
        when the feature is enabled - a disabled install ships no key and
        the client's Turnstile.is_active() reads false.

    secret_key
        SERVER-ONLY. The siteverify credential. It is never exported to the
        client, never logged, and never appears in a response.

    verify_timeout_seconds
        How long the outbound siteverify call may take. This is a SANCTIONED
        timeout, owner-approved 2026-08-12, and it is sanctioned because
        expiry degrades to FAIL CLOSED: the verification is rejected with
        the "temporarily unavailable" message and the user retries. It can
        never turn an unverified token into an accepted one. The general
        framework rule against timeouts still stands everywhere else.

    Enabled with either key empty throws a RuntimeException naming the
    missing environment variable(s), from whichever comes first: the
    window.rsxapp population point on a page render, or validate() on a
    submit. It is a 500, not a form error, because it is a deployment fault.

    A Cloudflare TESTING key (either the site key or the secret - see
    TESTING for the published list) on a STRICTLY-PRODUCTION build throws
    the same way, at the window.rsxapp population point. The always-pass
    testing secret accepts ANY token, so a production site running it has
    no human verification at all while every form claims it does. Debug
    mode is exempt: it is a sealed LOCAL test build, exactly where the
    dummy keys belong.

THE WIDGET

    <Turnstile_Input /> is a framework-core jqhtml component. It is globally
    available - the core bundle carries it - so there is nothing to import
    or register. Place it inside the form, above the submit button.

    Args:

        $theme       auto | light | dark                   (default auto)
        $size        normal | flexible | compact           (default normal)
        $appearance  always | execute | interaction-only   (default always)

    TWO STATES. The component decides which to show from whether the server
    exported a site key:

        active     Cloudflare's widget renders into the component's own
                   container. The hidden field starts empty and receives the
                   token when the challenge resolves.
        inactive   An inert, obviously-static placeholder shows where the
                   widget will sit, and the hidden field carries 'inactive'.

    The placeholder is a deliberate first-class state: on a fresh install every
    wired form shows it, which is how a developer sees at a glance that the
    form is wired and the feature is merely off.

    THE FIXED FIELD. The component renders a REAL
    <input type="hidden" name="__turnstile">. That one detail is what makes
    a single core component work on both transports with no dependency on
    application classes: Rsx_Form.vals() sweeps hidden inputs, and a native
    <form> POST serializes them. The name is a CONTRACT shared with
    Rsx_Turnstile::FIELD and must never be renamed on one side only. The
    same goes for the 'inactive' sentinel (Rsx_Turnstile::INACTIVE).

    Cloudflare is told 'response-field': false, so its own hidden
    cf-turnstile-response input is never injected. There is exactly one
    field, and RSpade owns it.

    AUTO-RESET ON A FAILED SUBMIT. The component subscribes to the
    surrounding Rsx_Form's 'error' event and resets the widget when it
    fires. This is mandatory, not a nicety: tokens are SINGLE-USE and
    validate() runs BEFORE any field validation, so EVERY failed submit has
    already spent the token - including one that failed on an unrelated
    field. Without the reset the user's retry dies on timeout-or-duplicate
    with no way to recover but a page reload. (jqhtml events are sticky, so
    a component registering after an error already fired replays it once and
    resets a freshly-minted widget. Harmless - it simply re-solves.)

    NOT A Form_Input_Abstract. Form_Input_Abstract and Rsx_Form are
    APP-owned (rsx/theme/components/), and a framework-core component may
    not depend on application classes. The hidden-input trick above replaces
    the inheritance. Practical consequence: it is not a form field in the
    Rsx_Form sense - it takes no $name, produces no field error, and must
    not be nested inside another input component.

THE VALIDATOR

    Rsx_Turnstile::validate(Request $request, ?array $params = null): void

    Call it as the FIRST statement of the POST/submit branch, before any
    credential check, email lookup or record work. That placement is the
    point: verification must gate enumeration too, and an endpoint that
    checks "does this email exist" before verifying the human has already
    answered the question an attacker was asking.

        #[Route('/login', methods: ['GET', 'POST'])]
        #[Auth('public')]
        public static function index(Request $request, array $params = [])
        {
            if ($request->is_post()) {
                Rsx_Turnstile::validate($request);
                // ... credentials, only now
            }
        }

        #[Ajax_Endpoint]
        #[Auth('public')]
        public static function submit(Request $request, array $params = [])
        {
            Rsx_Turnstile::validate($request, $params);
            // ...
        }

    THE $params ARGUMENT. Ajax and batch transports deliver the submitted
    body in $params; native #[Route] and #[Portal_Route] POSTs do not merge
    the body into $params at all. validate() reads $params first and falls
    through to $request->input(), so passing $params where you have it is
    always correct and omitting it where you do not is also correct.

    THE DECISION MATRIX.

        Disabled, field === 'inactive'      pass
        Disabled, anything else (or absent) MESSAGE_FAILED
        Enabled, keys missing               RuntimeException (a 500)
        Enabled, no token / 'inactive'      MESSAGE_MISSING
        Enabled, siteverify says no         MESSAGE_FAILED
        Enabled, siteverify unreachable     MESSAGE_UNAVAILABLE
        Enabled, hostname mismatch          MESSAGE_FAILED
        Enabled, verified                   pass

    The disabled branch demands the sentinel rather than accepting anything,
    so a form that lost its widget fails loudly instead of quietly opting
    out of verification.

    A FAILURE STOPS THE REQUEST. It does not accumulate into the endpoint's
    field errors and validate() does not return. The response is shaped for
    the channel the request arrived on, exactly as Rsx_Csrf does:

        inside Ajax::internal()   AjaxFormErrorException, which the batch
                                  controller maps into that one call's slot
        /_ajax*, /_upload         the ajax error contract (HTTP 200,
                                  _success:false, error_code 'validation')
        native or portal POST     Flash_Alert::error() + redirect back

    The message always rides the SUMMARY key (_message), never a
    __turnstile-keyed field error, because Form_Utils._normalize_errors()
    drops field keys beginning with an underscore. There is no field on the
    page for it to attach to anyway.

    THE HOSTNAME CHECK. siteverify reports the hostname the token was minted
    on. No config names it - the running application already knows who it is
    via Rsx::get_hostname() - and a mismatch is rejected. The ONE exemption
    is a verdict Cloudflare itself marks as produced by a testing key
    (metadata.result_with_testing_key): the published dummy keys always
    report hostname 'example.com' whatever host rendered the widget, so
    comparing it would make the documented dev recipe below unusable. The
    exemption reads Cloudflare's own marker rather than a hardcoded list of
    keys, and costs nothing in production - a real secret never sets it.

    FAIL CLOSED. A network error, a non-2xx status, or a non-JSON body from
    siteverify is a rejection with its own distinct message
    (MESSAGE_UNAVAILABLE), never a pass. An unverifiable token is never an
    accepted token. The distinct message matters operationally: "verification
    failed" is a user problem, "verification is temporarily unavailable" is
    yours. Only the outbound call is inside the try block - a genuine
    rejection can never be reported as an outage.

    MESSAGES (constants on Rsx_Turnstile, so a test can assert them):

        MESSAGE_FAILED       Verification failed - reload the page and try
                             again.
        MESSAGE_MISSING      Please complete the verification challenge.
        MESSAGE_UNAVAILABLE  Verification is temporarily unavailable -
                             please try again.

    THE EXTERNAL API. Api_Param_Validator normally 422s any undeclared
    parameter. __turnstile is exempted, so an API endpoint may call
    validate($request) without declaring an #[Api_Param] for it.

THE COMPLETENESS GUARD

    A form carrying the widget posts __turnstile to an endpoint that MUST
    call validate(). If it never does, the request was accepted with no
    verification whatsoever and nothing anywhere would say so: the page
    shows a widget, the user solves it, and the protection is inert. That
    is the worst failure mode a feature like this can have, because it looks
    exactly like the working one.

    So the framework detects it. Rsx_Turnstile::_guard_unvalidated_token()
    subscribes to the rsx.post_dispatch action event, and throws when a
    __turnstile value was submitted and validate() never ran:

        Turnstile implementation incomplete: this request submitted a
        __turnstile value but the endpoint never called
        Rsx_Turnstile::validate(). ... Handler: /some/path

    The fix is always the same: add the validate() call to that handler.

    WHY POST-DISPATCH. A pre-dispatch check cannot tell a wired endpoint
    from an unwired one - the call it is looking for has not had a chance to
    happen yet. Only after the handler returns is "did it validate?" a
    question with an answer. rsx.post_dispatch fires at every
    handler-invocation seam (browser Ajax, each Ajax::internal()/batch
    sub-call, external API, plain routes, portal routes), immediately after
    the handler returns and before response shaping, on the SUCCESS path
    only. Handlers run INLINE and may throw - which is precisely how the
    guard works. See: php artisan rsx:man event_hooks

    THE LATCH. validate() sets a per-request latch BEFORE reaching a verdict,
    so a validator that ran and REJECTED still counts as having run (without
    that, every genuine verification failure would draw a second, misleading
    exception). Ajax::internal() saves the latch, resets it for the
    sub-call, and restores it afterwards. Two consequences, both wanted: a
    batch cannot launder one call's verification across its siblings, and a
    handler that validated its own request and then made an internal call
    has not lost its own proof.

    The guard is idempotent - it only reads state - which matters because
    the event fires at nested seams (the Ajax handler AND the Dispatcher
    transport route around it).

TESTING

    THE DEV RECIPE. Cloudflare publishes dummy keys that work on ANY domain,
    localhost included, so the full enabled path can be exercised with no
    Cloudflare account and no public hostname:

        Site keys (client)
            1x00000000000000000000AA    always passes, visible widget
            2x00000000000000000000AB    always blocks
            3x00000000000000000000FF    forces an interactive challenge

        Secret keys (server)
            1x0000000000000000000000000000000AA   always passes
            2x0000000000000000000000000000000AA   always fails
            3x0000000000000000000000000000000AA   token already spent

    Mix and match: the always-passes site key with the always-fails secret
    is how you see the rejection path (and the widget auto-reset) without
    touching a real challenge.

        # .env - the standard "on, and working" development pair
        TURNSTILE_ENABLED=true
        TURNSTILE_SITE_KEY=1x00000000000000000000AA
        TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA

    Verdicts produced by these keys carry metadata.result_with_testing_key
    and report hostname 'example.com', which is why the hostname check
    exempts them (see THE VALIDATOR).

    Testing keys are for development and debug builds ONLY: a
    strictly-production build configured with any key from the tables above
    throws at the window.rsxapp population point (see CONFIGURATION).

    THE TEST SEAM. Rsx_Turnstile::$force_verify_result_for_tests is a
    process-global static that substitutes the siteverify VERDICT (true =
    verified, false = rejected; null = make the real call). It exists so a
    framework test can exercise the enabled path and the failure shaping
    with no network dependency. Nothing outside a test run may set it, and a
    test that sets it must clear it.

        Rsx_Turnstile::$force_verify_result_for_tests = false;
        try {
            // ... assert the rejection shape
        } finally {
            Rsx_Turnstile::$force_verify_result_for_tests = null;
        }

    The framework's own coverage is app/RSpade/tests/turnstile/ - run it
    with `php artisan rsx:test --framework --group=turnstile`.

COMMON PITFALLS

    Reusing a token
        Tokens are single-use and the server validates BEFORE field
        validation, so every rejected submit has spent one. Inside an
        Rsx_Form the widget resets itself on the form's 'error' event. If
        you submit some other way, you own the reset.

    Expecting a config flip to reach an open page
        A page rendered while the feature was off posts 'inactive'; one
        rendered while it was on posts a token. After a flip, the other
        state is rejected and the user must reload. This is accepted by
        design - it heals on the next page load and needs no machinery.

    A POST arriving without the field
        That is a form missing its widget, and it is rejected. Adding
        <Turnstile_Input /> to the form is the fix; making validate()
        tolerant of an absent field is not, because "absent" and "opted out
        of verification" would then be the same thing.

    Nesting the widget inside another input component
        <Turnstile_Input /> is not a Form_Input_Abstract. It goes in the
        form directly, as a sibling of the fields, never inside a
        <Form_Field> or another input.

    Enabling with one key
        Throws, on purpose. Set both, or set enabled=false.

    Adding the widget without the validate() call
        The completeness guard throws on the first submit. Do not silence
        it - add the call.
