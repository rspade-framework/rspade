NAME
    datetime_inputs - Date and time entry in RSX forms via native-typed
    Text_Input

DESCRIPTION
    RSX has no dedicated date-picker component. Date and time fields are
    ordinary Text_Input components rendered with a native HTML input type
    (type="date", type="time", type="datetime-local"). The browser supplies
    the picker UI; RSX supplies the form binding, and the string the input
    produces is stored and read back unchanged.

    This is deliberate. RSX date/time values are ISO strings end to end (see
    time(7)): a native type="date" input emits and accepts "YYYY-MM-DD", which
    is exactly the Rsx_Date string format and exactly what a DATE column casts
    to. There is no conversion layer, no JS date library, and no wrapper
    component to learn - a date field is a Text_Input with one extra argument.

    Unlike Laravel forms, which typically pair a Blade `<input>` with a
    JavaScript date-picker plugin and a Carbon cast on the model, RSX binds
    the raw native input directly through Rsx_Form and stores the browser's
    string value as-is. The model's Rsx_Date_Cast / Rsx_DateTime_Cast (applied
    automatically to DATE / DATETIME columns) keeps the round trip in strings,
    so nothing on either side ever holds a Carbon object.

    Key differences from Laravel:
    - Laravel: date-picker JS plugin + Carbon cast + manual value formatting
    - RSX: native input type + string value + automatic Rsx_Date/_Time casts

SYNOPSIS
    Date field (the common case):

        <Form_Field $label="Start Date">
            <Text_Input $name="start_date" $type="date" $max_length=-1 />
        </Form_Field>

    Time field:

        <Form_Field $label="Start Time">
            <Text_Input $name="start_time" $type="time" $max_length=-1 />
        </Form_Field>

BASIC USAGE
    A date field is a Text_Input. The only additions over a plain text field
    are $type (which native control to render) and $max_length (required on
    Text_Input; use -1 because a native date/time input has no free-text
    length to cap).

    Supported native types (each passes straight through to the input's HTML
    "type" attribute):

        date            Calendar picker. Value "YYYY-MM-DD".
        time            Clock picker. Value "HH:MM" (or "HH:MM:SS").
        datetime-local  Combined picker. Value "YYYY-MM-DDTHH:MM" (LOCAL,
                        no timezone, no seconds).

    In practice the reference app uses only $type="date" (project start/due
    dates, party date_of_birth). Verify a field renders and round-trips before
    relying on time / datetime-local - see PITFALLS.

    Binding in a form is identical to any other input: $name on the input is
    matched against a key in the Rsx_Form $data object; the field auto-fills on
    load and its value is collected on submit. Never set $value - the form
    populates it.

VALUE FORMATS
    The string the input produces is the string you store. Match the column
    type and the RSX date/time helper to the input type:

        Input type       Value string          Column   Helper class
        date             "2025-12-24"          DATE     Rsx_Date
        time             "09:00" / "09:00:00"  TIME     (string)
        datetime-local   "2025-12-24T15:30"    (see PITFALLS)

    type="date" values are already valid Rsx_Date strings. A DATE column read
    back through the model returns the same "YYYY-MM-DD" string (Rsx_Date_Cast),
    so it drops straight back into the form's $data with no formatting.

    Rsx_Date validates a submitted date with checkdate():

        use App\RSpade\Core\Time\Rsx_Date;
        if (!empty($params['start_date']) && !Rsx_Date::is_date($params['start_date'])) {
            $errors['start_date'] = 'Invalid date';
        }

TIMEZONE
    A native date/time input has NO timezone. It reads and writes wall-clock
    strings in whatever the browser's clock says, and it neither knows nor
    honors the user's resolved RSX timezone (login_users.timezone -> sites.
    timezone -> config; see time(7)).

    For type="date" that is exactly right, and it is why the reference app uses
    only dates: a calendar date is timezone-agnostic on both sides, so the round
    trip is lossless no matter where the user sits.

    For type="datetime-local" it is the whole hazard. "2025-12-24T15:30" is a
    moment ONLY once you say which zone it is in. The browser's zone and the
    user's configured zone can differ (a traveling user, a shared workstation,
    a user who set a zone deliberately), so the server must decide explicitly -
    normally by interpreting the submitted string in Rsx_Time::get_user_timezone()
    (or, for a tenant-owned schedule, Rsx_Time::get_site_timezone()) before it
    ever reaches a DATETIME column. Never assign the raw value: it has no offset,
    and the cast would store the wall-clock digits as if they were UTC.

    Rendering back is the mirror image: a DATETIME read from the model is an ISO
    8601 string in UTC, and to seed a datetime-local input you must first convert
    it to the resolved zone and truncate to "YYYY-MM-DDTHH:MM". A DATE column
    needs none of that.

    There is no picker component that hides any of this, and none is planned -
    see PITFALLS (Native picker only). The timezone chain, the preference API and
    the browser auto-set are documented in full in time(7).

SERVER-SIDE HANDLING
    Treat the value as a plain string param in the #[Ajax_Endpoint] save
    method. Store the string on the model (the cast keeps it a string), or NULL
    when the field was left empty - a native date input submits an empty string
    when cleared, and an empty string must not be written to a DATE/TIME column.

        #[Ajax_Endpoint]
        public static function save(Request $request, array $params = []) {
            $errors = [];
            if (empty($params['name'])) $errors['name'] = 'Required';
            if (!empty($errors)) return response_form_error('Fix errors', $errors);

            $project = $params['id'] ? Project_Model::find($params['id']) : new Project_Model();
            $project->name       = $params['name'];
            // Empty string -> NULL so the DATE column stays clean
            $project->start_date = !empty($params['start_date']) ? $params['start_date'] : null;
            $project->due_date   = !empty($params['due_date'])   ? $params['due_date']   : null;
            $project->save();

            return ['id' => $project->id];
        }

    (Pattern taken from rsx/app/frontend/projects/projects_controller.php.)

EXAMPLES
    Edit form with two date fields (from the reference app's project editor):

        <Rsx_Form $data="<%= JSON.stringify(this.data.form_data) %>"
                  $controller="Frontend_Projects_Controller" $method="save">
            <Hidden_Input $name="id" />
            <Form_Field $label="Name" $required=true>
                <Text_Input $name="name" $max_length=Project_Model.field_length('name') />
            </Form_Field>
            <Form_Field $label="Start Date">
                <Text_Input $name="start_date" $type="date" $max_length=-1 />
            </Form_Field>
            <Form_Field $label="Due Date">
                <Text_Input $name="due_date" $type="date" $max_length=-1 />
            </Form_Field>
        </Rsx_Form>

    Loading for edit - the model's DATE columns come back as ISO strings, so
    they drop straight into $data:

        async on_load() {
            if (!this.data.is_edit) return;
            const project = await Project_Model.fetch(this.args.id);
            this.data.form_data = {
                id:         project.id,
                name:       project.name || '',
                start_date: project.start_date || '',   // "2025-12-24" or ''
                due_date:   project.due_date   || '',
            };
        }

    Recommended column types:

        start_date   DATE NULL
        start_time   TIME NULL
        event_at     DATETIME NULL

DATABASE SCHEMA NOTES
    - Use real DATE / TIME / DATETIME columns. Rsx_Model_Abstract auto-applies
      Rsx_Date_Cast to DATE columns and Rsx_DateTime_Cast to DATETIME columns;
      never declare $casts with 'date'/'datetime'/'timestamp' (Carbon-backed,
      blocked by rsx:check).
    - Make optional date/time columns NULL and write NULL (not "") when the
      field is blank.
    - A DATE column read through the model yields "YYYY-MM-DD". A DATETIME
      column yields a full ISO 8601 datetime (see time(7)), NOT the truncated
      "YYYY-MM-DDT HH:MM" a datetime-local input emits - the two do not match.

PITFALLS
    datetime-local is NOT an Rsx_Time string.
        A type="datetime-local" input emits "YYYY-MM-DDTHH:MM" - local wall
        time, no timezone offset, no seconds. Rsx_Time works in timezone-aware
        ISO 8601 ("...T15:30:00-06:00"). Feeding a datetime-local value to
        Rsx_Time or a DATETIME column mixes a timezone-less string into a
        timezone-aware pipeline. Prefer separate date + time fields, or convert
        explicitly on the server before storing. Do not assume the two formats
        interchange.

    TIME columns round-trip with seconds.
        MySQL TIME columns are cast to plain strings, so $model->start_time is
        typically "09:00:00", while a native time input's own value is "09:00".
        The native control accepts "09:00:00" for display, but if you compare or
        validate against an "HH:MM" shape, normalize first.

    Empty string is not NULL.
        A cleared native date input submits "". Writing "" to a DATE/TIME column
        errors or stores a zero date. Convert empty to NULL in the save method
        (see SERVER-SIDE HANDLING).

    $max_length is still required.
        Text_Input requires $max_length even for native date/time types. Use -1
        (there is no free-text length to cap); a number would add a meaningless
        HTML maxlength.

    Never set $value.
        As with every RSX input, the value comes from the Rsx_Form $data object
        keyed by $name. Setting $value on the input is wrong and is ignored.

    Native picker only.
        There is no styled RSX date-picker widget - the UI is the browser's
        native control and varies by browser/OS. If a project needs a custom
        picker, build a component extending Form_Input_Abstract (see
        form_input(7)); there is no such component today.
