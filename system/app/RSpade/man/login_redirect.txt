LOGIN_REDIRECT(1)                 RSpade Manual                 LOGIN_REDIRECT(1)

NAME
    login_redirect - thread a validated intended-URL (?redirect=) through a
    multi-hop login flow so a user returns to the page they were trying to reach

SYNOPSIS
    At the auth-rejection point (an app's main.php or the dispatcher):
        return redirect(Rsx::Route('Login_Controller', Login_Redirect::capture($request)));

    Threaded into every route built inside the login flow:
        Rsx::Route('Login_2fa_Controller::index', ['token' => $t] + Login_Redirect::params())

    Dropped into every login-flow Blade form:
        {!! Login_Redirect::hidden_input() !!}

    Consumed exactly once, at the terminal post-login destination:
        return redirect(Login_Redirect::consume(Rsx::Route('Dashboard_Index_Action')));

    Identical-API JavaScript mirror (client-side / expired-session entry):
        window.location = Rsx.Route('Login_Controller', Login_Redirect.capture());

DESCRIPTION
    A user who requests a protected deep URL (e.g. /settings/onedrive) while
    logged out is bounced to login. Without help, the originally requested URL is
    discarded at that 302 and the user always lands on the dashboard afterward.
    Login_Redirect threads that intended URL through the login funnel as a
    ?redirect= query parameter, so the terminal post-login destination can return
    the user to it.

    All validation is centralized in this one class. Application developers wire
    the four calls but never read $_GET['redirect'], never build the param string,
    and never write a second validator - so an open redirect or a malformed value
    cannot be introduced by a downstream app.

    Unlike Laravel's url()->intended() (which stashes the intended URL in the
    server session), RSpade threads the value through the URL. This is a
    deliberate, decided design - see STRATEGY below - not an oversight.

    The param name ("redirect") is a private class constant. Nothing outside the
    class ever types the string; the hidden-input name attribute derives from it
    too.

API REFERENCE
    Login_Redirect::capture(Request $request): array
        Used at the auth-rejection point. Returns ['redirect' => '/path?query']
        only when the request is a plain GET page request worth returning to;
        returns [] for POST, XHR/Ajax requests, framework-internal / asset /
        Ajax-endpoint routes (/_...), external API routes (/api/...), and any
        excluded login-flow route (loop prevention). The value is the requested
        path plus its verbatim (already URL-encoded) query string. The page-path
        and exclusion rules are context-aware: in a portal request the portal
        prefix is a page namespace and the portal exclusion list applies (see
        PORTAL PARITY). The same call is the rejection point for both
        Main::pre_dispatch (staff) and Portal_Main::pre_dispatch (portal).

    Login_Redirect::params(): array
        The threading idiom. Reads the redirect value from the current request
        (GET query or POST body), validates it, and returns ['redirect' => $value]
        or []. Merge it into every route built inside the login flow. Because
        Rsx::Route() URL-encodes extra params, a nested query string in the value
        survives hops with no special handling.

    Login_Redirect::hidden_input(): string
        Emits the escaped <input type="hidden" name="redirect" value="..."> (or ''
        when no valid value is present) for Blade login-flow forms, so a POST
        handler receives the value with zero author thought. The form-POST hop is
        the one most likely to be forgotten when wired by hand; this call exists to
        kill that failure mode. Emit it unescaped in Blade: {!! ... !!} (the call
        escapes the value itself).

    Login_Redirect::consume(string $default): string
        The terminal call. Returns the validated redirect target, or $default when
        the value is absent or invalid. Use it exactly once, at the final-
        destination decision after successful authentication (and after any 2FA /
        site-selection funnels re-enter it). Welcome / onboarding flows still win
        over the redirect target - see the wiring contract.

    The JavaScript mirror (App\RSpade\Core\Js\Login_Redirect) has identical method
    names. capture() there reads window.location.pathname + search (the client-
    side / expired-session entry point); params() reads the current page URL's
    ?redirect=; hidden_input() and consume(default_url) behave as their PHP twins.

THE WIRING CONTRACT
    Every page between the auth rejection and the terminal post-login destination
    must merge Login_Redirect::params() into its outbound login-flow routes and
    include Login_Redirect::hidden_input() in its forms; the rejection point uses
    capture(); the terminal destination decision uses consume() exactly once.

    A hop that drops the param degrades gracefully - the user lands on the default
    destination (today's behavior), never an error. Dropping the param at a hop is
    a legitimate, deliberate choice when a flow owns its own destination (e.g. an
    invite-acceptance flow that always lands on its own workspace). This wiring is
    audited before launch via the prelaunch checklist (see rsx:man
    prelaunch_checklist, entry #1).

VALIDATION GUARANTEES
    The validator (inside params()/consume()/hidden_input(), and used by capture())
    accepts ONLY a local path: a single leading '/', an optional query string
    preserved verbatim. It rejects:
        - protocol-relative values ('//evil.example')
        - any scheme (a ':' before the first '/', e.g. 'javascript:...', 'https:...')
        - any host / absolute URL
        - backslashes (browsers may normalize '\' to '/')
        - control characters and newlines
        - fragments: any '#' rejects the WHOLE value (see FRAGMENTS)
        - login-flow routes (config rsx.login_redirect.excluded_prefixes, default
          ['/login', '/logout']) - loop prevention
        - framework-internal / asset / Ajax-endpoint (/_...) and external API
          (/api/...) paths - a non-page path is rejected by the VALIDATOR too, not
          only by capture(). A hand-threaded ?redirect=/_ajax/... therefore
          degrades in params()/consume() exactly as a captured one would - the
          capture/validate asymmetry is closed.
        - values longer than 2000 characters
        - the no-op bare landing root: a target that reduces to namespace path
          '/' WITH NO query string (staff '/' or the portal prefix root). That is
          where a just-authenticated user lands anyway, so threading it back adds
          only URL noise. A bare root WITH a query string still carries intent and
          is kept. See NO-OP ROOT below.
        - targets that are not routable in the active context: a structurally
          valid path that no REGISTERED GET route handles. See ROUTABILITY below.

    The page-path and loop-prevention rules are CONTEXT-AWARE (see PORTAL PARITY):
    in a portal request the portal prefix is a page namespace (prefix mode) and the
    portal exclusion list applies; staff and portal targets are isolated in both
    directions.

    Invalid, tampered, or hostile values degrade SILENTLY to [] / $default. The
    validator NEVER throws and NEVER flashes an error - a hostile ?redirect= must
    reproduce exactly the pre-feature behavior (the user lands on the dashboard).
    This is a deliberate, documented exception to the framework's fail-loud rule,
    scoped to this class's read/validate paths only.

FRAGMENTS
    Fragments (#...) are deliberately out of scope. Fragments never reach the
    server, so the server-side rejection path can never capture one regardless of
    design. The validated format is path + optional query only; a value containing
    '#' is rejected outright. If a future need appears, widening the validator is a
    separate, backward-compatible change.

NO-OP ROOT
    The bare landing root is the destination a just-authenticated user reaches
    anyway, so capturing it as a return target only produces a noisy
    /login?redirect=%2F URL that changes nothing. The validator therefore drops a
    target that reduces to namespace path '/' when it carries NO query string:

        - staff context:  '/'
        - portal context: the portal prefix root (e.g. /_portal, reduced to the
          namespace path '/' after the prefix is stripped)

    A bare root WITH a query string (e.g. /?tab=activity) still expresses intent
    and is kept. The drop applies both to a captured request (capture() returns [])
    and to a hand-threaded ?redirect=/ (params()/consume() degrade to the default),
    so the two paths stay in parity. This is only the bare-root no-op; it does not
    generalize to stripping ?redirect=/dashboard-style defaults (the per-context
    default landing route is known only at the terminal consume() call).

ROUTABILITY
    A structurally valid path can still point at a page that does not exist as a
    route - a stale or hand-crafted /does-not-exist would 404 the user right after
    a successful login. The validator closes that with a routability gate: the
    target's path must resolve to a REGISTERED GET route in the active context.

        - staff context:  Dispatcher::resolve_url_to_route($path, 'GET')
        - portal context: Portal_Dispatcher::resolve_url_to_route($path, 'GET')

    If neither resolves a route, the value degrades to [] / the default (silent
    degradation, never an error). The gate confirms only that a route PATTERN is
    registered for the URL. It is deliberately NOT:

        - a record-existence probe - /contacts/:id resolving does NOT mean contact
          :id exists; a missing record still 404s at the controller, as always.
        - an authorization check - a route the current user may not view still
          passes the gate. Routable is not the same as reachable; a target the user
          cannot access could bounce again post-login. Closing that fully would
          require a per-context authorization probe (a possible follow-up).

    The match is on GET only (capture() already rejects non-GET requests), so a
    POST-only endpoint correctly reads as "not a page to return to". A portal
    deployment that registers a catch-all portal route (e.g. the template app's
    Portal_Spa_Controller '/*') makes every under-prefix path routable, so in that
    configuration the portal gate only ever drops the no-op root.

STRATEGY - why URL threading, not a session stash (do not redesign)
    URL-param threading was chosen deliberately over a server session stash
    (Laravel's url.intended precedent) and over browser sessionStorage. The
    decisive argument is multi-tab correctness:

        The intended URL is per-NAVIGATION state, not per-BROWSER state. The
        session cookie is shared across tabs. If a user opens two tabs against two
        different protected URLs before logging in - or parks one tab on the plain
        login page while another arrives via a deep link - a session stash is
        last-write-wins: one tab logs in and is sent to the URL the OTHER tab
        captured, or a stale stash from a deep link visited hours earlier hijacks a
        routine login. Threading the value through the URL keeps it attached to the
        exact navigation sequence it belongs to.

    Browser sessionStorage was also rejected: the rejection is a server-side 302,
    so the protected page never renders and no JS ever runs on it - only the server
    knows the intended URL at rejection time.

    The known weakness of threading - "a hop forgot to carry the param" - is
    engineered away: the per-hop cost is one short call, the param name lives in a
    private constant (never hand-typed), and the wiring is documented here and
    audited via the prelaunch checklist. A dropped hop degrades gracefully; it
    never errors.

PORTAL PARITY
    Login_Redirect serves the staff app and the client portal with the SAME four
    calls. It reads Rsx_Portal::is_portal_request() (PHP) / Rsx_Portal.is_portal()
    (JS) and adapts its page-path and loop-prevention rules to the active context;
    application code writes the identical idiom on both sides.

    Prefix mode (no dedicated portal domain - config('rsx.portal.domain') empty)
        Every portal page URL is <prefix>/... (prefix = config('rsx.portal.prefix'),
        default /_portal). In a portal request the validator treats the portal
        prefix as a page namespace: a return target MUST be exactly the prefix or
        start with prefix + '/', and the prefix is stripped before the base rules
        apply. So /_portal/workspace/5 is a valid portal target, while the portal's
        own non-page sub-paths (/_portal/_ajax/..., /_portal/api/v1/...) still
        reject. A path NOT under the prefix (/login, /contacts) is rejected in
        portal context - the staff app and the portal cannot capture each other's
        URLs.

    Domain mode (dedicated portal host configured)
        Portal paths are unprefixed, so the base rules apply directly and the
        portal exclusion list matches un-prefixed.

    Cross-context isolation (both directions)
        In a STAFF request /_portal/... is never a valid target (it is an
        underscore-led non-page path under the base rules). In a PORTAL request a
        non-prefix path is never a valid target. Neither experience can be steered
        onto the other through ?redirect=.

    Loop prevention
        Portal login-flow routes come from config('rsx.login_redirect.
        portal_excluded_prefixes'), expressed in portal-NAMESPACE (unprefixed)
        terms - default ['/login','/logout','/register','/password/reset',
        '/request-access','/impersonate']. In prefix mode the portal prefix is
        stripped from the target before this comparison; in domain mode it matches
        directly. Staff requests keep using excluded_prefixes unchanged.

    Template wiring (shipped)
        Portal_Main::pre_dispatch is the rejection point:
            return redirect(Rsx_Portal::Route('Portal_Login_Controller',
                Login_Redirect::capture($request)));
        The portal login form (and the invitation register form) carry
        {!! Login_Redirect::hidden_input() !!} so the value survives the POST hop.
        Portal_Login_Controller and Portal_Register_Controller consume() at their
        terminal - the flow-owned invited-client workspace still WINS, and
        consume() supplies the dashboard default.

EXAMPLES
    App main.php rejection point:
        public static function pre_dispatch(Request $request, array $params = [])
        {
            if (!Session::is_logged_in()) {
                return redirect(Rsx::Route('Login_Controller', Login_Redirect::capture($request)));
            }
            return null;
        }

    Login form (Blade):
        <form method="POST" action="{{ Rsx::Route('Login_Controller') }}">
            {!! Login_Redirect::hidden_input() !!}
            ...
        </form>

    Terminal destination after successful auth (onboarding still wins):
        if ($needs_onboarding) {
            return redirect(Rsx::Route('Welcome_Controller'));
        }
        return redirect(Login_Redirect::consume(Rsx::Route('Dashboard_Index_Action')));

COMMON PITFALLS
    - Hand-reading $_GET['redirect'] or hand-building the param string. Always go
      through the API; the param name is private for a reason.
    - Writing a second validator "just for this hop". There is exactly ONE
      sanitizer in the codebase (this class); logout uses it too.
    - Letting a redirect skip required onboarding. Onboarding / welcome flows must
      win over the redirect target; consume() supplies the default, not an override.
    - Stashing the intended URL in the session or browser storage. See STRATEGY -
      this breaks multi-tab correctness.
    - Forgetting the hidden_input() on a form-POST hop. This is the most commonly
      dropped hop; the call exists precisely to make it a one-liner.
