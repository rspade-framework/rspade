NOTIFICATION(3)            RSX Framework Manual            NOTIFICATION(3)

NAME
    notification - Per-user notification system with dropdown UI

SYNOPSIS
    Send notification with entity reference:
        use Rsx\Lib\Notification\Notification;
        use Rsx\Models\Notification_Model;

        Notification::send(
            Notification_Model::TYPE_PROJECT_CREATED,
            [$user1_id, $user2_id],
            $project
        );

    Send notification with metadata only (no entity):
        Notification::send(
            Notification_Model::TYPE_TASK_ASSIGNED,
            [$assignee_id],
            null,
            ['task_title' => $task->title]
        );

    Get unread count:
        $count = Notification::get_unread_count();

    Get for dropdown:
        $result = Notification::get_for_dropdown(5);
        // ['notifications' => [...], 'total' => 12, 'unread' => 3]

DESCRIPTION
    The notification system delivers per-user notifications with a dropdown
    UI in the application header. Each notification type has a renderer that
    returns structured data (text, URL, optional image).

    Key Features
        - Per-user notification copies (one row per recipient)
        - Site-scoped (multi-tenant)
        - Optional polymorphic entity reference
        - Read/unread tracking
        - Display expiry (default 21 days): an expired notification is no
          longer shown, but is not deleted
        - Invalid notifications (entity deleted) are left out of every read
        - Nightly maintenance task deletes SEEN notifications older than
          90 days; unseen ones are never deleted; 0 keeps everything

    Components
        - Notification_Model: Main model with type enums
        - Notification helper: send(), get_unread_count(), etc.
        - Notification_Renderer: Render functions per type
        - Notification_Dropdown: Frontend component
        - Frontend_Notifications_Controller: Ajax endpoints
        - Notification_Service::purge: nightly maintenance task

    Database Tables
        notifications    Per-user notification records

API REFERENCE

    Notification::send($type, $user_ids, $entity = null, $metadata = [])
        Send notifications to multiple users.

        Parameters:
            $type       int     Notification_Model::TYPE_* constant
            $user_ids   array   Array of login_user IDs to notify
            $entity     object  Optional: Entity the notification references
            $metadata   array   Optional: Additional context data

        Returns:
            array of Notification_Model instances

        The creator is automatically set from the current session.
        Entity is optional - use metadata for notifications without
        a primary entity reference.

    Notification::get_unread_count()
        Get unread notification count for current user: unexpired, unread
        notifications whose entity still exists - the same set
        get_for_dropdown() counts as unread.

        Returns:
            int

    Notification::get_for_dropdown($limit = 5)
        Get notifications for dropdown display.

        Parameters:
            $limit      int     Max notifications to return (default 5)

        Returns:
            array with keys:
                notifications   Rendered notification data
                total           Total notification count
                unread          Unread count

        Leaves out invalid notifications (entity deleted); deletes nothing.

    Notification::mark_all_read()
        Mark all notifications as read for current user. A mass edit in
        set-based statements: one Site_Lock::write() section per chunk of
        Notification::MARK_ALL_READ_CHUNK (500) rows, each followed by
        Realtime::bulk_changed(), so the caller holds no site lock
        (the endpoint is #[Manual_Lock]; rsx:man site_locks, HOLDING A LOCK
        WELL, rule 8).

        Returns:
            int (number marked)

    Notification::mark_read($notification_id)
        Mark a single notification as read.

        Returns:
            bool (true if found and marked)

NOTIFICATION TYPES
    Types are defined as enums in Notification_Model with a renderer
    property containing FQCN::method that renders the notification.

    Standard types:
        TYPE_CLIENT_CREATED     1
        TYPE_CONTACT_CREATED    10
        TYPE_PROJECT_CREATED    20
        TYPE_TASK_ASSIGNED      30

    Adding Custom Types
        Add to the $enums array in Notification_Model:

            public static $enums = [
                'type_id' => [
                    // ... existing types ...
                    100 => [
                        'constant' => 'TYPE_INVOICE_SENT',
                        'label' => 'Invoice Sent',
                        'renderer' => 'Rsx\\Lib\\Notification\\Notification_Renderer::invoice_sent',
                    ],
                ],
            ];

        Then add the renderer method.

RENDERER PATTERN
    Each notification type has a renderer method that returns structured
    data (NOT HTML like action_log). This allows flexible display.

    Return structure:
        [
            'text' => 'John created project "Website Redesign"',
            'url' => '/projects/123',       // optional, for click navigation
            'image_url' => '/avatars/1.jpg' // optional, for display
        ]

    Example renderer:
        class Notification_Renderer
        {
            public static function project_created(Notification_Model $n): array
            {
                $creator = $n->creator();
                $creator_name = $creator ? $creator->email : 'Someone';
                $project = $n->entity;     // morphTo relation, read as a property

                if (!$project) {
                    return static::result("{$creator_name} created a project (deleted)");
                }

                $url = Rsx::Route('Projects_View_Action', $project->id);
                $text = "{$creator_name} created project \"{$project->name}\"";

                return static::result($text, $url);
            }

            protected static function result($text, $url = null, $image_url = null): array
            {
                return ['text' => $text, 'url' => $url, 'image_url' => $image_url];
            }
        }

    Key points:
    - Methods are static, receive Notification_Model instance
    - Return array with text, url, image_url keys
    - Handle missing entities gracefully
    - Use metadata when entity not available

INVALID NOTIFICATIONS, EXPIRY AND RETENTION
    Two settings, two jobs: EXPIRY decides what is SHOWN, the PURGE setting
    decides what is DELETED.

    A notification with an entity reference is INVALID once that entity no
    longer exists. Every read leaves invalid notifications out and deletes
    nothing:
    - Notification::get_for_dropdown() and get_unread_count() skip them
    - Notification_Model::fetch() reports one as absent

    Notifications without entity references are always valid.

    Expiry is DISPLAY only. It is set at send time
    (rsx.notifications.default_expiry_days, default 21): once expires_at has
    passed, the badge and the dropdown leave the notification out. Expiry
    never deletes the row.

    The read endpoints hold only the site's read lock, so they never write.
    Rows are deleted only by the maintenance task Notification_Service::purge
    (rsx/services/notification_service.php), scheduled in the daily
    maintenance window (#[Schedule('maintenance')], rsx.tasks.maintenance_hour).
    It has ONE rule: a notification the recipient has SEEN (read_at set) is
    deleted once it is older than rsx.notifications.purge_seen_after_days
    days (default 90), measured from created_at. An UNSEEN notification is
    never deleted - expired, orphaned or old. A seen orphan gets no special
    treatment: it waits for the age rule. The task walks every site,
    deleting in batches of 500, each batch under the site's write lock
    (Site_Lock::write()), and reports {deleted, purge_seen_after_days,
    disabled} as its state plus a one-line summary. Run it by hand with:

        php artisan rsx:task:run Notification_Service purge

    SETTING purge_seen_after_days TO 0 DISABLES THE PURGE: nothing is ever
    deleted, and each run reports that it is disabled. An application with a
    "never discard data" policy sets 0.

FRONTEND COMPONENT
    The Notification_Dropdown component displays a bell icon with badge
    and Bootstrap dropdown.

    Features:
        - Unread count badge (hides when 0)
        - Dropdown with notification list
        - Click notification to navigate and mark read
        - "Mark all read" button
        - "Show all (X more)" link when total > limit
        - Auto-refresh on SPA navigation (spa:dispatch event)

    Layout integration:
        <Notification_Dropdown $sid="notification_dropdown" />

    Already included in Frontend_Spa_Layout header.

AJAX ENDPOINTS
    Frontend_Notifications_Controller provides:

        get_count()
            Returns: { count: int }

        get_dropdown({ limit: int })
            Returns: { notifications: [...], total: int, unread: int }

        mark_all_read()
            Returns: { marked: int }

        mark_read({ id: int })
            Returns: { read: true }

CONFIGURATION
    In /rsx/resource/config/rsx.php:

        'notifications' => [
            'default_expiry_days' => 21,     // display only
            'purge_seen_after_days' => 90,   // 0 = never delete
        ],

BEST PRACTICES

    When to Send
        Send notifications in controller POST handlers after success:

            $project->save();
            Action_Log::record(Action_Log_Model::TYPE_PROJECT_CREATED, $project);
            Notification::send(
                Notification_Model::TYPE_PROJECT_CREATED,
                $team_member_ids,
                $project
            );

    Entity vs Metadata
        Use entity reference when:
        - Notification should link to the entity
        - Notification should auto-delete if entity deleted

        Use metadata only when:
        - No specific entity to link
        - Entity might be deleted but notification still relevant
        - Performance matters (no validation overhead)

    Determining Recipients
        The send() method takes an array of user IDs. Your application
        logic determines who to notify:

            // Notify all users except the actor
            $notify_ids = User_Model::where('site_id', $site_id)
                ->where('id', '!=', Session::get_user_id())
                ->pluck('id')
                ->toArray();

            Notification::send($type, $notify_ids, $entity);
