# rsx/app/frontend/tasks — CRUD, following the clients pattern

Follows `rsx/app/frontend/clients/CLAUDE.md` and the app skill `crud-patterns`, with the most divergence of the three: `view/` + `edit/` + `history/`, one controller, one datagrid. **What differs here:**

- **`Tasks_Index_Action.{js,jqhtml}` sits at the feature root, not in `list/`** (which holds only the three datagrid files) — the one structural break in the convention.
- **No export and no bulk actions at all**: no `export_csv`, no `export_xlsx`, no `bulk_delete`; the grid has no footer-actions slot, no select-all column and no row checkboxes, and the page header has no Export button. It does have a single-record `delete`, inside an `Action_Menu` in the view sidebar, but no `restore`/`fetch_deleted`.
- **A composite quick-filter value**: the status select carries a literal `open` option beside the enum, expanded by the query builder into `whereIn(PENDING, IN_PROGRESS)`. The key is `status_filter`, not `status`.
- **The only datagrid with `transform_records()`** — it bucket-loads the polymorphic `taskable` parents into a flat `parent_type`/`parent_label` per row, and maps two sort columns across two joins.
- **`save()` checks every value it writes**: the title's length, `due_date`/`completed_date` as real `YYYY-MM-DD` dates, a declared status and priority - anything else is a field error. The rules and the write live on the model - `Task_Model::value_errors()` and `Task_Model::save_edit()` - because the external API's `POST /api/v1/tasks/create` and `/:id/update` run the same two.
- **A derived column behind the Project picker**: `tasks.project_id` is a DERIVED column on `Task_Model` (`$columns`, `derive_project_id()`) - the project the parent chain reaches, else `direct_project_id`, the user's own choice - and nothing here ever assigns it. The picker's field is `direct_project_id`. When the parent chain reaches a project (`resolve_parent_project()`, asked live as the parent picker changes) the picker is disabled, shows the derived project and is annotated; `Tasks_Edit_Action` remembers the value it held and puts it back when the chain is broken, and its `before_submit` hook leaves `direct_project_id` out of the submission while disabled. `Task_Model::save_edit()` writes `direct_project_id` only when the submission carries it, so the stored choice survives a save under a project chain (the engine still lists the field in `_changed`, because the picker shows a value other than the record's). The model's `save()` rederives every descendant of a re-parented task. `save()` guards cycles. A reference the task already holds (assignee, direct project, parent) is not re-validated, so a task whose referent was since deleted still saves. The view page and the datagrid read `project_id`.
- **`description` is a declared `Rich_Text` column** on `Task_Model`: the edit form names no widget (`<{Task_Model.editor_component_for('description')} />`, which resolves to the WYSIWYG) and its form-data default is `null`, never `''`; the view page prints the value itself, guarded by `is_empty()`. The datagrid's `filter` still searches `tasks.description` with a `LIKE` over the stored markup.
- **The view page carries file attachments** — the reference implementation for every other record type. The Overview tab mounts `<Record_Attachments>` below Description; `task_attachments` lists and `attachments_add` (gated `can_edit_data`) claims uploaded keys, both through `Record_Attachment_List`. The rows load in the action's `on_load()` batch, an upload fires `changed` and the action `refresh()`es, and the claim emits the task's realtime frame so other open views follow. There is no remove action.
- **The edit form's navigation guard follows the form's `'dirty'` event** (on when the user has changed a value - showing the derived project, being programmatic, does not count - off when every value is back or the save succeeds), and goes off on the Cancel link (`@click=this.discard_changes`) and in `on_stop()` - the pattern commented in `../contacts/edit/Contacts_Edit_Action.js`. Skill `rspade:navigation-guard`.
- **`edit/form/` owns two inputs**: `Parent_Selector_Input` (a composite `{type, id}` value, submitted as the one field `taskable` that `save()` and `resolve_parent_project()` read; `save()` writes the `taskable_type`/`taskable_id` pair when `taskable` is in `_changed`, and passes `fields: Task_Model::EDIT_FIELDS` so another editor's re-parent - the pair is `Task_Model`'s `parent` fact group - is asked about instead of overwritten) and `Ajax_Entity_Select_Input`, which `../projects/edit/` also consumes.
